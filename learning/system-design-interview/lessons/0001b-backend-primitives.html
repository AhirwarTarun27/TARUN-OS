Part 1 · SQL vs NoSQL — the real differentiation

First, kill the framing. "NoSQL" is not one database. SQL is one clear thing (the relational model). "NoSQL" is an umbrella over four different data models that each reject the relational table for a different reason. Comparing "SQL vs NoSQL" is like comparing "cars vs not-cars." So step one is to un-blur the not-cars.

What SQL (relational) actually is

Data lives in tables — rows and columns, a fixed schema you define up front (this column is an integer, that one is text, this one can't be null). Tables link by relationships (a photos row points at a users row via user_id), and you recombine them at read time with a JOIN. Postgres, MySQL.

What "NoSQL" actually is — four families

  • Key-value — a giant dictionary. You hand it a key, it hands back a blob. Blindingly fast, no querying inside the value. Redis, DynamoDB, Memcached. (A cache is basically this.)
  • Document — stores JSON-ish documents; each row can have different fields (flexible schema). Good when your data is naturally a nested object. MongoDB, Couchbase.
  • Wide-column — rows keyed for massive horizontal scale and heavy writes; think "a table sliced across a thousand machines by design." Cassandra, HBase, Bigtable.
  • Graph — nodes and edges, for data that is mostly relationships (social graphs, recommendations). Neo4j.

When an interviewer says "would you use NoSQL here," the senior move is to answer which kind and why — "a key-value store for the session cache," "a wide-column store for the photo-metadata feed at write scale" — not the word "NoSQL."

The axes that actually differ

Relational (SQL)

  • Schema: fixed, enforced up front
  • Relationships: JOINs across tables
  • Transactions: ACID, strong consistency
  • Scaling: up + read-replicas; writes/size past one box needs sharding (manual, painful)
  • Best when: structured data, money, anything where "half-done" is a bug

Non-relational (NoSQL)

  • Schema: flexible, per-record
  • Relationships: weak/no JOINs — you denormalize
  • Transactions: often BASE, eventual consistency
  • Scaling: horizontal by design — sharding is built in
  • Best when: huge scale, simple access pattern, flexible/unknown shape, low latency
ACID vs BASE — the two consistency philosophies, one line each ACID (SQL default): a transaction is all-or-nothing and the data is always consistent the instant a write returns. Safe, harder to scale. BASE (many NoSQL): the system stays available and fast, and replicas become consistent eventually (a few ms/s later). You trade "always correct right now" for "always up and fast." This word consistency is the same idea that comes back in caching and replication — hold onto it.
Say this in the interview "I'd default to a relational DB — the data is structured and I want transactions. I'd reach for NoSQL only where a specific tier needs it: a key-value store for sessions and cache, and if photo-metadata reads outgrow one relational cluster, a wide-column store that shards natively. I pick the model per tier, not one database for everything."
The photo-app mapping (ties back to your fatal gap) Users, follows, photo metadata (id, owner, caption, timestamp) → relational to start; strong relationships, small rows. The photo bytes themselves never go in any database — they're large binaries, so they go to object storage (S3 / R2), and the DB stores only the object's key/URL. "SQL vs NoSQL" was never the right question for the pixels — the answer is "neither, it's a blob store."

Part 2 · Caching, and the four scary words

Start with what a cache is, because the four terms only make sense once this is concrete. A cache is a small, very fast, in-memory copy of data that's slow or expensive to get from the real source (the database). You keep the frequently-read stuff there so repeated reads skip the slow path. The database stays the source of truth; the cache is a disposable copy you can rebuild any time.

The read-through pattern (walk it slowly)

Request → Cache? HIT → return (fast) | MISS → read DB → write to cache → return

That's it. "Read-through" just means: always ask the cache first; on a miss, fill it from the DB so next time is a hit. Note what this is not — it's not "put data in Redis instead of the database." The DB is still the truth. The cache just remembers the answer to save a trip. Everything below is a consequence of running that copy.

The four words, from zero

1. TTL — Time To Live. Every entry you put in the cache gets an expiry timer, say 60 seconds. After that it's considered stale and thrown out, so the next read refetches fresh data from the DB. Why it exists: the DB changes, but the cache copy doesn't know that — without an expiry the cache would serve an old answer forever. The tradeoff: short TTL = fresher data but more DB hits (less benefit); long TTL = fewer DB hits but staler data. Picking the TTL is picking your staleness budget.

2. LRU — Least Recently Used (eviction). Cache memory is small and finite. When it fills up, to add a new entry you must throw one out. Which one? LRU throws out the entry that hasn't been touched for the longest time, betting "not used in a while = least likely to be needed next." That decision is the eviction policy; LRU is the common default (others: LFU = least frequently used, FIFO = oldest in). If someone asks "what happens when the cache is full," the word they want is eviction, and the default answer is LRU.

3. Write consistency (cache vs DB drift). Here's the catch with keeping a copy: what happens on a write? A user edits their caption. The DB now has the new value, but the cache still holds the old one. The copy has drifted from the truth, and every reader gets the stale caption until the entry expires. Two fixes: write-through (on a write, update the DB and the cache together) or cache invalidation (on a write, just delete that key — the next read misses and repopulates fresh). This is the same "consistency" idea from ACID/BASE, now between a cache and its DB.

4. SPOF — Single Point Of Failure. If every request funnels through one cache box and that box dies, one of two bad things happens: the app goes down, or every request suddenly stampedes the database all at once (the "thundering herd") and the DB falls over too. A single component whose death takes down the system is a single point of failure. The fix is the same as everywhere else: don't have one — run a cluster of cache nodes with replication, so losing one isn't fatal. (SPOF isn't a cache-only word. The single master DB is a SPOF. One web server is a SPOF. It's the general name for "if this one thing dies, we're dead.")

Say this in the interview (all four, senior-sounding) "I'd put a read-through cache in front of the DB. Four things I'd manage: a TTL so entries don't go stale forever, LRU eviction for when it fills up, write consistency — invalidate or write-through on updates so the cache doesn't drift from the DB — and I'd cluster it so the cache isn't a single point of failure."

Part 3 · Sharding and resharding

Start from the problem, or sharding sounds arbitrary. Replication scales reads only. Add more read-replicas and reads spread out — great. But two things replication does not fix:

  • Every write still goes to the one master. Writes don't scale.
  • Every node still stores the whole dataset. If the data won't fit on one machine, adding replicas doesn't help — they each need to hold all of it too.

So when writes or sheer data size outgrow a single box, you shard: horizontal partitioning. Split the data across N independent databases, each holding a slice. Nobody holds everything.

All users split by shard key → Shard 0 (users A-F) Shard 1 (G-M) Shard 2 (N-S) Shard 3 (T-Z)

Shard key = the field you split on (e.g. user_id). To find a user's row, you run the key through a rule — the classic being user_id % 4 gives you the shard number. A good key spreads data evenly and lets most queries hit a single shard. A bad key piles everyone onto one shard.

Resharding — the word you weren't sure about

You start with 4 shards. Traffic grows, 4 isn't enough, you add a 5th. Resharding is that event: changing the number of shards, which changes the rule that maps data to a shard, which means existing data now lives on the wrong shard and has to physically move to its new home.

Why it's painful: with naive modulo, going from % 4 to % 5 changes the answer for almost every user — nearly the entire dataset has to relocate while the system stays live. The fix is consistent hashing (that's Chapter 5): a smarter mapping where adding a shard moves only a small slice of the data instead of almost all of it. For now you just need the sentence: "resharding is expensive because it moves data; consistent hashing minimizes how much moves."

The other two sharding challenges (name them, don't solve them) Hotspot / celebrity problem: if one shard holds a hugely popular user, that shard gets hammered while others idle — uneven load. Cross-shard queries: a query that spans shards (a global feed, "top photos across everyone") can't do a simple JOIN anymore — the data is on different machines. You either fan out to every shard and merge the results, or you denormalize (pre-store the combined data). Naming these three — resharding, hotspots, cross-shard — is the whole difference between "I'd shard it" and a real answer.
Say this in the interview "Replication scaled my reads, but writes still hit one master and every node holds all the data. So I'd shard by user_id. Three things I'd flag: resharding is expensive because adding a shard moves data — I'd use consistent hashing to limit that; hotspots from a celebrity user on one shard; and cross-shard queries lose JOINs, so I denormalize or fan-out."

Retrieval check

No scrolling up. Pick, then read why.

Why does a cache entry need a TTL?

Data goes stale. The cache is a copy; the DB moves on without telling it. A TTL forces a refetch so the copy can't lie forever. "Which entry to evict when full" is a different word — that's eviction / LRU.

What makes resharding expensive?

Data has to move. More shards = a new key-to-shard mapping, so rows are on the wrong shard and must physically relocate. Consistent hashing exists to shrink how much moves.

Which is the strongest reason to reach for NoSQL over SQL?

Scale + simple access. NoSQL shines when you need to scale out horizontally and your reads are simple key lookups. The other three (JOINs, structure, strong consistency) are exactly what relational is better at.
Tie-it-together: a user updates their caption but still sees the old one. Two possible causes — name both.

(1) Cache drift — the write updated the DB but the cache still holds the old caption; it needed invalidation or write-through. (2) Replication lag — the write hit the master but the read went to a replica that hasn't caught up. Both are the same theme: a copy of the truth (cache, or replica) that hasn't caught up to the source. That theme — consistency of copies — is half of backend system design.
