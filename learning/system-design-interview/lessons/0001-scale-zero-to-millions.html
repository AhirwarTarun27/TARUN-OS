Scale from Zero to Millions of Users

One server to a system that serves millions — as a ladder you can climb out loud. Learn each rung, why you add it, and the one tradeoff it buys.

Read (canonical): ByteByteGo — Scale From Zero To Millions Of Users, the free web version of this chapter by Alex Xu. Why this is Lesson 1 Almost every "design X" prompt is really "start simple, then scale it." This chapter is the backbone move: you narrate a system growing from one box to millions of users, adding one lever at a time and justifying each. Nail this and you always have something to say — even on a system you've never seen. Chapters 4-15 are just this ladder applied to specific products.

Your win for today: close the laptop and narrate the whole ladder from memory — every rung, in order, with the one-line reason you added it. That narration is the interview skill.

Rung 1 · A single server

Everything on one box: web app, database, cache. A user types gradejar.com, and:

User / browser → DNS → IP → Web server (app + DB + cache) → HTML/JSON → User

DNS (usually a managed 3rd-party service) turns the domain into an IP address. The browser hits that IP; the server returns HTML or a JSON response. Web browsers and mobile apps are the two traffic sources. This works fine — until one box can't keep up.

Say this in the interview "I'll start with the simplest thing that works: a single server handling requests, with DNS resolving the domain. Then I'll scale it as we find the bottlenecks." Interviewers want you to start simple.

Rung 2 · Split the web tier and data tier

Move the database off the web server onto its own machine. Now the web tier and data tier can be scaled independently — the whole game from here on.

Which database? A quick fork most candidates fumble. Default to relational (SQL) — Postgres, MySQL — for structured data and multi-row transactions. Reach for non-relational (NoSQL) when you need very low latency, unstructured or huge data, or massive scale with simple query patterns.

Relational (SQL)

  • Joins, transactions, strong consistency
  • Battle-tested, well understood
  • Harder to scale horizontally (sharding)

Non-relational (NoSQL)

  • Scales horizontally with ease
  • Flexible schema, low latency
  • Weak joins, often eventual consistency

Rung 3 · Vertical vs horizontal scaling

Two ways to add power. This distinction is the vocabulary the whole chapter turns on.

Vertical (scale up)

  • Simple — just a bigger box
  • Hard ceiling on one machine
  • No failover — it's a single point of failure

Horizontal (scale out)

  • No real ceiling — add more boxes
  • Redundancy / failover built in
  • More complex — needs a load balancer
Say this in the interview "Vertical scaling is simplest but it has a hard ceiling and no failover. At scale I'll go horizontal — more servers behind a load balancer — for both capacity and redundancy."

Rung 4 · Load balancer

Put a load balancer in front of multiple web servers. Users hit the load balancer's public IP; it forwards each request to a healthy server over private IPs. This removes the web tier's single point of failure and lets you add servers as traffic grows.

Users → Load balancer → Web server 1 Web server 2 Web server N

Rung 5 · Database replication

The DB is now the weak link. Replication: one master (a.k.a. primary) takes all writes; multiple slaves (replicas) take reads. Most apps read far more than they write, so this scales the common case, and gives you reliability and availability.

  • Better performance — reads spread across many replicas.
  • Reliability — data survives if one node dies.
  • Availability — if a replica goes down, others serve; if the master dies, a replica is promoted (failover).

Rung 6 · Cache

A cache is a fast in-memory store (e.g. Redis) for the results of expensive or frequent reads. The web server checks the cache first (a read-through cache): hit → return it; miss → read the DB, store it in cache, return it.

Interview gold — cache considerations Name these unprompted and you sound senior: when to use (read often, write rarely); expiration / TTL (too short = thrash, too long = stale); consistency (cache vs source of truth can drift); eviction (LRU when full); and it's a single point of failure unless replicated.

Rung 7 · CDN

A CDN is a network of geographically distributed edge servers that cache static content — images, CSS, JS, video. A user in Tokyo gets assets from a nearby edge node instead of your origin in Virginia, so latency drops. Watch: TTL (how long to cache), a fallback if the CDN is down, and invalidation when assets change.

Cache vs CDN — don't blur them Cache = your dynamic data / query results, near the server. CDN = static assets, near the user. Different problems, different tiers.

Rung 8 · Stateless web tier

To scale the web tier freely, make it stateless: move session data out of the individual web servers into a shared store (a NoSQL store or cache). Now any server can handle any request, so you can add, remove, or auto-scale servers without breaking a user's session.

Say this in the interview "I'll keep the web tier stateless — session state lives in a shared store, not on the server — so I can autoscale horizontally and any request can hit any node."

Rung 9 · Multiple data centers

For global reach and disaster resilience, run in multiple data centers. geoDNS routes each user to the nearest one. If one DC fails, traffic reroutes to another. The hard parts to name: traffic redirection, data synchronization across DCs, and test/deploy consistency.

Rung 10 · Message queue

A message queue decouples producers from consumers. The web server drops a job on the queue and returns immediately; workers consume and process asynchronously. Producers and consumers scale independently, and a slow consumer can't block the request. Think: sending emails, processing uploads, generating thumbnails.

Rung 11 · Database sharding (scale the data tier)

Replication scales reads, not writes or storage. When one master can't hold or write the data, shard: split the data across many databases by a sharding key (e.g. user_id % 4). Each shard holds a slice; each is independent.

Interview gold — sharding challenges Resharding (adding a shard forces data movement — consistent hashing helps, that's Ch 5), hotspots / the "celebrity problem" (one shard gets hammered), and cross-shard joins (queries spanning shards get painful). Naming these is what separates a real answer.
Taste of Ch 2 (estimation): "millions of users" isn't a number — turn it into load.
10M daily users × 10 requests/day = 100M req/day.
100M ÷ 86,400 s ≈ ~1,160 QPS average, peak maybe 2-3x → ~3,000 QPS.
That number is what tells you how many web servers and replicas you actually need. We drill this next lesson.

The whole ladder — your narration script

This is the thing to memorize. Not the diagrams — this order. Each rung = the bottleneck it fixes.

  1. Single server. Simplest thing that works; DNS → one box.
  2. Split web / data tier. Scale them independently.
  3. Go horizontal. Vertical hits a ceiling and has no failover.
  4. Load balancer. Spread traffic; kill the web-tier SPOF.
  5. DB replication. Master writes, replicas read; reliability + failover.
  6. Cache. Absorb hot reads in memory.
  7. CDN. Serve static assets from the edge, near the user.
  8. Stateless web tier. Session in a shared store → autoscale freely.
  9. Multiple data centers. geoDNS routing; survive a DC outage.
  10. Message queue. Decouple + async; scale workers apart.
  11. Shard the database. Scale writes + storage past one box.

Retrieval check

No scrolling up. Answer, then read why.

What is the main weakness of vertical scaling?

Ceiling and no failover. One machine can only get so big, and if that single box dies the whole service dies. That's why large systems scale out, not just up.

In database replication, who handles write operations?

Only the master. Writes go to the single master; replicas take reads. Most apps read far more than they write, so this scales the common path — and a replica can be promoted if the master fails.

Which problem does sharding solve that replication does not?

Writes and storage. Replication only scales reads — every write still hits one master, and every node still holds the whole dataset. Sharding splits the data across many databases so writes and storage scale horizontally.
Harder: a user reports their new post is missing right after they publish it. What's a likely cause?

Replication lag. The write hit the master, but the read went to a replica that hasn't caught up yet — so the user reads stale data. Common fix: read-your-own-writes (route that user's reads to the master briefly, or read from cache). This is the everyday face of "eventual consistency."

Design out loud — the real rep

Stand up. Out loud, no notes, narrate scaling a photo-sharing app from its first user to 10 million. Force yourself to hit, in order:

  1. Single server + DNS → why you split the data tier off.
  2. Horizontal web tier + load balancer → why not just a bigger box.
  3. Replication → cache → CDN (and which content goes to the CDN, and why).
  4. Stateless tier → message queue (what async job? thumbnail generation).
  5. Sharding → name one challenge (celebrity user? resharding?).

Then tell your teacher (me) to grade it — or record it and self-grade against the ladder above. If you can do this in ~3 minutes without peeking, Chapter 1 is banked.
