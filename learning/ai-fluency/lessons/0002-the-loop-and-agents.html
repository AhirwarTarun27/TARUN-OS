Day 2 · AI Fluency — anchored in devflow

The loop, and agent vs workflow

A workflow is when you decide the steps. An agent is when the model decides the steps. Everything else today hangs off that one sentence.

Where this sits Day 1 gave you the survival sheet — every term with the sentence you say. Today is the first of six days that make one cluster of those terms yours, by teaching it through code you already own. Today's cluster is agent vs workflow, the agentic loop, and stopping conditions. The anchor is devflow. By the end you should be able to draw your own loop on a whiteboard without notes and defend where the gate sits.

0 · Gate check — carried from Day 1

Two from the survival sheet. Answer out loud, cold, before you scroll. If you can't, that's the finding, not a failure — write it in the learning record.

Does the model execute the function in tool calling?

No. The model returns a structured request — "call this function with these arguments" — as JSON matching a schema you gave it. Your code decides whether to run it, runs it, and passes the result back into the conversation.

That gap is the entire security model. The model proposes, your code disposes. People who have only read about tool calling get this wrong. People who have built it never do, which is exactly why interviewers use it as a filter. Volunteer the distinction before they ask.

Why not paste the whole repo into a 200k context window?

Two reasons, and you must give both. Cost is the obvious one and it's the answer that marks you as having read about this. The other is context rot: accuracy degrades as input grows, well before you hit the limit. There is published work testing 18 frontier models where every one got worse as input length grew, on tasks as simple as retrieval.

So a 200k window is not 200k of usable attention. Related term worth dropping: "lost in the middle" — material buried mid-context gets attended to worse than material at either end.

1 · The distinction that generates everything else

Use these definitions. They are Anthropic's, they are the cleanest available, and citing the source by name in an interview is free credibility.

WORKFLOW   LLMs and tools orchestrated through predefined code paths.
           // you wrote the steps. the model fills them in.

AGENT      the LLM dynamically directs its own process and tool usage.
           // the model decides what to do next, and when to stop.

Almost everything marketed as an "AI agent" in 2026 is a workflow with one agentic step inside it. That is not a criticism — it's usually the right design.

The answer that reads senior "Most things don't need an agent." Anthropic's own guidance is that optimising a single call with good retrieval and examples is usually enough. Saying this out loud separates you instantly, because the default candidate is an agent-maximalist. Agents cost more, are harder to debug, and fail in stranger ways.

2 · Your own loop

devflow is mostly a workflow, on purpose. The order is fixed. The agentic behaviour lives inside each stage, not across them.

PHASE 0 · joining a repo (once)
  onboard    survey it → dossier + contract
  setup      make it run on this machine
  orient     teach ME the project, in tiers

PHASE 1 · the front half
  kickoff ABC-123
    ├─ spec       vague request → written spec     (skippable)
    ├─ research   read the code → file:line facts  (REQUIRED)
    └─ plan       facts         → phased plan      (the artifact)

        ══════════════════════════
          I APPROVE          ← the ONLY gate
        ══════════════════════════

PHASE 2 · the build half
  implement   one phase at a time, committed per phase
  verify      build + lint + drive the real app in a browser
  review      critic ∥ impact-mapper, in fresh context
  ship        branch, commit, PR — never merges

PHASE 3
  compound    capture the ONE thing this cycle taught

Eight stages. One gate. If you can't say that number instantly you don't know your own system, and that is the first thing an interviewer will find out.

3 · Why the gate is at the plan

This is the best answer you have about the repo. It is a leverage argument, not a taste argument.

gate at the CODE                    gate at the PLAN
────────────────                    ────────────────
decision already made               reviewing the decision itself
↓                                   ↓
you review its consequences         changing it costs one paragraph
↓
reversing costs hours

a bad line of code  = one bad line
a bad line of plan  = hundreds

There is a second argument and it is about human behaviour, not software:

Say this "One gate is honest. If I put a gate at every stage I'd start rubber-stamping them, because nobody reads the fourth confirmation dialog. One gate I genuinely read is worth more than five I click through."

The skill enforces this in prose — it instructs the model not to ask in a way that invites a reflexive yes, because the gate's whole value is that a human actually reads the plan. Note what that means: you designed against your own laziness. That is a mature thing to have done and it is worth saying out loud.

4 · Stopping conditions — the follow-up nobody prepares for

Once you say the word "agent", a good interviewer asks how it stops. Agents that don't terminate are the single most common production failure in this space.

THE FOUR STOPS

1. iteration limit     "max N tool calls"      crude, always needed
2. budget cap          "max N tokens / $"      the one people forget
3. success condition   the build passes        the good one
4. human checkpoint    it asks                 the expensive one

Yours, concretely: the approval gate at the plan is a #4. The Stop hook is a #3 — it refuses to end the turn until the verify chain passes. And the platform force-ends after 8 consecutive blocks, which is a #1 acting as a backstop so a genuinely broken build can't trap the session.

Why is a budget cap the one people forget?

Because it only bites when something has already gone wrong. Iteration limits catch loops; success conditions catch completion. A budget cap catches the case where the agent is making progress in a direction that isn't worth what it costs — which feels fine from inside the loop and is obvious only on the invoice.

This is also the honest link to cost as a first-class concern, which is Day 7. Bring a rough number to an interview and you're ahead of nearly everyone.

5 · Research before planning, and why it isn't optional

In your loop, spec is skippable and research is required. That asymmetry is deliberate and it is worth being able to defend.

plan WITHOUT research          plan WITH research
─────────────────────          ──────────────────
model recalls how projects     scouts read THIS repo
"usually" look                 ↓
↓                              plan cites real file:line
plan references files that     ↓
don't exist, patterns this     every phase points at
repo doesn't use               something that exists
Say this "Never plan from assumption. The plan's file paths come from research having read the actual code. Otherwise the plan is fiction that happens to be well-formatted — and well-formatted fiction is harder to catch than obvious nonsense."

6 · The calibration

You have been working this way for about a year. The plugin is recent — it is the extraction, not the experiment. Keep those two facts separate and never merge them: "I've worked this way for a year" is true and is your real credential; "this repo is a year old" is false and takes one click to disprove.

The stages therefore have different mileage. Onboarding and verification you run daily. The full kickoff-to-PR chain exactly as written, less — because on the live project you adapted the artifact layout rather than following your own pipeline.

The adaptation is a strength — say it that way "I designed it to write specs, research and plans as separate documents. On the real project I collapsed that into one working document plus a run log, because the ceremony wasn't paying for itself at the size of changes I was making. A workflow you follow rigidly when it isn't earning its keep is just process."

That answer is better than claiming you follow it perfectly, because it demonstrates you evaluate your own system instead of defending it.

7 · Retrieval quiz

What separates a workflow from an agent?

Who decides the steps. Workflow = predefined code paths you wrote. Agent = the model dynamically directs its own process. Tools, loops and model count are all irrelevant to the distinction.

Where is the single approval gate in devflow?

At the plan. Leverage: a bad line of code is one bad line; a bad line of a plan becomes hundreds. Saying "at the PR" describes an ordinary git workflow and throws away the whole idea.

Which stage is required, not skippable?

Research. Spec is skippable when the request is already unambiguous. Research is not, because the plan's real file paths come from it. Planning from assumption produces well-formatted fiction.

Interviewer: "When would you NOT use an agent?"

Most of the time. This is the answer that reads senior, because the default candidate is an agent-maximalist. Agents cost more, debug worse, and fail in stranger ways. Reach for one when the path genuinely can't be predetermined.

Which is not a stopping condition?

Temperature. That controls sampling randomness, not termination. The four real stops are iteration limit, budget cap, success condition, human checkpoint.
