The two performances

This is one curriculum serving two goals that are not the same skill. Everything about how each session is structured follows from this table.

Node.js — write and speak

  • Goal: clear a backend interview
  • You already know JS and Express
  • You compose from a blank file
  • Failure looks like: freezing on a blank file

C# / .NET — read and explain

  • Goal: get shortlisted, then hold the job
  • You know zero C#
  • You transcribe, then review
  • Failure looks like: approving a PR you can't audit
Why they are trained differently Typing equal amounts in both languages spends half the block on the half that does not need composition. You will never be asked to write C# from a blank file under time pressure. You will be asked to explain why a .Result call took production down.
The thing that actually gets people fired Your plan is to have AI write the high-level C#. Fine. But the risk was never that you cannot write it — it is that you approve what you cannot read. Three bugs that ship silently, all of which a Node developer writes without flinching: .Result on a controller (deadlocks on Framework), a static field on a controller (a race under a thread pool), a lazy-loaded navigation property in a loop (an N+1 nobody sees until the table grows). Every .NET session here ends with you finding a planted bug and saying why.

Where the code gets typed

  • Lab: MyProjects/backend-lab/, its own repo, outside the AIOS. One Node project, one VS solution, a folder per session. node_modules plus bin/obj/packages would bury the workspace and slow every search in it.
  • Node in VS Code. C# in Visual Studio 2022. Not VS Code and not dotnet new — neither will scaffold .NET Framework web projects, and the old .csproj format needs real VS.
  • The AI reads your code and never edits it. A bug gets reported with the reasoning; you type the fix. Every line written for you is a rep you do not get.
C# 7.3 is a hard ceiling .NET Framework 4.8 cannot compile record, init setters, switch expressions, top-level statements, file-scoped namespaces or nullable reference types. Most C# written after 2020 targets .NET 5+ and will not build for you. That is not you doing it wrong. When a lesson shows the clumsy 7.3 way, it is because the elegant way does not exist on your runtime — and it will say so, because you will meet the modern version on Stack Overflow and need to recognise it as the wrong .NET.

Phase A · C# through JavaScript

Fast, and first, because reading .NET is impossible without it. Pure correlation: you never meet a C# construct without its JS counterpart on the same line. Two sessions, then straight into .NET.

01 C# for a JS dev — the file in progress · Build B owed

  • namespace / class / method vs module / function — the layers JS has no word for
  • var in C# is inferred static type, not JS var. Same word, opposite meaning.
  • Value vs reference types, and why int cannot be null unless you ask
  • Properties vs fields vs object properties · access modifiers · $"" vs template literals
  • List<T> and Dictionary<K,V> vs array and Map

Build: a Node script you compose, then the same shapes transcribed in C#. Review: the FirstOrDefault returns 0 trap.

02 C# for a JS dev — the shapes next

  • Interfaces, and why enterprise .NET has so many of them
  • Generics, which will feel like TypeScript generics until they do not
  • LINQ is your array methods — Select/Where/FirstOrDefault/Any/OrderBy
  • Exceptions vs error-first callbacks · using and IDisposable
  • async/await syntax only. The machinery is day 4, and it is not what you expect.

Build: the same transform pipeline in array methods and in LINQ. Review: a missing using leaking a connection.

Phase B · The machine underneath

Where internals enter, and the only place they do. Every difference between these two runtimes is a fact about threads, memory or syscalls. Learn the fact once and both languages stop being magic.

03 What a server actually is the foundation

  • Process, thread, socket, syscall, and the accept loop underneath every framework
  • Node = one thread and an event loop. Plus a libuv pool of 4 that most people forget exists.
  • .NET = a real thread pool, requests genuinely in parallel, plus IOCP
  • Why every shared, static or cached thing you write is now a potential bug

Build: a raw TCP echo server in net, no framework. Review: a static field on a controller.

04 async/await — one keyword, two machines the important one

  • Promise is cold and always async. Task is hot and can complete synchronously.
  • Microtask queue vs SynchronizationContext · thread hopping across an await
  • .Result and .Wait() deadlock on Framework — and the bug vanished in .NET Core, which is exactly why nothing you google will warn you
  • Stack, heap and GC generations — which is where day 1's "int cannot be null" finally means something

Build: Promise.all vs sequential await, timed. Review: cause the deadlock and watch it hang.

Phase C · .NET proper — the shortlisting payload

After session 6 you can hold the management conversation: trace a request end to end, name the four places .NET differs from Node and why, and say what you would watch for in a review.

05 The request pipeline next

  • Express's one (req, res, next) chain vs Web API 2's four extension points
  • Global.asax, WebApiConfig, attribute vs convention routing
  • Model binding — how JSON becomes a typed parameter before your code runs
  • Breakpoints and the call stack, which beat console.log outright

Build: a 3-endpoint Express API with middleware, composed from blank. Review: a filter ordering bug that skips auth.

06 DI, lifetimes, layering next

  • Constructor injection, and why session 2's interfaces suddenly pay off
  • Singleton vs Scoped vs Transient as one question: who owns this memory, and which thread touches it
  • No Node equivalent — and it only makes sense after session 3. Order matters.
  • Controller → Service → Repository, and why Node mostly does not need a container

Build: the same API refactored into layers with factory functions. Review: a DbContext registered as a Singleton.

Phase D · Data and SQL

Both stacks query the same LocalDB database, so the only variable is the client library. The schema ships deliberately un-indexed. You add the indexes here and measure what changed.

07 SQL — the query interview gold

  • An index is a B-tree over disk pages. That one fact explains every "why is this slow".
  • Joins · reading an execution plan · what a table scan costs at 20,000 rows
  • Raw SQL through mssql vs EF6 LINQ, and the SQL EF actually emitted
  • IEnumerable vs IQueryable — deferred execution, and where the filtering really happened

Build: the same query three ways, plan read for each. Review: a Where after .ToList().

08 SQL — connections and correctness next

  • Connection pooling, because a socket is expensive — the same internals fact as session 3
  • Transactions and isolation levels, in the language an interviewer expects
  • The N+1, in both stacks, and .Include() vs eager loading
  • new HttpClient() per request: socket exhaustion, the same lesson in a different suit

Build: cause an N+1 in Node, then fix it. Review: the HttpClient leak.

Phase E · The two performances

09 Errors, auth, production shape next

  • Exceptions vs error-first callbacks — in .NET, everything throws
  • Global exception filters and structured logging · DataAnnotations and ModelState
  • JWT on both sides, and the [Authorize] attribute
  • Config and secrets: Web.config vs .env, and where secrets do not go

Build: auth middleware in Express, composed from blank. Review: a secret in Web.config.

10 The double mock the exam

  • A. 45-minute Node backend interview. Speak and write, live, with follow-ups pushed two deep.
  • B. The management pitch. Explain the .NET pipeline and what you would watch for, in ten minutes, without bluffing.
  • C. A cold code review of AI-generated C# with unannounced bugs. No hints about how many.

Done when: both performances land without notes, and the drill board says so.

Pace

Ten sessions of two hours, in the 3:00-5:00pm block. Days 1-6 produce the internal-shortlisting outcome. Days 7-10 make the interview solid. Node is written every single day, never deferred.

Don't rush Phase A Reading fluency is the gate on everything after it. Two sessions on C#-the-language feels like a detour when .NET is what you actually need — it is the opposite. Every session from 3 onwards assumes you can read a C# file without stopping to decode the syntax. Sessions 4 and 7 are the two worth slowing down for a second sitting.
This map is not fixed. If work hands you a real task tomorrow, say so — the order gets rewritten around what you actually need. That is the whole advantage of learning against a real job instead of a syllabus. And a failed gate check re-drills yesterday instead of starting today. The lesson can wait a day. A concept that half-landed and then got buried cannot be recovered later.
