Session 1 · Phase A — C# through JavaScript

C# for a JS dev: the file

Everything you need to open a C# file and know what you are looking at. Nothing more.

Where this sits You cannot read .NET until you can read C#, and .NET is the part that pays. So this session and the next are the on-ramp, and they are deliberately fast. Nothing here is a backend concept — no HTTP, no routing, no ORM. You already own all of that. This is vocabulary, and vocabulary is cheap if you learn it against words you already have.

Every C# thing below arrives beside its JavaScript counterpart. If you ever see a C# construct in this course with no JS column next to it, that is a bug in the lesson. Tell me.

1 · The layers above the code

JavaScript has two containers: the file, and the function. C# has four, and the two extra ones are where new readers get lost — not because they are hard, but because nothing in JS occupies that slot.

JavaScript / Node
C# / .NET

→
namespace — a naming scope, declared in the file
a .js file / module
→
a .cs file — but the file name means nothing
class or a factory function
→
class — and everything must live inside one
require / import
→
using System.Text; — imports a namespace, not a file
package.json · npm
→
.csproj · NuGet · and a project above that
— no equivalent
→
solution (.sln) — several projects built together
using is not import. It does not pull in a file and it does not create a binding you can rename. It says "when I write StringBuilder, look in System.Text too." The code was already linked at compile time. using only saves you from typing the full name.

So the smallest legal C# file has three levels of nesting before you get to a line that does anything. That is not ceremony for its own sake — it is what makes a compiler able to find any symbol in a million-line codebase without reading every file.

You will see this written differently online Modern C# lets you write namespace HelpDesk.Core; on one line with no braces — a file-scoped namespace. It is nicer. It does not compile on .NET Framework 4.8. When you see it in a Stack Overflow answer, that answer is for the wrong .NET. Keep the braces.

2 · var is a false friend

Same three letters, near-opposite meaning. This is the single most likely thing to mislead you in week one, so it gets its own section.

JavaScript
C#
var = function-scoped, hoisted, retype freely
→
var = infer the static type, then lock it
let x = 1; x = "hi"; is fine
→
var x = 1; x = "hi"; will not compile
var in C# is a typing shortcut, not a looseness. var x = 1; and int x = 1; compile to byte-identical output. The variable is an int forever. Reading C#, treat var as "the type is obvious from the right-hand side" — and if it is not obvious to you, that is the compiler's hint that the line deserves a second look.

In C#, what does var actually do?

Infers one fixed type at compile time. The compiler reads the right-hand side, picks the type, and locks it. There is no runtime flexibility involved at all — var x = 1 is literally int x = 1 after compilation. C# does have a genuinely dynamic type, spelled dynamic, and you will almost never see it in a well-kept codebase.

if (someString) and if (count) do not compile. There is no truthiness in C#. if takes a bool and nothing else, so you write if (count > 0) and if (!string.IsNullOrEmpty(name)). Every falsy-value bug you have ever debugged in JS is structurally impossible here, and every "just check the value" shortcut is gone with it.

4 · Value types and reference types

This is the concept the rest of C# hangs off. It is also the first place where the machine underneath becomes visible, so it is worth slowing down on.

the machine A running program has two places to put things. The stack is a scratch area per thread: push on call, pop on return, effectively free, and it dies when the method returns. The heap is a shared pool that outlives any single call and has to be garbage collected.

JavaScript hides this from you completely — every object is on the heap and every variable holds a reference. C# lets you choose, and that choice is what "value type vs reference type" means. A value type holds the bytes; a reference type holds an address pointing at the bytes.
JavaScript
C#
primitives copy · objects share
→
value types copy · reference types share
number, boolean, string
→
int, bool, double, decimal, DateTime, struct, enum
{}, [], functions
→
class, interface, arrays, string, delegates
string is a reference type in C# but behaves like a value because it is immutable — exactly like JS strings. It is the one type that sits in both mental buckets, and interviewers like asking about it for that reason.

The consequence that actually bites: a value type has no null. It always holds a real value, and if you never assigned one, it holds the type's zero.

int    a;          // default 0     — not undefined, not null
bool   b;          // default false
string s;          // default null  — string is a reference type

int  id = null;    // compile error. int cannot hold null.
int? id = null;    // fine. int? is Nullable<int>, a different type.
The bug this causes, over and over In JS, a property you never set is undefined, which is falsy and obvious. In C#, an int property you never set is 0 — which is a perfectly valid id, quantity or price. "Not provided" and "zero" become the same value, and nothing warns you. This is why you will see int? all over real .NET code: it is how the codebase says "this one is genuinely optional".
Two nullables, and only one of them exists for you int? — a nullable value type. Been in C# since 2005. You have it.
string? — a nullable reference type. C# 8, .NET Core era. You do not have it, and on Framework 4.8 it will not compile. Reference types are already nullable; the ? was only ever an annotation for the compiler to warn you. Expect null checks by hand.

A class has an unassigned public int Count; field. What is its value?

Zero, because int cannot hold null. Value types always hold a real value, and the runtime zeroes the memory for you. That is exactly the trap: the field looks legitimately set to 0 and you cannot tell it apart from someone genuinely passing zero. If "unset" needs to be distinguishable, the field has to be int?.

5 · Properties, not object literals

JS objects are bags you can add to at any time. C# objects have a fixed shape decided at compile time. The declaration is longer; the payoff is that the compiler catches every typo'd field name.

JavaScript
C#
a plain key on an object
→
field — private int _count;, usually hidden
get / set accessor
→
property — public int Count { get; set; }
#privateField
→
private — and it is enforced by the compiler
{ get; set; } looks like it does nothing, and that is the point — it is an auto-property. The compiler generates a hidden backing field plus a getter and setter method. It matters because a property is a pair of method calls, not a memory slot, so it can be put on an interface, intercepted, or made read-only later without breaking any caller.

The convention that will trip your fingers: C# uses PascalCase for everything public — classes, methods, properties. camelCase is only for locals and parameters. A private field is usually _leadingUnderscore. This is not preference; every codebase you touch will follow it.

int[] is a fixed-size array — it has Length and no .Add(). If you want JS array behaviour, you want List<T>, and that is what real code uses almost everywhere. The <T> is not optional decoration: List<Ticket> can only ever hold tickets, so the compiler already knows the type of every element you pull out of it.

Which line will the C# compiler reject?

if (tickets.Count). Count is an int, and if requires a bool. There is no truthiness to fall back on, so you write if (tickets.Count > 0). The other three are all valid — ?? is the null-coalescing operator and works exactly like it does in modern JS.

8 · The compiler is now your fastest feedback loop

The habit shift that matters more than any syntax on this page.

In Node you find out something is wrong by running it. In C# you find out by building it, and the build is faster than the run. Roughly the whole class of bug you are used to hunting — typo'd property name, wrong shape passed to a function, forgot to handle a case — is now a red squiggle before you leave the file. Read the first error, not the last. One real error commonly produces a cascade of twenty, and fixing the first usually clears the rest.

Build A — Node · you compose this from blank

In backend-lab/node/01-the-file/tickets.js. No copying, no reference. This is the interview rep, so struggling here is the point.

  1. An array of 4 ticket objects: id, title, status, assignedToId. Leave assignedToId unset on two of them — actually unset, not null.
  2. findById(id) — returns the ticket or undefined.
  3. summarize(ticket) — a template literal, "#3 Login fails [open]".
  4. unassignedCount() — how many have no assignee. Decide what "no assignee" means and write down the check you used. You will need that decision in ten minutes.
  5. Run it. Print all four summaries and the count.

it prints four lines and a count, and you can say out loud what findById(99) returns.

Build B — C# · you transcribe this

New Console App in Visual Studio 2022, targeting .NET Framework 4.8, saved to backend-lab/dotnet/. Type it; do not paste. The goal is that your fingers stop treating { get; set; } as strange.

  1. A Ticket class with Id, Title, Status and AssignedToId. Choose the type of AssignedToId yourself and be ready to defend it.
  2. A List<Ticket> with the same four tickets.
  3. FindById — a foreach, returning null when nothing matches. No LINQ; that is session 2.

Code review — you are the reviewer

This compiles, passes review, and ships. It is wrong. One bug, and it is the exact thing a Node developer writes without noticing.

public class TicketFilter
{
    public int    AssignedToId { get; set; }
    public string Status       { get; set; }
}

public List<Ticket> Search(TicketFilter filter)
{
    var results = new List<Ticket>();

    foreach (var t in _allTickets)
    {
        if (t.Status == filter.Status &&
            t.AssignedToId == filter.AssignedToId)
        {
            results.Add(t);
        }
    }
    return results;
}

// caller — the user only filtered by status
var filter = new TicketFilter { Status = "open" };
var open   = Search(filter);
// returns 0 rows. Nobody knows why.

What is the bug, and why would the same code in JavaScript have worked?

The answer

The caller never set AssignedToId, so it is 0, not null. The filter then silently demands "assigned to user 0", which is nobody, so the result is empty. There is no error, no warning, and no null reference to trace. It just quietly returns nothing.

Why JS is safe here: an unset property is undefined, so t.assignedToId === filter.assignedToId is comparing against undefined and the mistake shows up immediately, or the developer writes a truthiness guard out of habit. C# has no undefined and no truthiness, so the zero looks like a deliberate value.

The fix: public int? AssignedToId { get; set; }, and guard the comparison — (filter.AssignedToId == null || t.AssignedToId == filter.AssignedToId). The type now carries the meaning "optional", which is what int? is for and why you see it everywhere in real .NET.

Say this part out loud: "a value type has no null, so unset and zero are the same value, and the type system cannot tell them apart unless I ask for int?." That sentence is the whole session.
