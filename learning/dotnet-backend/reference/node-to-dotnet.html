Reference · .NET Framework Backend

Node → .NET Framework 4.8

The translation sheet. Keep this open while you read code at work. Green is what you already know. Blue is what it is called in .NET. The amber line is where the mapping breaks — that is the part worth your attention.

Scope This sheet is for .NET Framework 4.8 (Web API 2 / MVC 5 / System.Web), not .NET Core or .NET 8-9. Where modern .NET differs in a way that will confuse you while googling, it is marked [Core differs]. See the course map for the session each row is taught in.

1 · Project and dependencies

Node
.NET Framework
package.json
→
HelpDesk.Api.csproj
(no equivalent)
→
HelpDesk.sln — the solution
Node has no concept above the package. A .sln groups several .csproj projects that compile into separate assemblies (.dll files) and reference each other at compile time. A project cannot use another project's code unless a reference is added explicitly. There is no require('../other') across projects.
node_modules/
→
packages/ + bin/
npm install express
→
Install-Package Microsoft.AspNet.WebApi
Run from Package Manager Console in Visual Studio, not a terminal. NuGet also edits your .csproj and sometimes Web.config — it is not the inert dependency drop that npm is. [Core differs: uses dotnet add package and a clean SDK-style csproj]
.env
→
Web.config
Web.config is XML, is committed to source control, and configures the web server as well as your app. Secrets do not belong in it. Changing it restarts your application — there is no equivalent of quietly editing .env and restarting nodemon.
node server.js
→
IIS / IIS Express hosts your DLL
You do not own main(). There is no process you start that listens on a port. You compile a library, and IIS loads it into a worker process (an app pool) that it controls, and can recycle out from under you. This is the biggest mental shift in the whole list.

2 · The language

JavaScript
C# 7.3
const x = 5
→
var x = 5; // still statically typed
var in C# is not var in JS. It means "infer the type at compile time and lock it in", not "any type". var x = 5; x = "hi"; does not compile.
module.exports = {}
→
public class / namespace
There are no free-floating functions. Every piece of code lives inside a class. A file's folder path and its namespace are conventionally kept in sync, but nothing enforces it.
require('./x')
→
using HelpDesk.Core;
using imports a namespace, not a file, and it is only shorthand — the reference must already exist in the .csproj. Also: using has a completely unrelated second meaning as a statement (using (var db = ...)) that means "dispose this when the block ends".
{ id: 1, title: "x" }
→
new Ticket { Id = 1, Title = "x" }
No anonymous object literals flying around as your data model. You define a class first, always. This feels heavy for a week and then becomes the reason the compiler catches your typos.
arr.map(x => x.name)
→
list.Select(x => x.Name)
Nothing executes until the result is enumerated (.ToList(), foreach). This is deferred execution and it is the #1 LINQ surprise. See section 5.
arr.filter / .reduce / .find
→
.Where / .Aggregate / .FirstOrDefault
.First() throws when nothing matches. .FirstOrDefault() returns null for classes, but 0 for int and false for bool. A "not found" can silently become a real-looking zero.
null / undefined
→
null (and int? for nullable value types)
No undefined. And int, bool, DateTime cannot be null unless declared int?. An unset int is 0, and an unset DateTime is 1/1/0001, not null.
`Hello ${name}`
→
$"Hello {name}"
try/catch/finally
→
try/catch/finally — same
One real difference: errors are thrown, never returned. There is no error-first callback and no [err, result] tuple convention. If a method can fail, it throws, and an uncaught throw is a 500.
The C# 7.3 ceiling .NET Framework 4.8 caps at C# 7.3. Records, top-level statements, init setters, switch expressions, file-scoped namespaces, and nullable reference types are all C# 8, 9, or later and will not compile for you. Most C# written on the internet since 2020 assumes .NET 5+. When you google C# and the answer looks unusually clean, that is the tell. Verified via Microsoft's language versioning docs.

3 · The request pipeline

Express
Web API 2
app.js / server.js
→
Global.asax + App_Start/WebApiConfig.cs
Startup is split across files by convention, and Global.asax.cs is where the app lifecycle events live (Application_Start). Nothing points at it — you are expected to know it is the entry point. [Core differs: one Program.cs]
app.get('/tickets', handler)
→
[HttpGet, Route("tickets")] public ...
Routes are attributes on methods or a central convention template, not registration calls. Order of registration mostly does not matter the way it does in Express, but attribute and convention routing can conflict in ways that are genuinely hard to debug.
router / controller module
→
public class TicketsController : ApiController
The class name is load-bearing. TicketsController serves /api/tickets because the framework strips the word "Controller". Rename the class, break the route.
(req, res, next) => {}
→
DelegatingHandler
The closest true middleware analogue: it wraps the whole request and calls the next handler. But .NET splits the job Express does with one signature into four different extension points, each at a different depth — see the trap below.
route-specific middleware
→
ActionFilterAttribute
Applied by decorating a controller or method ([Authorize], [ValidateModel]), or registered globally. Declarative rather than positional.
error-handling middleware
→
ExceptionFilterAttribute / IExceptionHandler
req.body (after body-parser)
→
a typed method parameter
Model binding deserializes the JSON body straight into your class before your code runs. You never touch the raw body. If a field will not bind, your parameter is silently null — it does not throw. Check ModelState.IsValid.
res.json(data)
→
return Ok(data);
You return a result, you do not write to a response object. Serialization to JSON happens after you return, via content negotiation — which means a serialization crash happens outside your try/catch.
res.status(404).send()
→
return NotFound();
Express's one hook is .NET's four In Express, everything is (req, res, next) and position in the chain decides when it runs. Web API 2 splits that into message handlers (whole request, earliest), authorization filters, action filters (around your method), and exception filters. Picking the wrong one is the most common structural mistake a Node dev makes in .NET — the code works, but runs at the wrong depth and misses cases. When you need cross-cutting behaviour, the first question is which layer, not what code.

4 · Concurrency — the section that will actually bite you

Read this one twice Node runs your JS on one thread. Two requests never execute your handler code simultaneously. That single fact quietly protects every module-level variable you have ever written.

.NET uses a thread pool. Requests run genuinely in parallel on different threads, inside one process, sharing memory. Every habit built on Node's single thread is now a potential production bug — and it will be the kind that only shows up under load, on the server, intermittently.
Node
.NET Framework
event loop, single-threaded
→
thread pool, multi-threaded
A static field, a cached singleton, or a shared Dictionary is now touched by many threads at once. Dictionary<K,V> and List<T> are not thread-safe — concurrent writes can corrupt them or hang the process. Use ConcurrentDictionary or a lock.
Promise
→
Task / Task<T>
A Promise is always asynchronous. A Task may already be complete when you receive it, and await on a completed Task runs synchronously on the same thread. Same keyword, different machine underneath.
async/await
→
async/await — identical syntax
Identical syntax is exactly what makes this dangerous. There is no event loop, no microtask queue, and after an await your code may resume on a different thread than it started on. Thread-local assumptions break across an await.
await somePromise
→
await someTask ✅
(no equivalent — cannot block)
→
task.Result / task.Wait() ☠
This deadlocks your request on ASP.NET Framework. Not slow — hung, forever. The request context allows one thread in at a time; you block it waiting for a task that needs that same context to finish. JS physically cannot do this, so you have no instinct against it. Stephen Cleary explains the mechanism. [Core differs: no SynchronizationContext, so it does not deadlock there — which is why most modern advice will never warn you]
Promise.all([a, b])
→
await Task.WhenAll(a, b)
Note WhenAll (awaitable), not WaitAll (blocking — same deadlock trap as above).

5 · Data access

Node
.NET Framework
Sequelize / Prisma / Mongoose
→
Entity Framework 6 (EF6)
EF6 is the Framework-era version. EF Core is a different product, not an upgrade — the APIs diverge and its docs will mislead you. Confirm any EF answer is tagged EF6.
the db client/connection
→
DbContext
DbContext is not thread-safe and is meant to live for one request. Making it a singleton — the instinct from a Node connection pool you create once at boot — is a classic and severe .NET bug. It ties directly to section 4.
Model.findAll({ where })
→
db.Tickets.Where(t => t.IsOpen)
This returns IQueryable, and your lambda is translated into SQL, not run in C#. So you cannot call an arbitrary C# method inside it — EF will not know how to translate it and throws at runtime, not compile time.
(query runs immediately)
→
deferred until .ToList() / foreach
Building a query costs nothing and hits no database. Enumerating it twice hits the database twice. And an IQueryable returned from a method whose DbContext has been disposed throws when someone finally enumerates it — far from the actual mistake.
include / populate
→
.Include(t => t.Comments)
Without .Include, EF6 lazy loads by default: touching ticket.Comments in a loop silently fires one query per row. The N+1 is invisible in the C# — it reads like plain property access.
await model.save()
→
await db.SaveChangesAsync();
You do not save an object — you mutate tracked objects and then commit the whole context at once. EF works out the SQL by diffing what it tracked. Change tracking has no Node equivalent and is the core mental model of EF.

6 · Wiring things together

Node
.NET Framework
require() a module, use it
→
constructor injection + a DI container
Classes declare what they need as constructor parameters and a container supplies them. This is why enterprise .NET has an interface for nearly everything — it is not ceremony, it is what makes the code swappable and testable. [Framework has NO built-in container — a codebase picks Unity, Autofac, or Ninject. Core has one built in.]
module cache (accidental singleton)
→
explicit lifetime registration
Three choices with no Node equivalent: Singleton (one for the whole app, shared across threads — must be thread-safe), Scoped (one per request — what DbContext needs), Transient (new every time). Registering a DbContext as Singleton is the bug that connects sections 4, 5, and 6 into one incident.
console.log
→
log4net / NLog / Serilog
No built-in logger in Framework. Whatever the codebase already uses is the answer — do not introduce a fourth one.
jest / mocha
→
xUnit / NUnit / MSTest + Moq
Tests live in a separate project in the solution, not a __tests__ folder. Moq fills the role jest.mock() plays, and it only works against interfaces or virtual methods — another reason for all those interfaces.

The five things worth actually memorizing

  1. Requests run in parallel. Shared mutable state is a bug now. Node's single thread was protecting you and it is gone.
  2. Never .Result or .Wait(). It deadlocks the request on Framework. Async all the way down.
  3. DbContext is per-request. Not a connection pool you make once. Scoped, never Singleton.
  4. LINQ does not run when you write it. Deferred. And IQueryable is secretly SQL.
  5. You are on C# 7.3. Half the C# on the internet will not compile for you. Check before you copy.
