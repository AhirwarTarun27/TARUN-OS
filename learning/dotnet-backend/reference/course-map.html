Course Map · .NET Framework Backend

Ten sessions to useful

Read → Write → Ship. One project throughout. Every session ends in code you type yourself.

Progress:  0 of 10

The deal This runs in your office blocks (3:30-5:30pm, 10:00-11:30pm) — employer-assigned work paid for with employer hours. It never touches dsa, machine-coding, sysdesign, or interview-qa. Those are the job-hunt engine and they outrank this. If .NET starts eating them, that is a failure state, not progress.
Why ten and not fifty The goal is not mastery of .NET. It is time-to-productive: open a real file, know what it says, fix a real bug without asking what a DbContext is. Everything that maps cleanly from Node gets one row on the translation sheet and no session at all. The sessions are spent almost entirely on the handful of places where the mapping breaks.

The spine project — HelpDesk API

One project, built across all ten sessions. A support-ticket REST API: Tickets, Users, Comments.

Chosen for two reasons. It is the exact shape of most enterprise .NET work, so the patterns transfer directly to whatever you are handed. And you could build it in Express in an afternoon — which makes .NET the only new variable in every session. You are never learning the domain and the language at the same time.

HelpDesk.Api→ HelpDesk.Core→ HelpDesk.Data→ EF6→ LocalDB
  • Stack: ASP.NET Web API 2 · .NET Framework 4.8 · C# 7.3 · EF6 Code First · SQL Server LocalDB
  • Tooling: Visual Studio 2022 Community (already installed). Not VS Code — dotnet new will not scaffold Framework web projects.
  • Lives at: MyProjects/HelpDeskApi/, its own repo. Never inside the AIOS repo — bin/, obj/ and packages/ would bury it.

Phase 1 · Read

Goal: open any file in a real codebase and know what every block does. This is the fastest path to being useful at work — after session 3 you can be handed a bug and make progress on it.

01 The shape of a .NET app start here

  • Solution / project / assembly — the layer above package.json that Node has no word for
  • NuGet vs npm, Web.config vs .env, IIS vs node server.js
  • The compile loop, and why the compiler is now your fastest feedback
  • The C# 7.3 ceiling — why half of googled C# will not compile for you

Build: solution scaffolded, one endpoint returning JSON.

02 C# for a JS developer next

  • Reading a file: namespace, class, access modifiers, properties vs fields
  • Static typing without the fear — var is not JS var
  • Value vs reference types, and why int cannot be null unless you ask
  • Interfaces, and why enterprise .NET has so many of them

Build: the Ticket, User, and Comment models.

03 Tracing a request next

  • Express's one (req, res, next) vs Web API 2's four extension points
  • Global.asax, WebApiConfig, attribute vs convention routing
  • Model binding — how JSON becomes a typed parameter before your code runs
  • Debugging: breakpoints and the call stack, which beat console.log outright

Build: full CRUD on Tickets, in memory. Traced with a breakpoint.

Phase 2 · Write

Goal: change code without causing an incident. This phase is where the Node instincts that do not transfer get corrected — it is the highest-value part of the course.

04 The threading trap the important one

  • Node's single thread vs .NET's thread pool — requests genuinely run in parallel
  • Why every shared/static/cached thing you write is now a potential bug
  • Task is not Promise: hot vs cold, no event loop, thread hopping across an await
  • .Result and .Wait() deadlock on Framework — and why modern .NET advice never warns you

Build: make it async all the way down. Then deliberately cause the deadlock and watch it hang.

05 LINQ is your array methods the easy win

  • map/filter/reduce/find → Select/Where/Aggregate/FirstOrDefault
  • Deferred execution — nothing runs until you enumerate
  • IEnumerable vs IQueryable: in-memory vs turned into SQL
  • FirstOrDefault returning 0 instead of null, and other quiet failures

Build: filtering, sorting, and paging on the tickets list.

06 EF6 and a real database next

  • DbContext, change tracking, and why it is per-request and not a pool
  • Code First migrations: Enable-Migrations, Add-Migration, Update-Database
  • Relationships, .Include(), and the invisible N+1 that lazy loading gives you
  • Reading the SQL EF actually generated — the habit that saves you later

Build: real persistence in LocalDB. Data survives a restart.

07 DI and service lifetimes next

  • Constructor injection, and why the interfaces from session 2 suddenly pay off
  • Singleton vs Scoped vs Transient — no Node equivalent, and it only makes sense after session 4
  • Framework has no built-in container: Unity, Autofac, Ninject
  • The layered split: Controller → Service → Repository

Build: refactor into three projects with a container wiring them.

Phase 3 · Ship

Goal: an app that survives contact with reality, and something you can put on a screen for your team.

08 Config, IIS, and hosting next

  • Web.config, transforms, connection strings, and where secrets do not go
  • App pools, recycling, and why you do not own main()
  • Deploying to local IIS and reading the failure when it will not start

Build: running on real IIS, not just IIS Express.

09 Errors, logging, validation next

  • Exceptions vs error-first callbacks — everything throws
  • IDisposable and using, the resource discipline JS never asked of you
  • Global exception filters and structured logging
  • DataAnnotations + ModelState for validation

Build: no unhandled 500s, every error logged with context.

10 Auth, tests, and the demo next

  • Token auth on Web API 2, and the [Authorize] attribute
  • xUnit/NUnit + Moq — why mocking needs those interfaces
  • Swagger for a UI you can actually show someone
  • Polish, then demo it

Build: secured, tested, demoable. Show it at work.

Pace

Ten sessions of roughly 45-60 minutes. At one per weekday inside an office block, that is two working weeks to the end of Phase 3 — and you are useful at work well before that, from about session 4.

Don't rush Phase 1 Reading fluency is the gate on everything else. A session spent genuinely understanding what Global.asax is doing pays for itself the first time you are dropped into a real codebase. Sessions 4 and 6 are the two worth slowing down for a second sitting.
This map is not fixed. If work hands you a real task tomorrow, say so — the order gets rewritten around what you actually need. That is the whole advantage of learning against a real job instead of a syllabus.
