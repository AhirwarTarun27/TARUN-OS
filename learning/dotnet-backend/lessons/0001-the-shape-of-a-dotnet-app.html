Lesson 01 · Phase 1 — Read

The shape of a .NET app

What the files are, where the app starts, and the one language constraint that will waste your afternoon if nobody tells you about it. Ends with a running endpoint.

The win By the end of this session you can open an unfamiliar .NET Framework repo and answer three questions without asking anyone: where does it start, what are all these files, and where do dependencies come from. Plus you will have HelpDesk API returning JSON.

Start from what you own

You already know backend. HTTP, routing, middleware, ORMs, async, dependency graphs — all of that transfers. What you are missing is C# vocabulary and .NET's conventions. So this course never teaches you what a route is. It tells you what .NET calls it, then spends the real time on the places where your Node instinct is actively wrong.

Three of those places are in this lesson.

1 · The layer above package.json

In Node, the top of your project is package.json. There is nothing above it. One package, one dependency tree, one thing.

.NET has two layers above your files, and this is the first thing that makes a repo feel unfamiliar:

Node
.NET Framework
package.json
→
HelpDesk.Api.csproj — the project
(nothing above it)
→
HelpDesk.sln — the solution
A solution groups several projects. Each project compiles to its own assembly — a .dll. Project A cannot use project B's code unless someone added an explicit reference. There is no require('../other') reaching across.

So when you open an enterprise .NET repo and see eight folders that each contain a .csproj, that is eight separately-compiled assemblies with a deliberate dependency graph between them. It is closer to a monorepo of eight npm packages than to one Express app with eight folders.

Why it matters on day one Your first instinct in a new repo will be to find "the main folder". There usually isn't one. Open the .sln, look at the project list, and find the one whose name ends in .Api or .Web. That is the entry point. Everything else is a library it consumes.

2 · You do not own main()

This is the big one, and it is genuinely disorienting coming from Node.

In Node you write node server.js. Your code starts, you call app.listen(3000), you own the process. You can see the whole lifecycle.

In ASP.NET Framework, you never start a process. You compile a library. IIS — the Windows web server — loads your DLL into a worker process it controls, called an app pool. It decides when to start you, and it can recycle you at any time.

Nothing in your code says "serve this on port 3000". The framework discovers your controller by convention and wires it up. That convention-over-configuration habit runs through all of .NET, and it is why the entry point is not obvious.

Here is where it actually is:

IIS→ Global.asax.cs→ WebApiConfig.cs→ routes→ YourController
  • Global.asax.cs — Application_Start() runs once when the app boots. This is the closest thing to the top of your server.js.
  • App_Start/WebApiConfig.cs — route setup and framework config. Called from Application_Start.
  • Controllers/ — your handlers. Discovered by naming convention, not registration.
Habit worth building today In any unfamiliar .NET Framework repo, open Global.asax.cs first, then App_Start/. Ten minutes there tells you more about how the app is assembled than an hour of reading controllers.

3 · The C# 7.3 ceiling

This one is not conceptual. It is a practical constraint that will cost you an afternoon if you learn it the hard way.

Read this before you google any C# .NET Framework 4.8 caps at C# 7.3. It is frozen — no new language features since 4.8.1 in August 2022. Meanwhile the language is at C# 13+, and effectively all C# written online since 2020 assumes .NET 5 or later.

So you will google a problem, find a clean modern answer, paste it, and get a compiler error that does not mention versions in any helpful way. The answer was not wrong. It was for a different .NET.

The features you will hit most often, and their 7.3 equivalents:

Modern C# — will NOT compile
C# 7.3 — what you write
record Ticket(int Id);
→
class Ticket { public int Id { get; set; } }
namespace App;
→
namespace App { ... }
public int Id { get; init; }
→
public int Id { get; set; }
x switch { 1 => "a", _ => "b" }
→
switch (x) { case 1: ... }
string? name;
→
string name; // nullable by default
Nullable reference types are C# 8. On 7.3 every reference type is already nullable and the compiler will not warn you. Note that int? is different and does work — nullable value types have been in the language since C# 2.

Practical filter: when you search, add asp.net-web-api2 or "C# 7.3" to the query, and on Stack Overflow prefer answers tagged for the 4.x tree. Confirmed against Microsoft's language versioning docs.

4 · The compiler is your new feedback loop

In Node, you find out something is wrong by running it. Save, restart, hit the endpoint, read the stack trace. Your feedback loop is the runtime.

In C#, most of that class of mistake is caught at compile time. Typo a property name, pass the wrong type, forget to handle a case — the build fails before anything runs. This feels slow at first because you cannot just save and refresh. It is not slow. It moved your bug reports from 3am production logs to your screen ten seconds after you typed it.

The practical difference: build often. Ctrl+Shift+B. Treat a red squiggle the way you would treat a failing test, not the way you would treat a linter warning.

Check yourself

You open an unfamiliar .NET Framework repo. Where do you look first to understand how the app boots?

Right. Application_Start() in Global.asax.cs is the closest thing to the top of your server.js, and it calls into App_Start/ for route and framework setup. Controllers are discovered by convention afterwards, so they tell you what the app does but not how it is assembled.

You paste a Stack Overflow answer using a record and the build fails. What happened?

Right. Records arrived in C# 9 with .NET 5. Framework 4.8 is capped at C# 7.3, so no NuGet package or import will make it work. Write a plain class with { get; set; } properties instead.

In a solution with eight projects, how does one project use another project's code?

Right. Each project compiles to its own assembly and the dependency graph is explicit. A using statement is only shorthand for a namespace — it fails to compile unless the project reference already exists. This is why .NET repos have a deliberate layering that Node projects often do not.
Build it — HelpDesk API, session 1

Type every line yourself. Do not paste. The point of this block is that your fingers learn where the ceremony goes.

  1. Open Visual Studio 2022. Not VS Code — dotnet new cannot scaffold Framework web projects.
  2. Create a new project → ASP.NET Web Application (.NET Framework). Careful: the list also contains "ASP.NET Core Web Application", which is the wrong .NET.
  3. Name it HelpDesk.Api, solution name HelpDesk, location Documents/Learning/MyProjects/HelpDeskApi. Framework: .NET Framework 4.8.
  4. Pick the Web API template.
  5. Before writing anything: open Global.asax.cs, then App_Start/WebApiConfig.cs. Read them. Find the default route template. You are looking for api/{controller}/{id}.
  6. Add Models/Ticket.cs — a plain class with Id (int), Title (string), IsOpen (bool). Properties with { get; set; }, not fields, and not a record.
  7. Add Controllers/TicketsController.cs, inheriting ApiController. One Get() method returning Ok(...) with a hardcoded list of two tickets.
  8. Press F5. Navigate to /api/tickets.
  9. Now break it on purpose: rename the class to TicketController (singular) and reload. Watch the route 404. Rename it back. That is convention-over-configuration biting, and it is worth feeling once.

You see JSON at /api/tickets, and you can explain why that URL works without any route being written for it.

Primary source for this session Get Started with ASP.NET Web API 2 (C#) — Microsoft Learn. First-party, and correctly on the 4.x doc tree. If a tutorial you find opens with WebApplication.CreateBuilder(args), close it — that is .NET Core.
