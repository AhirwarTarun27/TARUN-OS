Comparisons: ==, is, in

The six operators you know work the same. What's new is what they can compare: lists and dicts by their contents (JS says no), plus two new operators, is and in. Three of the four JS traps here make JS say false where Python says True. About 20 minutes.

1. The six comparison operators

A comparison operator looks at two values (its operands) and answers True or False. Exercism also calls these relational operators. You know all six:

PythonMeansExample
==equal3 == 3 → True
!=not equal1 != 2 → True
> <greater, less2 < 1 → False
>= <=greater or equal, less or equal3 >= 3 → True

The big difference is that Python has only one equality operator. There is no === and no !==. And Python's == already acts like JS's ===: it doesn't convert types for you.

JavaScript 
17 == "17"     true    // converts the string
17 === "17"    false
Python 
17 == "17"     False
17 == 17.0     True    # numbers mix freely

Values of different types are never equal, with one exception: numbers. An int and a float with the same value are equal (Lesson 3).

Where comparisons sit in the order All the comparison operators tie with each other, and they run after arithmetic and before not, and and or. The whole ladder, tightest first: **, then * / // %, then + -, then comparisons, then not, then and, then or. So not 1 == 2 is not (1 == 2). Chains like 1 < x < 10 (Lesson 4) work because of this tie.

2. Comparing text

Strings are compared one character at a time, starting from the left, until two characters differ. Each character has a number from Unicode, the big table that gives every letter, digit and emoji its own number. That number is its code point. The built-in ord() shows it:

ord("A")  65
ord("Z")  90
ord("a")  97

So the comparison is really a comparison of those numbers. This way of ordering is called lexicographic order: dictionary order, except that every capital letter comes before every lowercase one, because capitals have smaller numbers.

"apple" < "apricot"     True     # 'p' = 'p', then 'p' < 'r'
"Python" > "Rust"       False    # 'P' < 'R'
"B" < "a"               True     # 66 < 97

JS gives the same answers for these. The point is that "B" < "a" being True surprises people, so don't use plain < to sort names by hand.

3. Comparing lists, tuples and dicts

First, three new containers. A container is a value that holds other values. You'll learn each in its own chapter, but you only need the look of them here:

  • a list is Python's array: [1, 2, 3]
  • a tuple is a list that can't be changed, written with round brackets: (3, 4, 5)
  • a dict is Python's object: {"name": "John", "age": 19}

Python compares containers by what's inside them. Same contents means equal. JS doesn't do that. It compares arrays and objects by where they live in memory, so two separate arrays with the same contents are never equal.

JavaScript 
[1, 2] === [1, 2]       false
({a: 1}) === ({a: 1})   false
Python 
[1, 2] == [1, 2]        True
{"a": 1} == {"a": 1}    True

More details:

[2, 1] == [1, 2]        False   # lists care about order
(3, 4, 5) == (5, 4, 3)  False   # so do tuples
[1, 2] < [1, 2, 3]      True    # same start, shorter one is "less"
{"a": 1} == {"a": 2}    False   # dicts compare their contents

Order only matters for lists and tuples. Lists and tuples are compared position by position, like strings.

JS habit: comparing arrays by hand In JS you'd loop, or call JSON.stringify on both, to compare two arrays. In Python you just write ==. It compares the contents, however long they are.

4. is: same object, not same value

You met is in Lesson 2. It asks a different question from ==:

  • == asks: "do these have the same value?"
  • is asks: "are these the very same object?" That's called identity. is not is its opposite.

Every object has an identity number that never changes, and the built-in id() shows it. Two lists can hold the same items yet be two separate objects:

a = [1, 2]
b = [1, 2]
c = a
a == b        True     # same contents
a is b        False    # two separate objects
a is c        True     # c is just another name for a's object

That last line, c = a, doesn't copy anything. It gives the object a second name. Another name for the same object is called an alias (this is the "names point at objects" idea from Lesson 1).

The one place you should use is: None

There is only ever one None in a whole program. An object like that, with a single copy, is called a singleton. So the exact check is identity, and PEP 8 (Lesson 1) says to write it that way:

JavaScript 
if (x === null) { ... }
if (x !== null) { ... }
Python 
if x is None:
    ...
if x is not None:
    ...

x == None usually gives the same answer, but PEP 8 says don't. Always is None and is not None.

Don't use is for numbers or text is is for None and for "same object?" questions. To ask "same value?" always use ==, even if is happens to work on a small number today.

5. in and not in: is it inside?

in asks "is this a member of that?". This is called a membership test, and not in is the opposite. It works on text, lists and dicts:

"Bat" in "Super Batman"        True     # a piece of text inside text
"bat" in "Super Batman"        False    # case matters
3 in [1, 2, 3]                 True
5 not in [1, 2, 3]             True
"age" in {"age": 33}           True
33 in {"age": 33}              False

Two things to notice:

  • For text, in checks for a substring: a piece of the text, of any length, in one piece.
  • For a dict, in checks the keys only, the left-hand names like "age". The values (like 33) don't count.
JavaScript 
"Super Batman".includes("Bat")   true
[10, 20, 30].includes(20)        true
"age" in {age: 33}               true
Python 
"Bat" in "Super Batman"          True
20 in [10, 20, 30]               True
"age" in {"age": 33}             True
JS habit: in on an array In JS, in looks at positions, not values: 2 in [10, 20, 30] is true, because position 2 exists. In Python, in looks at values: 2 in [10, 20, 30] is False. Python's one in replaces JS's .includes() and its in.

6. One strange value: NaN

NaN stands for "not a number". It's what you get when a calculation has no sensible number as an answer. In Python you make one with float("nan"). Every ordered comparison with it is False, and it isn't even equal to itself:

nan = float("nan")
nan == nan     False
3 < nan        False
nan < 3        False

JS works the same way: NaN === NaN is false. You'll rarely meet NaN in Python, because Python stops with an error instead (1 / 0 is a ZeroDivisionError, Lesson 3). It shows up when you load real-world data later.

That's the whole chapter. Your own classes can also decide what == and < mean for them. That's in the classes chapter, much later.

Check yourself: 5 questions

From memory. Getting it wrong here costs nothing.

1. What does 17 == "17" give in Python?

False. Python's == doesn't convert types, so it acts like JS's ===. No error, just False.

2. What does [1, 2] == [1, 2] give?

True. Python compares lists by contents. The JS version gives false. To ask "same object?", use is.

3. What does 2 in [10, 20, 30] give?

False. Python's in checks values. JS's in checks positions, which is why 2 in [10, 20, 30] is true there.

4. How do you check that x is None?

x is None. === and null don't exist in Python, and a single = would try to assign. x == None usually works, but PEP 8 says to use is.

5. What does "B" < "a" give?

True. ord("B") is 66 and ord("a") is 97, so every capital letter sorts before every lowercase one.
