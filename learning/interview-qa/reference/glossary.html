Must-Say Terms

Not a summary. The exact words that have to leave your mouth for the answer to count — plus the follow-up each one invites.

How to use this Anything in an orange chip is a scoring term: the interviewer is listening for that specific word, and a correct answer that omits it reads as a memorised one. Wording around it is free — say it however you like. The green blocks are full sentences worth having word-perfect, because they are the answers that end the follow-ups instead of inviting them. Ten minutes, out loud. Reading this silently is not the exercise.

0 · Your three tells — check these first

Found across the L2, L3 and L4 drills. They are not knowledge gaps. Every one of them is a correct mechanism that came out of your mouth attached to the wrong word.

Tell 1 — surface-shape matching You fire the first rule the snippet's shape resembles, and stop. It produced the L2 misses, the L3 read-point misses, and three "rule 3" answers for .call/.bind in L4. The cure is one beat of doubt: run the rule you just fired and check its answer isn't absurd. inner.call(this) under rule 3 would make this a function. That absurdity is the signal.
Tell 2 — the label is one step behind the mechanism You explain how it works correctly and then produce the wrong name for it. Confirmed on TypeError, n++, ===, HOF, and explicit binding. Say the label first, then the mechanism — not the other way round.
Tell 3 — the source-location anchor Under pressure you describe runtime things using authoring-time words: "surrounding", "where it is defined". Those words are correct for closures and wrong for this. If one of them is about to come out while you're answering a this question, stop and say call site instead.

M2 · Scope, Hoisting & the TDZ done

scope chain function-scoped block-scoped hoisting registers declarations uninitialised temporal dead zone ReferenceError TypeError the binding, not the value shadowing fresh binding per iteration

Asked asMust containThe follow-up it invites
What is scope?where a name is visible. Global / function / block. The scope chain walks outward only"Can outer code see inner?" → never. Inner reaches out, outer never reaches in
var vs let vs constFour axes, in order: scope · reassign · redeclare · hoisting. var function-scoped; let/const block-scoped"Is const immutable?" → no — it freezes the binding, not the value
What is hoisting?the engine registers declarations in the scope before execution. Nothing physically movesSaying "moved to the top" is the textbook answer; saying "registers" + TDZ is the senior one
Is let hoisted?Yes — hoisted but uninitialised. That's the trap in the question"Then why does it throw?" → the temporal dead zone
What is the TDZ?the window between the binding entering scope and its declaration being evaluated; any access throws ReferenceError"typeof in the TDZ?" → also throws. typeof is only safe on undeclared names
Why does the TDZ exist?It turns a silent undefined bug into a loud error. Design intent, not an accidentThis sentence alone separates you from candidates who only recite behaviour
"prints 6 every time"one var i = one binding for the whole loop; setTimeout runs after the loop, which left i at 6Give both fixes: let (a fresh binding per iteration) and the wrapper function (a new scope per call)
Which error?ReferenceError = couldn't find the name. TypeError = found it, the operation was illegalFind vs do. This one rule answers every error-naming question in the course

M3 · Functions, Closures & HOFs done

first-class lexical lexical environment at authoring time per invocation private state callback higher-order function side effect pure IIFE captured, not copied

Asked asMust containThe follow-up it invites
What is a closure? (99% of interviews)a function bundled with the lexical environment it was created in, so it still reads those variables after the outer function has returned"So why does it still work?" → the environment reference is attached at authoring time and keeps the scope alive (not garbage collected)
—Never say "a function inside a function." That describes the shape, not the mechanism, and it is the answer that collapses on the follow-up—
Two counters from one factoryeach call creates a new environment → closures capture per invocation, not per definitionThis is the fastest test of whether you understand closures or recognise the shape
What is a callback?a function passed as an argument, to be called later, by someone else—
What is a HOF?takes a function as an argument, returns a function, or both. Nesting is irrelevant"Difference from a callback?" → two ends of one handoff. In arr.map(fn), map is the HOF, fn is the callback
Pure vs impuresame input → same output AND no side effect. Both halves requiredThe React tie-in: render must be pure, never mutate state, useMemo/React.memo only work because of it
What is an IIFE?immediately invoked function expression — the parens make JS read it as an expression"Do you still write them?" → "IIFEs solved the scoping problem that let and modules now solve."
Arrow limitations (recall, all 5)1. not hoisted with a body · 2. no arguments · 3. no own this · 4. can't be a constructor (new throws TypeError) · 5. can't be a generator#3 is all of M4
Deferred readsa closure captures the variable, not a copy — captured, not copied. Arguments capture the value at call timen++ returns the old value · ++n returns the new one. After 3 calls n is 3 either way
Say it like this — the highest-value 20 seconds in the whole course "A closure is a function plus its lexical environment. Every function closes over the scope where it was defined, not where it's called, so it can still read those variables after the outer function has returned — the scope stays alive because something can still reach it. That's what makes private state, function factories and once/memoize possible."

The two traps you personally failed — do not lose these again

Trap A — the dot in .call is not a binding dot Rule 3 reads the object to the LEFT of the dot. Rule 2 reads the object INSIDE the parentheses. If the context arrived as an argument, it is rule 2 — always. And anything that came out of bind is rule 2 forever, however it is later invoked.
Trap B — the same arrow, two opposite answers The question is never "is it an arrow", it is "does a real function enclose it?"
· { n:1, f: () => this.n } → no enclosing function (an object literal is not a scope) → reaches global → undefined.
· function C(){ this.f = () => this.n } → yes, the constructor → captures the instance → survives extraction, call, and setTimeout.

What strips the dot

You writeCallee receivesRule

Anywhere a method crosses a comma, it loses its dot. And forEach/map/filter/some/every all take an optional thisArg as their second argument — worth naming, almost nobody does.

Say it like this "this refers to the object currently executing the function, and it's bound at call time, not definition time — so to work out this I don't read the function, I read the call site. There are four rules in precedence order: new, explicit, implicit, default. Arrows aren't in that list at all — they have no this of their own, so it resolves lexically."

5 · The procedure — all five questions, one list

Built across three drills. Q1-Q3 came from M2, Q4 from M3, Q5 from M4. Run them in order on every identifier and never skip to the answer.

  1. Which keyword declares it? function · var · let · const · class · parameter · nothing
  2. What state is the binding in at this exact line? undeclared · TDZ · holds undefined · holds a real value
  3. What are you doing to it? reading · calling · assigning · typeof
  4. When does this actually run — and what is the binding at that moment? (closures move the read into the future)
  5. How was this function called — and is it an arrow? Arrow → skip the table, walk the scope chain. Not an arrow → new · explicit · left of the dot · bare
