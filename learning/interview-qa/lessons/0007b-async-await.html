Lesson 7b · Module 7 — JavaScript Foundations

async/await & the combinators

await doesn't stop JavaScript. It stops one function, and everything else keeps running. Get that one sentence right and every question on this page follows.

What your probe showed
  • async returns a Promise: right.
  • Errors with try/catch around await: right.
  • Promise.all fails if one fails, allSettled waits for all: right. This page adds race and any, and exactly what each one gives back.
  • The real gap: what await does. You predicted f(); console.log(3) would print only 1, as if await froze everything, including the code after f(). The truth is 1 3 2. await pauses only f. §2 is built around this.

0 · Gate check

Open items from the event loop drill, in new shapes. Answer all three before you scroll.

G1 · What prints, and when exactly does "then" get queued? 
let release;
const p = new Promise(res => { release = res; });
p.then(() => console.log("then"));
console.log("sync");
setTimeout(() => release(), 0);
Answer

sync, then then. When .then runs, the Promise is pending, so the callback is only registered. It joins the microtask queue at the moment release() is called, which is inside the timer. The Promise was resolved by a function that was saved and called later. That's still just "whoever writes the ()".

G2 · [5, 6].at(-1) and "k" in { k: 0 }?
Answer

6, the last element. true: in asks whether the key exists, and it doesn't care that the value is 0. Both were missed twice before.

G3 · Say it out loud: the 4 steps of new

① Create an empty object. ② Link its prototype to Constructor.prototype, which is the step that makes inheritance work. ③ Run the constructor with this = that object. ④ Return it, unless the constructor returns its own object. Steps ③ and ④ were the ones left out.

1 · An async function always returns a Promise

async function f() { return 5; }
f();                     // a Promise, fulfilled with 5. Not 5 itself
f().then(v => console.log(v));   // 5

async function g() { throw new Error("x"); }
g();                     // does NOT throw here. It returns a REJECTED Promise
g().catch(e => console.log(e.message));   // x

Two rules, and they're the same two rules as a .then callback: return a value → the Promise fulfills with it. Throw → the Promise rejects. That's no coincidence, as §3 shows.

2 · await pauses the function, not the program

This is the whole page. When a function reaches await:

  1. That function pauses. Only that one.
  2. It returns to whoever called it, handing back its (still pending) Promise. The caller keeps running.
  3. When the awaited Promise resolves, the rest of the function goes into the microtask queue and runs from there, picking up where it left off.
async function f() {
  console.log(1);
  await null;          // pause f. Return to the caller
  console.log(2);      // "the rest of f": a microtask
}
f();
console.log(3);        // the caller keeps going
// 1   3   2

Two facts that interviewers test:

  • Everything before the first await runs synchronously. Calling an async function is not "async" until it hits an await, which is why 1 prints first.
  • await on something that isn't a Promise still pauses. await null treats null as an already-resolved Promise, so the rest still goes to the microtask queue. That's why 2 comes after 3.

3 · The one model: an async function is a .then chain in disguise

You already know .then perfectly. await is just nicer syntax for it:

async function f() {                       function f() {
  console.log(1);                              console.log(1);
  const x = await p;              ≈            return p.then(x => {
  console.log(x);                                console.log(x);
}                                              });
                                             }

Everything after an await is a .then callback. So it's a microtask, it runs after the current sync code, and a throw in it rejects the Promise. When an async output question gets confusing, rewrite it as a .then chain in your head and use the event loop rules you already have. (Both versions print the same thing, checked on Node.)

4 · Errors

A rejected await throws at that line

async function load() {
  try {
    const data = await fetchSomething();   // if this rejects, it THROWS right here
    console.log(data);                     // skipped
  } catch (e) {
    console.log("failed:", e.message);     // lands here
  }
}

That's the point of await: async errors work with normal try/catch. No try? Then the async function's own Promise rejects, and the caller's .catch (or its try/catch around await) gets it.

The bug: forgetting await

async function oops() {
  try {
    Promise.reject(new Error("lost"));   // no await!
  } catch (e) {
    console.log("caught");               // never runs
  }
  console.log("finished");
}
// finished   …then: Uncaught (in promise) Error: lost

Without await, the try block finishes before the rejection is noticed, so try/catch can't see it. It's the same lesson as throw inside a callback: a try only catches what goes wrong while it's running.

5 · Sequential vs parallel

const wait = ms => new Promise(r => setTimeout(r, ms));

// sequential: the second wait doesn't START until the first finishes
await wait(100);
await wait(100);                                   // total ≈ 200ms

// parallel: both start now, then wait for both
await Promise.all([wait(100), wait(100)]);         // total ≈ 100ms

Timed on Node: about 200ms vs about 100ms. Two awaits in a row are one after the other. If the two calls don't depend on each other (a user's profile and their orders, say), start them together with Promise.all. This is one of the most common real-world performance questions: "this page makes 3 API calls, why is it slow?"

6 · await inside loops

[1, 2].forEach(async id => {
  await null;
  console.log("item", id);
});
console.log("done");
// done   item 1   item 2   ← forEach did NOT wait

forEach doesn't wait for async callbacks. It calls your function once per element and ignores what comes back, which here is a Promise. It's the same as forEach ignoring any return value. The two fixes:

for (const id of ids) { await doThing(id); }           // one at a time, in order
await Promise.all(ids.map(id => doThing(id)));         // all at once, wait for all

7 · The four combinators

Each takes an array of Promises and returns one Promise. The question is always: what makes it settle, and with what?

Fulfills when……withRejects when…Use it for
allevery one fulfillsan array of values, in input orderthe first rejection (fail-fast)things you need all of: a page's required data
allSettledalways, once all settlean array of {status, value} / {status, reason}neverindependent jobs where partial success is fine: a batch upload, separate widgets
racethe first to settle is a fulfillthat valuethe first to settle is a rejecta timeout (Drill A)
anythe first to fulfillthat valueall reject, with an AggregateErrorthe fastest of several mirrors or servers
  • all keeps input order, not finish order. Promise.all([slow, fast]) gives ["slow", "fast"].
  • Fail-fast doesn't cancel anything. The other Promises keep running; all just stops waiting for them.
  • race vs any is the classic follow-up. If a quick failure races a slow success, race rejects (the first to settle was a failure) and any fulfills (it skips failures and waits for a success).
  • The ebook's line on any is garbled. The correct version: it fulfills with the first success, and rejects only if every Promise rejects.
Say it like this "all needs everything and fails fast. allSettled waits for everything and never fails, and gives me a status for each. race takes the first to settle, success or failure, so it's good for timeouts. any takes the first success, and fails only if they all fail."

8 · The procedure: no new question

The eighth question (sync, microtask, or task?) already covers await, once you add one line: the code after an await is a microtask, queued when the awaited thing resolves.

9 · Solving async output questions

  1. Everything up to each function's first await is sync.
  2. At each await, the function returns to its caller. Keep reading the caller.
  3. "The rest of the function" is a microtask, queued when the awaited thing resolves. If it awaits a timer, that's not until the timer's task runs.

The ebook's question 15 (it's scenario 2 in the visualizer):

async function foo() {
  console.log("A");                               // sync (foo was called synchronously)
  await Promise.resolve();                        // pause foo → back to the caller
  console.log("B");                               // microtask
  await new Promise(r => setTimeout(r, 0));       // pause again, until a TIMER resolves it
  console.log("C");                               // after that task, as a microtask
}
console.log("D");                                 // sync
foo();
console.log("E");                                 // sync: the caller kept going
// D A E B C

One correction to the ebook's explanation: it says control returns "to the caller function (foo())". It returns to the code that called foo, which here is the script. Foo is the one that paused.

10 · Retrieval quiz

async function f() { return 5; } What is f()?

A Promise fulfilled with 5. An async function always returns a Promise. return sets what it fulfills with.

When a function reaches await, what pauses?

Only that function. It returns to its caller, which keeps running. The rest of the function comes back later as a microtask.

An async function throws and nothing catches it inside. What happens?

Its Promise rejects. The caller deals with it through .catch, or a try/catch around await.

A quick failure races a slow success. Which combinator fulfills?

any. It skips failures and waits for the first success. race rejects, because the first to settle was a failure.

ids.forEach(async id => await save(id)); console.log("done"). When does "done" log?

Before any save finishes. forEach ignores the Promises your callback returns. Use for...of with await, or Promise.all.

11 · Output drills

Cold. For each one, find each function's first await, then label sync, microtask, or task.

D1 · what an async function gives back 
async function g() { return 7; }
const r = g();
console.log(r instanceof Promise);
r.then(v => console.log(v));
console.log("end");

true, end, 7. r is a Promise, and its .then is a microtask, so it runs after end.

D2 · awaiting a timer 
async function load() {
  console.log("start");
  await new Promise(r => setTimeout(r, 0));
  console.log("loaded");
}
load();
Promise.resolve().then(() => console.log("micro"));
console.log("sync");

start sync micro loaded. start is sync. The await waits on a timer, so loaded needs that task first. micro is an ordinary microtask, so it runs as soon as the script ends.

D3 · two async functions 
async function a() { console.log("a1"); await null; console.log("a2"); }
async function b() { console.log("b1"); await null; console.log("b2"); }
a(); b();
console.log("main");

a1 b1 main a2 b2. Each runs synchronously up to its await, then hands back. The two "rests" are microtasks, in the order they were queued.

D4 · try/catch with await 
async function risky() {
  try {
    await Promise.reject(new Error("bad"));
    console.log("after");
  } catch (e) {
    console.log("caught", e.message);
  }
  return "done";
}
risky().then(v => console.log(v));

caught bad, done. The rejected await throws, so after is skipped. The catch handles it, and the function carries on and returns normally.

D5 · Promise.all keeps order 
const slow = new Promise(r => setTimeout(() => r("slow"), 20));
const fast = Promise.resolve("fast");
Promise.all([slow, fast]).then(v => console.log(v));

["slow", "fast"]. That's input order, even though fast finished first.

D6 · allSettled's shape 
Promise.allSettled([Promise.resolve(1), Promise.reject(new Error("no"))])
  .then(r => console.log(r.map(x => x.status)));

["fulfilled", "rejected"]. It never rejects. Each entry is { status: "fulfilled", value } or { status: "rejected", reason }.

D7 · race vs any 
const quickFail = new Promise((_, rej) => setTimeout(() => rej(new Error("fail")), 10));
const slowOk = new Promise(res => setTimeout(() => res("ok"), 20));
Promise.race([quickFail, slowOk]).catch(e => console.log("race:", e.message));
Promise.any([quickFail, slowOk]).then(v => console.log("any:", v));

race: fail, then any: ok. Same two Promises, opposite results.

12 · Label-only round

Does the resulting Promise FULFILL or REJECT? Labels only. Bar 7/8. (ok fulfills and fail rejects. "Fast" and "slow" are about timing.)

  1. Promise.all([ok, ok])
  2. Promise.all([ok, fail])
  3. Promise.allSettled([ok, fail])
  4. Promise.race([fastFail, slowOk])
  5. Promise.any([fastFail, slowOk])
  6. Promise.any([fail, fail])
  7. (async () => { throw new Error("x"); })()
  8. (async () => 5)()
Answers
  1. FULFILL
  2. REJECT: fail-fast
  3. FULFILL: allSettled never rejects
  4. REJECT: the first to settle was a failure
  5. FULFILL: any waits for a success
  6. REJECT: all failed, so AggregateError
  7. REJECT: a throw in an async function becomes a rejected Promise, not a thrown error
  8. FULFILL, with 5

#3, #5 and #7 are the traps. #3 and #5 contain a failure but fulfill. #7 looks like it throws, but it rejects instead.

13 · Coding drills

For each one, work in this order: how it's used → trace one example by hand → the steps as comments → code.

Drill A: withTimeout(promise, ms)

Return a Promise that settles like promise, unless ms passes first, in which case it rejects with Error("timeout").

// how it's used
withTimeout(fetchUser(), 3000)
  .then(user => show(user))
  .catch(e => console.log(e.message));   // "timeout" if fetchUser takes over 3s
Hint ladder, then the answer

Hint 1. It's a race between two Promises: the real one, and one that rejects after ms. Which combinator takes whichever settles first?

Hint 2. The timeout Promise is your sleep from the previous page, except it calls reject instead of resolve.

function withTimeout(promise, ms) {
  const timeout = new Promise((_, reject) =>
    setTimeout(() => reject(new Error("timeout")), ms));
  return Promise.race([promise, timeout]);
}

Verified on Node: a 20ms job with a 50ms limit gives data; an 80ms job with a 50ms limit gives timeout. Limitation to say yourself: the timer keeps running after the real Promise wins. A cleaner version keeps the timer's id and calls clearTimeout in a .finally. Also, the slow job itself isn't cancelled; race just stops waiting for it.

Drill B: write myPromiseAll(promises)

The most-asked Promise coding question. It has to behave like Promise.all: values in input order, reject on the first failure, and [] gives [].

// how it's used
const slow = new Promise(r => setTimeout(() => r("slow"), 20));
myPromiseAll([slow, Promise.resolve("fast"), 3]).then(v => console.log(v));
// ["slow", "fast", 3]   ← input order; a plain value (3) is allowed too
Hint ladder, then the answer

Hint 1, the shape. Return a new Promise. Inside, attach a .then to each input. Each .then stores its value, and when all have arrived, you call resolve.

Hint 2, order. Values arrive in finish order. How do you put each one in its input position? (You have the index from forEach.)

Hint 3, "all arrived". Don't check results.length. Setting results[1] on an empty array makes its length 2, even though only one value has arrived. Keep a counter.

function myPromiseAll(promises) {
  return new Promise((resolve, reject) => {
    const results = [];
    let done = 0;
    if (promises.length === 0) return resolve([]);
    promises.forEach((p, i) => {
      Promise.resolve(p).then(value => {
        results[i] = value;                         // input position, not finish order
        done++;
        if (done === promises.length) resolve(results);
      }, reject);                                   // the first failure rejects everything
    });
  });
}

Four things to say out loud: index, not push (keeps order) · a counter, not length (the sparse-array trap) · Promise.resolve(p) (so plain values like 3 work) · the empty-array case (otherwise it never resolves). Calling reject more than once is harmless: a Promise settles once. All three cases verified on Node.
