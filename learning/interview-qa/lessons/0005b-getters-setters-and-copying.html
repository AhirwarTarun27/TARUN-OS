Getters, setters & what = really does

Lesson 5 said spread and Object.assign are both shallow copies of own enumerable properties. That is true and it is not the whole truth. The difference between them is one mechanism you have never been taught, and it is the same mechanism behind el.innerHTML = x, Vue reactivity, and a real security bug.

Why this page exists — read it, it changes how you drill This page was written on 2026-09-20 because of an honest sentence: "To be honest, I don't know anything about getters and setters, and I don't imagine their exact use case, because I haven't used this kind of thing in real production code."

That is the correct thing to have said, and it located the gap in one line. Lesson 5 §4 and §8 both assume accessor properties exist — the freeze/seal section, the spread section and the descriptor table are all written on top of a concept that was never taught. This page is the missing floor. It is not new material to get through. It is the floor under material you already read.

Also banked here: the interview answer he could not reach without it — the spread vs Object.assign discriminator, which almost no candidate can name at all.

1 · = does not always mean "store a value"

Start here, because you already know this and have never had it named. You have written this thousands of times:

el.innerHTML = "<p>hi</p>";

Ask the question nobody asks: did that store a string in a box called innerHTML? No. It parsed HTML, destroyed the existing child nodes, built new ones, and scheduled a repaint. One character — = — ran a pile of C++.

That is a setter. You have been using them daily:

You wroteWhat it looks likeWhat actually happened
el.innerHTML = "…"storing a stringparse HTML, rebuild the DOM subtree
location.href = "/login"storing a stringthe browser navigates away
input.value = ""storing a stringthe visible input is redrawn
el.className = "active"storing a stringthe class attribute is rewritten, styles recalc
The whole lesson in one sentence A property is either a box or a pair of functions wearing an = costume. You cannot tell which from the call site. That is deliberate, and it is the entire point of the feature.

2 · The real dichotomy: data property vs accessor property

Every property in JavaScript is exactly one of two kinds. Lesson 5's descriptor table showed you one of them. Here is the pair, printed by Object.getOwnPropertyDescriptor:

const data = { a: 1 };
Object.getOwnPropertyDescriptor(data, "a");
// { value: 1, writable: true, enumerable: true, configurable: true }

const acc = { get a() { return 1; }, set a(v) {} };
Object.getOwnPropertyDescriptor(acc, "a");
// { get: [Function], set: [Function], enumerable: true, configurable: true }

Look at what is missing from the second one: there is no value and no writable. Nothing is stored. There is no box. The property is two functions and nothing else.

Data propertyAccessor property
Descriptor holdsvalue, writableget, set
Reading ithands back the stored valueruns the getter
Writing itreplaces the stored valueruns the setter
Storageyes, one slotnone — it stores nothing
How you make one{ a: 1 }get/set, or defineProperty

Say "accessor property," not "getter." The interviewer's follow-up is "so what does the descriptor look like?" — and the answer is no value, no writable, just get and set. That single sentence is worth more than any amount of syntax recall.

3 · The syntax, in three places

In an object literal — the form you will read most:

const user = {
  firstName: "Tarun",
  lastName: "Ahirwar",

  get fullName() {                 // runs on READ:  user.fullName
    return this.firstName + " " + this.lastName;
  },
  set fullName(v) {                // runs on WRITE: user.fullName = "…"
    [this.firstName, this.lastName] = v.split(" ");
  }
};

user.fullName;                     // "Tarun Ahirwar"   — the getter ran
user.fullName = "Asha Roy";        // the setter ran
user.firstName;                    // "Asha"
Object.keys(user);                 // ["firstName", "lastName", "fullName"]

Three things to notice, all of them interview-grade:

  • No parentheses. user.fullName, not user.fullName(). It is disguised as data on purpose.
  • Nothing named fullName is stored anywhere. It is computed on every read.
  • It still shows up in Object.keys. Accessors are enumerable when declared this way — which is exactly why the copying question in §6 is a real question.

In a class — where the accessor lands on the prototype, not the instance (Lesson 5 §5 territory):

class C { get v() { return 1; } }
const c = new C();

Object.keys(c);                          // []            — nothing own
Object.getOwnPropertyNames(C.prototype); // ["constructor", "v"]
{ ...c };                                // {}            — spread copies OWN props. there are none.

With defineProperty — the long form, and the one that reveals the defaults:

const dp = {};
Object.defineProperty(dp, "k", { value: 9 });

Object.keys(dp);                            // []   ← invisible!
Object.getOwnPropertyDescriptor(dp, "k");
// { value: 9, writable: false, enumerable: false, configurable: false }
Remember this default defineProperty defaults every flag to false, while an object literal defaults every flag to true. A property added with defineProperty and no flags is read-only and invisible to Object.keys, for...in, JSON.stringify and both copy operations. This is a favourite "why doesn't my key show up" trick question.

4 · Why anyone writes one (the use case you asked for)

You said you have never written one in production. That is normal and it is not a gap in your engineering. Here is where they actually live, ranked by how likely you are to meet them:

Reactivitythe framework learns you wrote, so it can re-renderVue 2 was built entirely on this. this.count = 5 re-renders because count is a setter. MobX, older Angular digest work the same way
Host objectsan = that drives a real machineinnerHTML, location.href, value — every day

The one to say out loud: "Vue 2's reactivity was accessor properties — it walked your data object and replaced every field with a getter/setter pair so it could track reads and intercept writes. Vue 3 swapped that for Proxy because accessors can't see new keys being added or array index writes." That answer is a whole level above "getters compute values," and it connects to a framework you actually use.

5 · The mechanism: there are TWO ways to put a property on an object

This is the concept the whole page exists for. Nobody teaches it, and everything downstream is unreachable without it.

Way 1 — assignmentWay 2 — definition
Written asobj.x = 5Object.defineProperty(obj, "x", {…})
Spec name[[Set]][[DefineOwnProperty]]
Walks the prototype chain?yesno
Triggers an existing setter?yesno
Read-only property in the way?throws (strict) / silent no-opoverwrites it, if configurable
Resultwhatever the setter decidedalways a plain data property
Analogyknock on the front door — the doorman decidescrane it in through the roof — nobody is consulted

Assignment is polite: it asks the object (and its whole prototype chain) whether anyone wants to handle this key. Definition is brute force: it installs a data property and bulldozes whatever was there.

const target = {
  set price(v) { console.log("setter ran"); this._price = v * 2; }
};

target.price = 100;               // "setter ran"
target._price;                    // 200   — the 100 never landed anywhere
Object.keys(target);              // ["price", "_price"]

And the prototype chain matters — an inherited setter fires just the same, which is the case that bites in class code:

class Base { set price(v) { console.log("proto setter ran"); this._price = v * 2; } }
const inst = new Base();

inst.price = 50;                  // "proto setter ran"
inst._price;                      // 100
Object.keys(inst);                // ["_price"]  ← no own `price`. it lives on the prototype.

6 · Now the discriminator: spread vs Object.assign

Everything above collapses into one row.

Object.assign(t, src){ ...src }
Mechanismassignment [[Set]]definition [[CreateDataProperty]]
Setter on the target fires?yesnever
Read-only property on targetTypeError in strict modecannot happen — target is fresh
Targetan existing object — mutates ita brand new object
Returnsthe target (same reference)a new reference
Shallow?yesyes
Copiesown enumerable, string + symbolown enumerable, string + symbol
Getters on the sourceinvoked, value copied flatinvoked, value copied flat
Prototype carried?nono
Why you have never seen the difference bite Spread has no target. { ...src } always builds a fresh empty object, so there is never a pre-existing setter for it to trigger. The difference is only observable when the target already has an accessor or a read-only property — and only Object.assign can have a target at all. That is why this is a discriminator question and not a daily concern. In your own code: use spread, and move on.

Both operations read the source the same way. A getter on the source is invoked by both, and what lands in the copy is a flat, dumb value — the accessor is not carried:

const src = { get n() { console.log("get"); return 7; } };

const viaSpread = { ...src };            // "get"
const viaAssign = Object.assign({}, src); // "get"

Object.getOwnPropertyDescriptor(viaSpread, "n");
// { value: 7, writable: true, enumerable: true, configurable: true }
// the getter is GONE. both copies froze it into the value it happened to return.

That is the practical bug, and it is worth more than the setter trivia: copying an object with a getter silently converts a live computed value into a stale snapshot. Both operators do it. Object.getOwnPropertyDescriptors + Object.defineProperties is the copy that preserves accessors.

7 · The one time it bites in production: __proto__

__proto__ is an accessor property living on Object.prototype whose setter changes the object's prototype. Every object inherits it. So an assignment to a key named __proto__ does not store a key — it runs a setter that rewires inheritance.

const evil = JSON.parse('{"__proto__": {"isAdmin": true}}');
Object.keys(evil);                        // ["__proto__"]  — JSON.parse makes a real OWN data key

// assignment → knocks on the door → hits the __proto__ SETTER
const a = Object.assign({}, evil);
Object.getPrototypeOf(a) === Object.prototype;  // false  ← prototype was swapped
a.isAdmin;                                      // true   ← inherited from the injected prototype
Object.keys(a);                                 // []     ← and it is INVISIBLE

// definition → through the roof → no setter consulted
const b = { ...evil };
Object.getPrototypeOf(b) === Object.prototype;  // true   ← untouched
b.isAdmin;                                      // undefined
Object.keys(b);                                 // ["__proto__"]  — just an inert key

Same input, same-looking operation, and Object.assign got hijacked while spread did not. Read line 6 again: Object.keys(a) is empty. The attack leaves no own property behind, which is exactly why prototype pollution survives naive logging and validation.

The realistic shape Object.assign(currentUser, JSON.parse(req.body)) — merging user-controlled JSON into an existing object. This is a whole CVE class (lodash merge, jQuery extend, minimist, and others all shipped it). It is not an exotic hypothetical, and it exists entirely because of assignment-vs-definition.

8 · The remaining edge cases, verified

// a setter with no getter: writes work, reads give undefined
const wo = { set x(v) { this._x = v; } };
wo.x = 5;
wo.x;                             // undefined  ← there is no getter. nothing to read.
wo._x;                            // 5

// read-only property on the target
const ro = {};
Object.defineProperty(ro, "id", { value: 1, writable: false, enumerable: true });
Object.assign(ro, { id: 2 });     // TypeError (strict mode / modules)
({ ...ro });                      // { id: 1 }   — copying OUT is always fine

// frozen target
const fz = Object.freeze({ q: 1 });
Object.assign(fz, { q: 2 });      // TypeError
({ ...fz });                      // { q: 1 }    — the copy is NOT frozen

// assign returns the target itself; spread returns a new reference
const tgt = { a: 1 };
Object.assign(tgt, { b: 2 }) === tgt;  // true

9 · Quick checks

Which descriptor field does an accessor property NOT have?

writable — and value with it. An accessor stores nothing, so there is no slot to describe as writable. It has exactly get, set, enumerable, configurable.

const o = { set x(v) { this._x = v } }; o.x = 5; — what is o.x?

undefined. The write ran the setter and stored 5 on _x. Reading x looks for a getter, finds none, and returns undefined. Set and get are independent halves.

The real difference between spread and Object.assign, beyond mutation, is:

Assign uses assignment, so a setter already on the target fires. Spread defines properties and never triggers one. The other three are all false — both are shallow, both copy own enumerable only, and both copy symbol keys.

After const c = { ...objWithGetter }, what is the getter in c?

Gone. The getter is invoked once during the copy and the returned value is frozen into a plain data property. A live computed value becomes a stale snapshot. Object.assign does exactly the same. To preserve accessors you need defineProperties + getOwnPropertyDescriptors.

10 · Cold drills — predict the output

Cover the answers. Say the output and the mechanism word (assignment or definition) out loud before you open each one. All outputs below were run on Node 20, not written from memory.

D1 — const o = { get a() { return this.b * 2 }, b: 3 }; const c = { ...o }; o.b = 10; console.log(c.a, o.a);

6 20

The spread invoked the getter once, when b was still 3, and froze 6 into c as a data property. c.a is now a dead number and will never update again. o.a is still a live getter and recomputes to 20. This is the copy bug that actually costs people time — far more than the setter trivia.

D2 — class U { set name(v){ this._n = v.trim() } }
const u = new U(); Object.assign(u, { name: " Tarun " }); console.log(u._n, Object.keys(u));

"Tarun" [ '_n' ]

Two things at once. The setter lives on U.prototype, and assignment walks the prototype chain, so it still fires — an inherited setter is as good as an own one. And the instance ends up with no own name key at all, because the setter chose to store _n instead. Assignment means the target decides what happens.

D3 — const src = JSON.parse('{"__proto__":{"x":1}}'); const a = Object.assign({}, src); console.log(Object.keys(a), a.x);

[] 1

Prototype pollution in two lines. Object.keys is empty because nothing was ever stored as an own property — the __proto__ setter on Object.prototype intercepted the write and swapped a's prototype instead. a.x then resolves up the chain. An invisible property that still answers. Swap Object.assign for { ...src } and you get ['__proto__'] undefined.

D4 — const o = {}; Object.defineProperty(o, "k", { value: 1 }); console.log(Object.keys(o), JSON.stringify(o), { ...o });

[] '{}' {}

defineProperty defaults everything to false, so k is non-enumerable. It exists — o.k is 1 and "k" in o is true — but it is invisible to Object.keys, for...in, JSON.stringify, spread and Object.assign, because every one of those is defined in terms of own enumerable properties.

D5 — const t = {}; Object.defineProperty(t, "id", { value: 1, enumerable: true }); Object.assign(t, { id: 2 });

TypeError: Cannot assign to read only property 'id'

writable defaulted to false, and Object.assign uses assignment, which respects that. In a module or any strict-mode code it throws; in sloppy mode it fails silently, which is worse. Spread cannot hit this — its target is always a fresh object. Second half of the discriminator, after setters.

D6 — class C { get v(){ return 1 } }
console.log({ ...new C() }, Object.keys(new C()));

{} []

Fuses this page with Lesson 5 §5. Class accessors and methods live on C.prototype, and every copy operation takes own properties only. So spreading a class instance gives you a plain object that has lost its methods, its getters and its prototype. The standard follow-up: "so how do you copy an instance?" — Object.create(Object.getPrototypeOf(c)) plus Object.defineProperties(…, Object.getOwnPropertyDescriptors(c)), or structuredClone if you accept that it also drops the prototype.

11 · Label-only round

The locked 08-07 method: no outputs, no explanations. For each line, say only "assignment" or "definition", and whether a setter on the target could fire. 60 seconds. Bar is 7/8.

  1. obj.x = 5
  2. { ...src }
  3. Object.assign(t, src)
  4. Object.defineProperty(o, "k", { value: 1 })
  5. const { a, ...rest } = src
  6. o["dynamic" + i] = v
  7. Object.defineProperties(o, descriptors)
  8. arr.push(v)
Answers

1 assignment (setter can fire) · 2 definition (never) · 3 assignment (can fire) · 4 definition (never) · 5 definition — rest in destructuring builds a fresh object, same mechanism as spread (never) · 6 assignment — computed key changes nothing, the mechanism is the = (can fire) · 7 definition (never) · 8 assignment — push is specified as a [[Set]] of an index plus a [[Set]] of length, which is why it throws on a frozen array (can fire).

The trap is 6 and 8. Both are surface shapes that look like "something else" — a computed key and a method call — but the mechanism underneath is plain assignment. This is surface-shape matching, the course's most durable failure mode, dressed for a new module. The discriminator: ignore what it looks like, ask whether an = happens.

12 · The sentences you say

"What's a getter and setter?"

"An accessor property. Instead of storing a value it stores two functions — one that runs on read, one on write — so the descriptor has get and set instead of value and writable. You use them every day without noticing: el.innerHTML = x is a setter, which is why one = can rebuild the DOM. Vue 2's entire reactivity system was accessor properties."

"Spread vs Object.assign?"

"Both are shallow, both copy own enumerable string and symbol properties, and both invoke getters on the source and flatten them to values. The obvious difference is that Object.assign mutates its target. The real difference is the mechanism: Object.assign uses assignment, so it walks the prototype chain and triggers any setter already on the target, and throws on a read-only property. Spread defines properties, so it never triggers a setter and always produces plain data properties. The famous consequence is __proto__ — Object.assign hits that setter and you get prototype pollution, spread just stores an inert key."

Keep your honest line If asked whether you have used accessors in production, say no and say what you have used: "Not directly — the ones I work with are the DOM's and the framework's. Where it has mattered to me is knowing that copying an object with a getter turns a live value into a stale one." Never claim authorship you can't defend. Naming the copy bug proves the understanding without the claim.
