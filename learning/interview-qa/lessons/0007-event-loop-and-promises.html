Lesson 7 · Module 7 — JavaScript Foundations

The event loop & Promises

JavaScript does one thing at a time. Everything on this page answers one question: so how does it wait for anything without freezing?

Where this sits, and what the 10-06 probe found M7 is split in two, like M6. This page: the event loop and Promises. Lesson 7b: async/await, Promise.all and friends, and the hard output questions. The split follows the probe, because await is built on Promises and Promises were a clean "no idea".
  • Single-threaded, call stack: right. One stack, functions pushed on and popped off, last in first out. §1-§2 only sharpen it.
  • setTimeout(fn, 0): the mechanism is right, the label isn't. You said it goes to the "macro stack". It goes to a queue, the task queue. A stack is last-in-first-out; a queue is first-in-first-out, and that difference decides output order. §3.
  • What a Promise is: "no idea". That's the biggest gap, and you've been using them through async/await and Promise.all at work without the floor under them. §5 and §6 build that floor.
  • await: half. "It waits, then runs the next line" is true inside the function. The missing half is that it doesn't block anything else. Lesson 7b owns it.
  • The 1-4-3-2 snippet: right. You have the ordering intuition. This page gives you the reason, so it survives harder snippets than that one.

0 · Gate check — carried from M6

Open items from earlier chapters, in new shapes. Answer all four before you scroll.

G1 · What does each one return, or does it throw?
  1. arr.splice(1)
  2. arr.splice(1, 0, "y")
  3. arr.at(-2)
  4. new WeakSet().add("x")
  5. new WeakMap().has("x")
Answers
  1. An array of the removed items: everything from index 1 to the end.
  2. []. It inserts and removes nothing. splice always returns an array of what it removed.
  3. The second-to-last element. Negative indexes count from the end.
  4. Throws TypeError. Weak collections only accept objects, and add/set enforce it.
  5. false, with no throw. Only add/set throw; has/get just answer.
G2 · Say it out loud: when does JavaScript free an object, and what is a memory leak?

Freed once it's no longer reachable from a root (a global, a running function's variables, a live closure). delete and = null only cut one path. A leak is memory you no longer need that is still reachable, so it can never be freed: a forgotten listener, an uncleared interval, a cache that only grows. If you didn't say the word reachable, it doesn't count yet.

G3 · Say it out loud: why does firstUnique work, and what's its complexity?

A Map keeps keys in insertion order, so the first key with count 1 is the first such character in the string. O(n): one pass to count, one pass over at most n keys. This one was owed three times on 10-06.

G4 · OWN, INHERITED or NOT FOUND? (and one value) 
class Lamp {
  watts = 40;
  on() {}
  get bright() { return this.watts > 30; }
}
const l1 = new Lamp(), l2 = new Lamp();
l1.on = "x";

Say where each is found: l1.watts, l1.bright, l1.on, l2.on, l1.valueOf. Then: what is { ...l1 }.bright, and is it live?

Answers

watts OWN (a field) · bright INHERITED (getters live on the prototype) · l1.on OWN (shadowed by the assignment) · l2.on INHERITED (untouched) · valueOf INHERITED (from Object.prototype). { ...l1 }.bright is undefined: spread only copies own properties, and the getter lives on the prototype, so it isn't copied at all. (Spread snapshots a getter only when the getter is an own property, as in an object literal.)

1 · Single-threaded, said properly

Your probe answer was right: there is one call stack, so JavaScript runs one thing at a time. Add one phrase, because it's the one that explains every output question on this page:

Run to completion Once a piece of JavaScript starts running, nothing interrupts it. Not a timer, not a click, not a finished network request. They all wait until the call stack is empty.

The cost of that rule is blocking. A long loop freezes the page: no clicks, no repaint, no timers. This is the ebook's output question 13, and it's a famous one:

let a = true;
setTimeout(() => { a = false; }, 2000);
while (a) { console.log("inside while"); }

This never stops. The timer callback that would set a = false can only run when the stack is empty, and the stack is never empty, because the loop is waiting for a to become false. Each side is waiting for the other. The bounded version proves the rule:

setTimeout(() => console.log("timer"), 0);
const end = Date.now() + 100;
while (Date.now() < end) {}         // block the stack for 100ms
console.log("loop done");
// loop done   then   timer   — the "0ms" timer waited the full 100ms

2 · The call stack (you have this)

Call a function and a frame (its local variables and where to return to) is pushed. It returns and the frame is popped. Last in, first out. Two facts to add:

  • "The stack is empty" means all the synchronous code has finished, every last line of it. That's the moment everything else on this page waits for.
  • Recursion with no base case keeps pushing until the engine gives up: RangeError: Maximum call stack size exceeded. That's a stack overflow, and it's an interview question of its own.

3 · Who does the waiting: the host, and the task queue

If JavaScript can only do one thing at a time, who counts the 2 seconds? Not JavaScript. The host does: the browser (through its Web APIs) or Node. setTimeout is a request to the host: "count this time, then give me back this function."

  1. setTimeout(fn, 1000) hands the timer to the host and returns immediately, with an id. (A number in browsers, an object in Node. Pass it to clearTimeout(id) to cancel.)
  2. JavaScript keeps running the rest of your code.
  3. When the time is up, the host puts fn into the task queue (also called the macrotask or callback queue).
  4. fn runs only when the call stack is empty, and only when it reaches the front of the queue.

Your probe's label, fixed: it's a queue, not a stack. A queue is first in, first out, like a line at a counter. Two timers that finish in order run in order. If it were a stack, the later one would jump the line.

So setTimeout(fn, 0) doesn't mean "run now". It means "run as soon as possible, but not before the current code finishes." The delay is a minimum, never a promise.

setInterval and stopping it

let n = 0;
const id = setInterval(() => {
  n++;
  console.log("tick", n);
  if (n === 3) clearInterval(id);    // without this it runs forever (and leaks, L6b §5)
}, 100);
// tick 1   tick 2   tick 3

Every tick is a new task in the queue. In React, the interval you forgot to clear in the useEffect cleanup is exactly the "uncleared interval" leak from 6b.

4 · The event loop

The event loop is the part that connects the queue to the stack. Its first version is one sentence:

The event loop, version 1 When the call stack is empty, take the first task from the task queue, run it to completion, then repeat. Forever.

That's the whole thing for timers. §7 adds the second queue, the one Promises use. You need Promises first.

5 · Promises from zero

Before Promises, "give me the result later" meant passing a callback: getUser(id, (err, user) => { ... }). Two problems: callbacks nested inside callbacks ("callback hell"), and you hand your function to someone else's code and trust them to call it once, and with the right arguments. Promises fix both by turning "later" into a thing you can hold.

What a Promise is A Promise is an object that stands for a value that isn't ready yet. It's a receipt. You keep it now, and it tells you later whether you got the value or an error.

Three states, and it settles once

StateMeans
pendingnot finished yet. Every Promise starts here
fulfilledfinished, with a value
rejectedfailed, with a reason (usually an Error)

"Settled" means fulfilled or rejected, in other words not pending any more. The ebook lists "settled" as a fourth state. It isn't one; it's a word for "done, either way". And a Promise settles once: the first resolve or reject wins, and every later call is silently ignored.

Making one: the executor runs right now

const p = new Promise((resolve, reject) => {
  // this function is the EXECUTOR — it runs immediately, synchronously
  const ok = true;
  if (ok) resolve("data");             // → fulfilled with "data"
  else reject(new Error("failed"));    // → rejected
});

The trap: the function you pass to new Promise is not async. It runs on the spot, during new Promise(...). Only what you do later with the result is async. This is the ebook's output question 14 (§9), and it's the single most planted trap in async questions.

Shortcuts: Promise.resolve(v) gives an already-fulfilled Promise, and Promise.reject(err) gives an already-rejected one.

Using one: then, catch, finally

p.then(value => console.log("got", value))     // runs if fulfilled
 .catch(err => console.log("failed", err))      // runs if rejected
 .finally(() => console.log("either way"));     // runs after either, gets no value

These are callbacks again, but with the guarantees callbacks never had: each one is called at most once, and always asynchronously, even if the Promise is already settled when you attach it.

6 · then returns a new Promise, and that's chaining

Ask L6's question 7: what does .then return? A brand-new Promise. Not the same one (p.then(f) === p is false). That new Promise settles with whatever your callback did:

Your then callback…The next Promise is…
returns a value vfulfilled with v
returns nothingfulfilled with undefined
returns a Promisewaits for it, then takes its result
throwsrejected with what was thrown, so it skips to the next catch

Row 2 is L6 §2b again. map stores whatever your callback returns, including undefined. then passes on whatever your callback returns, including undefined. A forgotten return inside a then is the most common Promise bug there is.

And a catch that returns a value recovers the chain: the next then runs normally with that value. D5 in §11 tests exactly this.

7 · The second queue: microtasks

Promise callbacks (then, catch, finally) do not go into the task queue. They go into a separate, higher-priority queue: the microtask queue. (queueMicrotask(fn) puts a function there directly, and in 7b, the code after an await goes there too.)

The event loop, version 2 (the real one)
  1. Run the current task to completion. (At the start, that's your whole script.)
  2. The stack is empty, so run every microtask in the microtask queue, including any that get added while you're doing this. Keep going until it's empty.
  3. (The browser may repaint here.)
  4. Take the next one task from the task queue. Go to 1.

That's why your probe answer was 1 4 3 2: 3 is a microtask, so it runs as soon as the script ends. 2 is a task, so it waits for the next turn of the loop. Microtasks always drain completely before the next task.

setTimeout(() => console.log("task"), 0);
Promise.resolve().then(() => {
  console.log("m1");
  Promise.resolve().then(() => console.log("m2"));   // added DURING the drain
});
// m1   m2   task

m2 was queued while microtasks were draining, so it runs in the same drain, still before the task. (The flip side: a microtask that keeps queueing more microtasks starves every task, and the page freezes just like the while loop in §1.)

Goes toWhatRuns
Nowhere: runs now (sync)ordinary code · the Promise executor · callbacks to map/forEach/sortimmediately, in order
Microtask queuethen / catch / finally callbacks · queueMicrotask · code after await (7b)as soon as the stack is empty, all of them
Task queuesetTimeout / setInterval callbacks · event handlers (click, keypress) · network callbacksone per turn, after the microtasks drain

Row 1 has a trap of its own: "callback" does not mean "async". The function you pass to map runs synchronously, right there, inside map (L6 §2b). Only callbacks handed to the host or to a Promise wait.

9 · How to solve any output-order question

Don't simulate it in your head line by line. Label, then list.

  1. Go through the code once and label every console.log: S (sync), M (inside a then/catch/finally), or T (inside a setTimeout/setInterval).
  2. Write all the S ones, in source order.
  3. Then the M ones, in the order they were queued.
  4. Then the T ones, in queue order (shorter delays first). After each T, re-check: did it queue any new M? Those run before the next T.

The ebook's question 14, labelled:

setTimeout(() => console.log(1), 0);       // T
console.log(2);                             // S
new Promise(res => {
  console.log(3);                           // S  ← inside the executor: sync!
  res();
}).then(() => console.log(4));              // M
console.log(5);                             // S
// S: 2 3 5 · M: 4 · T: 1   →   2 3 5 4 1

Whoever answers 2 5 3 4 1 fell for the executor. That's the one to watch.

10 · Retrieval quiz

Where does a setTimeout callback wait until it can run?

The task queue. The host counts the time, then queues the callback. It runs when the stack is empty and it reaches the front of the queue: first in, first out.

The function you pass to new Promise(...) runs…

Immediately. The executor runs during new Promise(...). Only the then/catch callbacks are async.

Which of these is not one of a Promise's states?

Settled isn't a state. It's a word for "fulfilled or rejected", meaning no longer pending. The ebook gets this wrong.

p.then(f) returns…

A new Promise, which settles with whatever f returns (or throws). That's what makes chaining work.

After the script finishes, there are 2 tasks and 3 microtasks queued. What runs next?

All 3 microtasks, then 1 task. Microtasks drain completely, then one task runs, then the microtasks drain again.

11 · Output drills

Cold. Label first (S / M / T), then list. Give the output and the label for each line.

D1 · the executor 
console.log("a");
new Promise(res => { console.log("b"); res("c"); }).then(v => console.log(v));
console.log("d");

a b d c. b is in the executor, so it's S. c is a then callback, so it's M.

D2 · tasks and microtasks queueing each other 
setTimeout(() => {
  console.log(1);
  Promise.resolve().then(() => console.log(2));
}, 0);
setTimeout(() => console.log(3), 0);
Promise.resolve().then(() => {
  console.log(4);
  setTimeout(() => console.log(5), 0);
});

4 1 2 3 5. The script queues T1, T2 and M1. Microtasks drain first: M1 logs 4 and queues T3. Then T1 logs 1 and queues M2, which runs before T2 because microtasks drain after every task: 2. Then T2: 3. Then T3: 5.

D3 · two chains 
Promise.resolve().then(() => console.log("A1")).then(() => console.log("A2"));
Promise.resolve().then(() => console.log("B1")).then(() => console.log("B2"));

A1 B1 A2 B2, interleaved. A2 can't be queued until A1's callback has run (it's waiting on the new Promise that A1's then returned). By then, B1 is already in line ahead of it.

D4 · the missing return 
Promise.resolve(5)
  .then(x => { x * 2; })
  .then(y => console.log(y));

undefined. Braces make a block with no return, so the first then passes on undefined. §6 row 2, and L6 §3's map trap in a new costume.

D5 · throw, catch, recover 
Promise.resolve(1)
  .then(x => { throw new Error("boom"); })
  .then(x => console.log("skipped?", x))
  .catch(e => { console.log("caught", e.message); return 7; })
  .then(v => console.log("after", v));

caught boom then after 7. The throw rejects, so the second then is skipped. catch handles it and returns 7, which recovers the chain, so the last then runs with 7.

D6 · settles once 
new Promise((res, rej) => { res("first"); res("second"); rej("third"); })
  .then(v => console.log("ok", v), e => console.log("err", e));

ok first. The first settle wins and the other two are silently ignored. (then takes an optional second argument, a rejection handler.)

D7 · two timers and a promise 
setTimeout(() => console.log("t10"), 10);
setTimeout(() => console.log("t0"), 0);
Promise.resolve().then(() => console.log("p"));
console.log("s");

s p t0 t10. S, then M, then the tasks in the order their timers finish. t0's timer finishes first even though it was set second.

13 · Coding drills

Drill A: write sleep(ms)

Write a function that returns a Promise which fulfills after ms milliseconds, so that sleep(1000).then(() => console.log("done")) logs after one second. It's three lines. It's also the most common "wrap a callback API in a Promise" question.

Hint, then the answer

Hint. You need a Promise (so: new Promise), and something that calls resolve later (so: setTimeout). Which function should the timer call?

function sleep(ms) {
  return new Promise(resolve => setTimeout(resolve, ms));
}

The bug everyone writes once: setTimeout(resolve(), ms). The () calls resolve right now and hands its return value (undefined) to the timer, so the Promise fulfills immediately (verified on Node). That's L3's "passing a function vs calling it", and 6b's "arguments are evaluated before the call".

Drill B: write promisify(fn)

Node-style APIs take an error-first callback as their last argument: getUser(id, (err, user) => ...). Write promisify(fn), which returns a new function that takes the same arguments (minus the callback) and returns a Promise instead.

function getUser(id, cb) {
  setTimeout(() => (id > 0 ? cb(null, { id }) : cb(new Error("bad id"))), 10);
}
const getUserP = promisify(getUser);
getUserP(1).then(u => console.log(u));             // { id: 1 }
getUserP(-1).catch(e => console.log(e.message));   // bad id
Hint ladder, then the answer

Hint 1. promisify takes a function and returns a function. That's a HOF (L3).

Hint 2. The returned function collects its arguments with rest (...args), returns a new Promise, and inside the executor calls fn with those arguments plus one more: a callback that you write, which turns err into reject and result into resolve.

function promisify(fn) {
  return function (...args) {
    return new Promise((resolve, reject) => {
      fn.call(this, ...args, (err, result) => {
        if (err) reject(err);
        else resolve(result);
      });
    });
  };
}

What it fuses: L3 (a HOF that returns a function), L5 (rest parameters), L4 (fn.call(this, ...) keeps this, so it works on methods. That's why the outer one is a regular function, and the executor is an arrow, so it can see that this.) And this page: the callback converts "called later, by someone else" into a Promise that settles once. It's Node's util.promisify, by hand. All three cases, including a method that uses this, verified on Node.
