Lesson 4 · Module 4 — JavaScript Foundations

The this keyword & binding

Closures are decided by where a function was written. this is decided by how it was called. That one contrast is the whole module.

Where this sits Lesson 3 gave you lexical — a function is bundled with the scope it was born in, and nothing you do at call time can change that. this is the exact opposite: it is bound fresh on every single call, and the same function can see a different this on two consecutive lines. Hold those two sentences side by side and most of this lesson is already done. Lesson 3 also left one thing deliberately unfinished — "an arrow has no own this" was stated without proof. This lesson pays that off, and the ebook marks this section "asked frequently, all scenarios covered, learn carefully."

0 · Gate check — carried from Lesson 3

Two items came out of the L3 drill. Answer both out loud, cold, before you scroll. No peeking at Lesson 3 first — the point is whether the label is there without the examples.

Define higher-order function and callback. Are they the same thing?

A higher-order function takes a function as an argument, returns a function, or both. A callback is a function passed into another function to be called later, by someone else. They are not the same — they are the two ends of one handoff. In arr.map(fn), map is the higher-order function and fn is the callback.

Nesting has nothing to do with it. Where the function sits in the source is irrelevant; what matters is whether functions cross the boundary as values. You have already written three: once takes one, the counter factory returns one, memoize does both.

And keep this separate from Lesson 3: memoize is a higher-order function because of its signature, and a closure because the returned wrapper keeps reading cache after memoize returned. Interviewers ask them as one question. Answer them as two.

What does === compare when both sides are objects?

Reference identity, and nothing else. It asks one question: are these two names pointing at the same object in memory? It never looks inside.

{ a: 1 } === { a: 1 }        // false — two objects, identical contents

const x = { a: 1 };
const y = x;
x === y                      // true  — one object, two names

This is the one you will meet again in three places: mutating an argument (below), React refusing to re-render because you mutated state in place and the reference never changed, and Object.freeze in Lesson 5.

1 · The one rule that generates all the others

this is not decided by where a function is written. It is decided at call time, by how the function is invoked. The same function body can see four different this values depending on nothing but the call site.

function whoAmI() {
  console.log(this.name);
}

const a = { name: "A", who: whoAmI };
const b = { name: "B", who: whoAmI };

a.who();            // "A"
b.who();            // "B"  — same function, different this
whoAmI();           // undefined / crashes — no call-site object at all
The sentence that answers the whole module "this refers to the object that is currently executing the function, and it's bound at call time, not at definition time. So to work out this, I don't read the function — I read the call site."
Contrast with Lesson 3 — say this if they push Closures are lexical, this is dynamic. A closure's variables are fixed by where the function was authored and can never be reassigned from outside. this is re-decided on every invocation and can be forced from outside, with call/apply/bind. This single contrast is the most common follow-up in the module.

2 · The four binding rules, in precedence order

Every this question in every interview is one of these four. Check them top down and stop at the first match — that order is the precedence.

#RuleCall looks likethis is
1new bindingnew Fn()the brand-new object being constructed
2explicit bindingfn.call(o) · fn.apply(o) · fn.bind(o)whatever you passed in — o
3implicit bindingobj.fn()the object left of the dot — obj
4default bindingfn()globalThis/window, or undefined in strict mode

Arrow functions are not on this list, and that is the point. An arrow has no this of its own, so none of the four rules apply to it — it is skipped entirely and this resolves lexically instead. §5 proves it.

Rule 4, the bit that gets asked In non-strict mode, if this would be null or undefined, JavaScript substitutes the global object. That substitution is why a plain fn() sees window. In strict mode (and inside ES modules and class bodies, which are strict by default) there is no substitution and this stays undefined. "Depends on strict mode" is the answer that scores; "it's window" is the answer that gets a follow-up.

Rule 3 in one line: read left of the dot

const user = {
  name: "Tarun",
  greet() { console.log("Hi " + this.name); }
};
user.greet();                // "Hi Tarun" — `user` is left of the dot

const outer = { name: "outer", inner: { name: "inner", greet() { console.log(this.name); } } };
outer.inner.greet();         // "inner" — only the LAST dot counts
The only dot that matters a.b.c.fn() → this is a.b.c. Not a. Interviewers love a three-deep chain precisely because people answer with the outermost object.

3 · Losing this — the bug this module exists for

Here is the failure that generates 90% of real-world this bugs. A method is only a method because of how it's called. Pull it off its object and it is just a function again.

const user = {
  name: "Tarun",
  greet() { console.log("Hi " + this.name); }
};

user.greet();                     // "Hi Tarun"     — rule 3

const g = user.greet;             // we copied the FUNCTION, not the binding
g();                              // "Hi undefined" — rule 4

setTimeout(user.greet, 100);      // "Hi undefined" — passed as a value, called bare
button.addEventListener("click", user.greet);  // same bug
Why this is a Lesson 3 problem wearing a Lesson 4 costume const g = user.greet copies the function value — exactly the "functions are values" fact from L3 §1. The object was never part of the function; it was supplied by the call site, and you just threw the call site away. There is no such thing as a bound method in JavaScript unless you bind it.

Three fixes, and you should be able to name all three:

setTimeout(user.greet.bind(user), 100);          // 1. bind — rule 2
setTimeout(() => user.greet(), 100);             // 2. wrap it, restore the dot — rule 3
setTimeout(function () { user.greet(); }, 100);  // 3. same idea, older syntax

4 · call, apply, bind

Rule 2 — forcing this from outside. The ebook flags this as very frequently asked, and it wants the example first, then the difference.

MethodInvokes?ArgumentsReturns
callimmediatelyone by one, comma-separatedthe function's result
applyimmediatelyas a single arraythe function's result
bindno — laterone by one (and can be pre-filled)a new function
 
function intro(greeting, punct) {
  console.log(greeting + ", I'm " + this.name + punct);
}
const t = { name: "Tarun" };

intro.call(t, "Hello", "!");       // runs now — args one by one
intro.apply(t, ["Hello", "!"]);    // runs now — args in an array

const bound = intro.bind(t);       // runs NOTHING. returns a new function.
bound("Hello", "!");               // now it runs
Say this "call and apply both invoke immediately — the only difference is argument syntax: call takes a list, apply takes an array. bind doesn't invoke at all; it returns a new function with this permanently fixed, which is what you want for an event handler or a setTimeout, where you know the context now but not the firing time."
A for array — the mnemonic that survives the pressure apply → array. And bind is the odd one out because it is the only one that returns instead of runs.

Partial application — the bind detail that separates candidates

const hello = intro.bind(t, "Hello");   // pre-fill the FIRST argument
hello("!");                             // "Hello, I'm Tarun!"
hello("?");                             // "Hello, I'm Tarun?"

Arguments passed to bind are locked in ahead of the ones passed at call time. That is partial application, and it is the same closure-over-configuration shape as the multiplier factory from Lesson 3.

Once bound, always bound A bound function cannot be re-bound. intro.bind(a).bind(b) still uses a, and bound.call(b) is ignored too. bind beats call because the inner binding was already applied when the wrapper was created — rule 2 already fired.

5 · Arrows: the payoff Lesson 3 owed you

Lesson 3 told you an arrow "has no own this". Here is what that actually means: an arrow is not in the four-rule table at all. When you write this inside an arrow, it is not resolved by the call — it is resolved the same way any ordinary variable is resolved, by walking up the scope chain from Lesson 2 to the nearest enclosing function that does have a this.

const obj = {
  name: "Tarun",
  regular() { console.log(this.name); },
  arrow:   () => console.log(this.name)
};

obj.regular();      // "Tarun"    — rule 3, left of the dot
obj.arrow();        // undefined  — the dot is IGNORED
Why obj.arrow() fails — the exact wording "An arrow has no this binding of its own, so this resolves lexically, from the scope where the arrow was defined — not from the call site. An object literal does not create a scope, so the enclosing scope here is the module or global, and this is undefined/window. That's why an arrow can never be used as a method."
The trap inside the trap People say "an object creates a scope." It does not. Only functions and blocks create scope (Lesson 2). { name: "Tarun" } is data, not a scope. That is the real reason the arrow reaches straight past it.

So when IS an arrow the right answer?

Exactly when you want to keep the outer this — the callback-inside-a-method problem, which was a genuine ES5 pain point:

// ES5 — the callback got its own `this`, so you had to hand it in
const timer = {
  name: "T",
  start: function () {
    setTimeout(function () {
      console.log(this.name);      // undefined — rule 4, bare call
    }.bind(this), 1000);           // ← the fix everyone wrote for years
  }
};

// ES6 — the arrow simply never had its own `this` to lose
const timer2 = {
  name: "T",
  start() {
    setTimeout(() => console.log(this.name), 1000);   // "T"
  }
};

The rule that decides it every time: use a regular function when the object should supply this (a method). Use an arrow when you want to inherit the surrounding this (a callback inside a method). Arrows didn't add a feature — they removed a footgun.

The full arrow limitation list

fn.call(obj) on an arrow does not error — it is simply ignored, which is worse, because it fails silently. And notice row 3 is your TypeError rule again: the name resolved fine, the operation was illegal.

6 · this in classes and React

Class bodies are strict mode, so a lost this throws instead of silently reading the global — which is why the React class-component bug was so loud:

class Counter {
  constructor() { this.count = 0; }
  inc() { this.count++; }
}
const c = new Counter();          // rule 1 — `this` is the new object

const f = c.inc;
f();                              // TypeError: Cannot read properties of undefined

// the three historical fixes, in the order the ecosystem found them
this.inc = this.inc.bind(this);   // 1. bind in the constructor
onClick={() => this.inc()}        // 2. arrow at the call site
inc = () => { this.count++; }     // 3. class field — arrow captures instance `this`
Worth saying out loud in a React interview "Hooks made this mostly moot — a function component has no this to lose, which removed an entire category of bug. But the mechanism is the same one: pulling a method off its object drops the call site." That answer shows you know why the framework moved, not just that it did.

7 · The procedure — the fifth question

Lesson 2 gave you three questions. Lesson 3 added a fourth (when does this run, and what is the binding at that moment?). this gets the fifth, and it is deliberately worded to fire at the call site, because that is where you keep not looking:

Question 5 How was this function called — and is it an arrow?
Arrow → skip the table, walk the scope chain to the enclosing function's this.
Not an arrow → run the four rules top down: new → explicit → left of the dot → bare call.

Do it in that order and never read the function body first. The body cannot tell you the answer. The call tells you the answer.

8 · Retrieval quiz

When is this decided?

At call time. This is the exact opposite of a closure, which is fixed lexically at authoring time. Same function, two call sites, two different this values.

a.b.c.fn() — what is this?

a.b.c. Implicit binding reads only the last dot. The outer objects in the chain are irrelevant to this.

Which one does not invoke the function immediately?

bind. It returns a new function with this fixed, to be called whenever you like. call and apply both run right now and differ only in how arguments are passed — a list vs an array.

const o = { n: 1, f: () => console.log(this.n) }; o.f();

undefined. An arrow has no own this, so the dot is ignored and this resolves lexically. An object literal is not a scope, so it skips straight to module/global scope, where there is no n.

Non-strict mode, plain fn() — what is this?

The global object (window/globalThis), because non-strict mode substitutes the global object whenever this would be null or undefined. In strict mode there is no substitution and it stays undefined. Naming the substitution is what scores.

9 · Output drills

Cold. Per line, apply question 5 first — how was it called, and is it an arrow? — before you read a single line of the body.

D1 · the copied method 
const user = { name: "T", greet() { return this.name; } };
const g = user.greet;
console.log(user.greet(), g());

"T" undefined (non-strict; throws in strict mode/modules). user.greet() is rule 3. g() is a bare call — rule 4. Copying the function copied the value, never the binding.

D2 · method vs arrow in the same object 
const o = {
  n: 10,
  reg()  { return this.n; },
  arrow: () => this.n
};
console.log(o.reg(), o.arrow());

10 undefined. Same object, same dot, opposite results — because the arrow is never in the four-rule table. If this is undefined at module scope, this.n throws; at top-level script scope this is window, so it reads undefined.

D3 · the nested function 
const obj = {
  n: 5,
  run() {
    function inner() { return this.n; }
    return inner();
  }
};
console.log(obj.run());

undefined. run() gets this = obj fine, but inner() is a bare call — rule 4. this does not inherit down into nested regular functions the way scope does. This is the difference between the scope chain and this in one snippet: inner can read obj's variables lexically, but not its this. Fix: make inner an arrow.

D4 · bind beats call 
function f() { return this.v; }
const a = { v: 1 }, b = { v: 2 };
const bf = f.bind(a);
console.log(bf(), bf.call(b));

1 1. A bound function cannot be re-bound — rule 2 already fired when bind created the wrapper, and the later call is ignored.

D5 · call vs apply 
function sum(a, b) { return a + b + this.base; }
const ctx = { base: 100 };
console.log(sum.call(ctx, 1, 2), sum.apply(ctx, [1, 2]));

103 103. Identical results — the only difference is argument syntax. If you can't name a behavioural difference beyond that, you're right: there isn't one.

D6 · the callback trap 
const timer = {
  n: 7,
  start() {
    setTimeout(function () { console.log(this.n); }, 0);
    setTimeout(() => console.log(this.n), 0);
  }
};
timer.start();

undefined then 7. The regular callback is invoked bare by the timer — rule 4, and the call site is inside the browser, not your code. The arrow never had its own this, so it reads start's, which is timer. This is the single most useful snippet in the module.

10 · Coding drill — write bind yourself

The classic follow-up: "implement Function.prototype.bind." It is a Lesson 3 problem in disguise — a higher-order function that returns a closure over this and the pre-filled arguments. Attempt it before opening the answer.

Function.prototype.myBind = function (ctx, ...preset) {
  // return a NEW function that calls the original with `ctx` as this
};
Answer + what it proves 
Function.prototype.myBind = function (ctx, ...preset) {
  const fn = this;                       // `this` IS the function — rule 3, left of the dot
  return function (...later) {           // closure over fn, ctx and preset
    return fn.apply(ctx, [...preset, ...later]);
  };
};

Three things it demonstrates at once: this inside myBind is the function it was called on (implicit binding, because you write intro.myBind(...)); the returned function is a closure holding fn, ctx and preset alive after myBind returned; and apply is the natural choice because you already have the arguments as an array.

Also try myCall: same shape, but invoke immediately with a spread instead of returning a wrapper.
