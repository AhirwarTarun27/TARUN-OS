Classes, from the floor up

5c showed that a class is the prototype chain with nicer syntax. This page covers the rest: constructor, super, private fields, static, instanceof, and the gotchas interviewers actually ask about. One idea holds the whole page together: in a child class, the parent builds the object.

What your probe showed
  • new, steps 1 and 2: right. Step 3 you couldn't remember. Step 3 is run the constructor body with this set to the new object. This page is built on it, because in a child class, super is how step 3 happens. §3.
  • Class methods are non-enumerable, and the class body is strict: right. §2 adds the other differences.
  • "extends links multiple prototypes": no. A class has one parent. extends adds one link, and the chain stays a single line. §3.
  • super(props), a child with no constructor, calling the parent's method: "no idea". §3, §4, §5.
  • "#count is not accessible outside the class": right idea, no label. It's a SyntaxError, so the file never runs at all. §7.
  • "instanceof checks the Error prototype": half. It walks the left side's chain, looking for the right side's .prototype. §10.
You asked to keep React class components short, since react.dev now treats them as legacy. §12 is one section: what you need to read old code, and the one place a class is still required.

1 · A class, read line by line

Every part of a class in one example. Read the comments: each says where that line ends up. You already proved the field and method rows cold in 5c. This adds the rest.

class Counter {
  static created = 0;              // static field   → on Counter itself
  #count = 0;                      // private field  → on the instance, hidden
  label = "clicks";                // public field   → on the instance

  constructor(start) {             // runs during `new`, at step 3
    this.#count = start;
    Counter.created++;
  }

  increment() { this.#count++; return this; }   // method → Counter.prototype
  get value() { return this.#count; }           // getter → Counter.prototype
  static describe() { return "counts things"; } // static method → Counter
}

const c = new Counter(5);
c.increment().increment();
c.value;              // 7         ← a getter, so no ()
Counter.created;      // 1
Counter.describe();   // "counts things"
Object.keys(c);       // ["label"] ← #count is not a key at all
typeof Counter;       // "function" ← a class IS a function
You writeIt lands onOwn property of the instance?
label = "clicks" (field)the instanceyes, one per object
#count = 0 (private field)the instance, hiddennot a property at all. No key, no spread, no JSON
increment() {} (method)Counter.prototypeno, shared through the chain
get value() {} (getter)Counter.prototypeno, shared through the chain

Methods and getters go on the prototype. Fields go on the instance. Statics go on the class. That's the 5c rule with two more rows.

2 · Class vs constructor function: the same machine, with guards

These two build the same thing: same prototype, same chain, same rex.bark === fido.bark.

// the old way
function DogFn(name) { this.name = name; }
DogFn.prototype.bark = function () { return this.name + " woof"; };

// the class way
class Dog {
  constructor(name) { this.name = name; }
  bark() { return this.name + " woof"; }
}

The structure is the same. The behaviour is not. A class adds guards that catch bugs the old way lets through quietly:

3 · The floor: step 3 of new, and why super exists

Here's new from 5c, with the step you couldn't remember marked:

const rex = new Dog("Rex");

  1.  create a fresh empty object
  2.  link it: its prototype = Dog.prototype
  3.  RUN THE CONSTRUCTOR BODY with `this` = that object      ← this.name = "Rex" happens here
  4.  return it

For a class without extends, that's the whole story. A child class is different. The child does not build the object. The parent does. When the child's constructor starts, there is no object yet, so this doesn't exist. super(...) is the call that runs the parent's constructor, which builds the object and hands it back. Only then does the child have a this.

class Animal {
  constructor(name) { this.name = name; }
}
class Puppy extends Animal {
  constructor(name) {
    super(name);           // the parent builds the object
    this.tricks = [];      // now `this` exists
  }
}

new Puppy("Rex");

  Puppy's constructor starts             this = (nothing yet)
  super("Rex")  →  Animal's constructor runs:
                    1. create {}
                    2. link it to Puppy.prototype     ← the CHILD's prototype, not Animal's
                    3. run Animal's body: this.name = "Rex"
                    4. hand it back
  this = that object                     ← only now
  this.tricks = []
  return it                              // { name: "Rex", tricks: [] }

Step 2 says Puppy.prototype. Animal builds the object, but links it to the prototype of the class you actually called new on. That's why a puppy gets Puppy's methods and, one link further up, Animal's. Checked on Node: inside Animal's constructor, Object.getPrototypeOf(this) === Puppy.prototype is true.

The error, and what it means

class Bad extends Animal {
  constructor(name) {
    this.x = 1;            // no object yet
    super(name);
  }
}
new Bad("a");
// ReferenceError: Must call super constructor in derived class
//   before accessing 'this' or returning from derived constructor

It's a ReferenceError, not a TypeError. Same family as the TDZ: this is a binding that isn't ready yet, like let x before its line. Leaving out super altogether gives the same error, at the moment the constructor finishes.

The myth: "super must be the first line" False. The rule is only no this before super. Ordinary code before it is fine: 
class Doubled extends Animal {
  constructor(n) {
    const twice = n + n;   // fine: doesn't touch `this`
    super(twice);
  }
}
new Doubled("ab").name;    // "abab"

One parent only

class C extends A, B {} is a SyntaxError. extends takes one class, and the chain is one line: puppy → Puppy.prototype → Animal.prototype → Object.prototype → null. If you need behaviour from two places, combine objects (store a helper in a field) instead of inheriting twice.

What extends and super replace

Interviewers ask "how did inheritance work before class?". It took four lines, and each one maps to something you know from 5c:

function AnimalFn(name) { this.name = name; }
AnimalFn.prototype.speak = function () { return this.name + " speaks"; };

function PuppyFn(name) {
  AnimalFn.call(this, name);                          // ≈ super(name). Borrow the parent's body
  this.tricks = [];
}
PuppyFn.prototype = Object.create(AnimalFn.prototype); // the instance link
PuppyFn.prototype.constructor = PuppyFn;               // repair the pointer you just replaced
Object.setPrototypeOf(PuppyFn, AnimalFn);              // the static link (5c §6)

new PuppyFn("Bo").speak();                             // "Bo speaks"

There's one real difference, and it's the one that matters. In the old way, the child creates the object and borrows the parent's body with .call. In a class, the parent creates it. That's why a class can properly extend built-ins, whose constructors have to make the object themselves:

class MyArr extends Array {}
const m = new MyArr();  m[5] = 1;
m.length;  Array.isArray(m);   // 6  true    ← a real array

// the old way: Array.call(this) can't turn an ordinary object into an array
function MyArrFn() { Array.call(this); }
MyArrFn.prototype = Object.create(Array.prototype);
const f = new MyArrFn();  f[5] = 1;
f.length;  Array.isArray(f);   // 0  false   ← an ordinary object that inherits array methods
"Is class just syntactic sugar?" "Mostly. It builds the same prototype chain, and typeof a class is "function". But it isn't only sugar. It refuses to run without new, its body is always strict, its methods are non-enumerable, and in a subclass the parent creates the object. That last part is why extends Error and extends Array work properly. Private #fields have no old-style equivalent either."

4 · No constructor? JavaScript writes one for you

class Animal { constructor(name) { this.name = name; } }
class Puppy extends Animal {}          // no constructor written

new Puppy("Rex").name;                 // "Rex"   ← the parent's constructor ran

A class without a constructor gets a default constructor:

ClassThe constructor you get for free
no extendsconstructor() {}
extends Parentconstructor(...args) { super(...args); }, which passes every argument up

The bug comes when you write your own. As soon as a child has a constructor, the free one is gone, and passing arguments to super is your job:

class Puppy2 extends Animal {
  constructor(name, breed) {
    super();               // forgot to pass name up
    this.breed = breed;
  }
}
const q = new Puppy2("Rex", "lab");
q.name;    // undefined   ← Animal ran with no argument
q.breed;   // "lab"

No error, just a missing value. The rule: only write a child constructor when the child needs its own setup. If you write one, pass the parent's arguments to super.

5 · Overriding, and super.method()

A child can define a method with the same name as the parent's. The child's version wins, because it's found first on the chain. That's 5c's shadowing, one level up. To add to the parent's version instead of replacing it, call super.method():

class Animal {
  constructor(name) { this.name = name; }
  speak() { return this.name + " makes a sound"; }
}
class Dog extends Animal {
  speak() { return super.speak() + ", then barks"; }
}
new Dog("Rex").speak();     // "Rex makes a sound, then barks"
rex.speak()

 rex                 { name: "Rex" }     speak? ✗
  │
  ▼
 Dog.prototype       { speak }           speak? ✓  STOP   ← the override wins
  │
  ▼
 Animal.prototype    { speak }           reached only through super.speak()
  │
  ▼
 Object.prototype  →  null

super.speak() starts the search one link above the class it's written in, but this is still rex. That's why the parent's version prints "Rex".

The infinite-loop trap Writing this.speak() instead of super.speak() inside the override calls itself, because this.speak finds Dog's version first. It runs until the stack is full: RangeError: Maximum call stack size exceeded.

6 · The init-order trap

This is the hardest class question you're likely to get, and it follows from §3. Predict before you read the answer:

class A {
  name = "A";
  constructor() {
    console.log(this.name);
    this.hello();
  }
  hello() { console.log("A hello"); }
}
class B extends A {
  name = "B";
  greeting = "hi";
  hello() { console.log("B hello", this.greeting); }
}
new B();
Answer 
A
B hello undefined

A class's fields are installed right after its super() returns. So in new B():

  1. B's free constructor calls super(), so A builds the object.
  2. A's fields go on: name = "A".
  3. A's constructor body runs. It logs "A", because B's name doesn't exist yet. Then it calls this.hello(), which finds B's version, because methods are on the prototype from the start. B's greeting isn't there yet, so undefined.
  4. super() returns. B's fields go on: name = "B", greeting = "hi".
  5. The rest of B's constructor runs (there isn't any).

After construction, b.name is "B". It was only "A" while A's constructor ran.

Say it like this "A parent's constructor runs before the child's fields exist. So the parent can call the child's methods, which are already on the prototype, but it can't see the child's fields. Don't call overridable methods from a constructor."

7 · Private #fields: real privacy

class Wallet {
  #balance = 0;
  deposit(n) { this.#balance += n; return this.#balance; }
  static isWallet(x) { return #balance in x; }      // does x have this class's #balance?
}
const w = new Wallet();
w.deposit(50);          // 50
w.balance;              // undefined  ← there's no public property called balance
w["#balance"];          // undefined  ← the string "#balance" is just a different key
Object.keys(w);         // []
JSON.stringify(w);      // "{}"
Wallet.isWallet(w);     // true
Wallet.isWallet({});    // false

Outside the class it's a SyntaxError, so nothing runs

console.log("line 1 ran");      // never prints
class W { #b = 1; }
const x = new W();
console.log(x.#b);
// SyntaxError: Private field '#b' must be declared in an enclosing class

"Not accessible" is the behaviour. SyntaxError is the label, and it says something specific: the engine rejects the file before running any of it, so even line 1 never runs. Privacy is checked while the code is parsed, not while it runs.

  • A subclass can't see it either. class Child extends Wallet { peek() { return this.#balance; } } is the same SyntaxError. # is private to the class body it's written in. It's not "protected", and JavaScript has no protected.
  • Calling a method on the wrong object fails at run time: w.deposit.call({}, 5) gives TypeError: Cannot read private member #balance from an object whose class did not declare it.
  • Private methods work the same way: #validate() {}, called as this.#validate().
ApproachReally private?Trade-off
this._balanceno. It's a naming conventionanyone can read or change it, and Object.keys lists it
closure (Lesson 3)yesevery method has to live in the constructor, so you get one copy of each method per object (5c §1's 1000 dogs)
#balanceyes, enforced by the languagemethods stay shared on the prototype. This is the modern answer
TypeScript private balanceonly at compile timeit compiles to a normal property: Object.keys gives ["balance"] at run time

That last row is worth saying in an interview, since you write TypeScript. Checked by compiling it with tsc: the output is a plain balance = 100.

8 · static: on the class, not the instances

class User {
  static count = 0;
  constructor(name) { this.name = name; User.count++; }
  static fromJSON(json) { return new this(JSON.parse(json).name); }
}
const u = User.fromJSON('{"name":"Asha"}');
u.name;         // "Asha"
User.count;     // 1
u.count;        // undefined   ← statics are not on instances
u.fromJSON();   // TypeError: u.fromJSON is not a function   ← never found on u's chain
  • this inside a static method is the class. That's Lesson 4's rule 3: User.fromJSON() has User left of the dot. So new this(...) builds whichever class it was called on. Admin.fromJSON(...) builds an Admin, through the static link from 5c.
  • Use statics for things that belong to the class as a whole: factory methods like fromJSON, counters, constants, helpers.
  • You've used statics all along: Array.from, Array.isArray, Object.keys, Promise.all, Number.isInteger, Date.now. Every one is called on the class, never on an instance. [1,2].isArray doesn't exist.

9 · Getters and setters in a class

5b taught accessors. In a class they look like this, usually with a private field holding the real value:

class Temp {
  #c = 0;
  get f() { return this.#c * 9 / 5 + 32; }
  set f(v) { this.#c = (v - 32) * 5 / 9; }
  get c() { return this.#c; }                 // getter only: read-only from outside
}
const t = new Temp();
t.f = 212;      // looks like storing a value. It runs the setter
t.c;            // 100
Object.hasOwn(t, "f");             // false   ← accessors live on Temp.prototype
Object.hasOwn(Temp.prototype, "f"); // true

Writing to a getter-only property: in non-strict code it's silently ignored (t.c stays 100). In strict code, which includes every class body and every ES module, it's TypeError: Cannot set property c of #<Temp> which has only a getter.

10 · instanceof is a walk up the chain

x instanceof C asks one question: is C.prototype anywhere in x's chain? It walks the left side's chain and looks for the right side's .prototype.

class ValidationError extends Error {}
const err = new ValidationError("bad email");

 err ──► ValidationError.prototype ──► Error.prototype ──► Object.prototype ──► null

err instanceof ValidationError;   // true   ValidationError.prototype is on the chain
err instanceof Error;             // true   Error.prototype is further up
err instanceof Object;            // true
err instanceof TypeError;         // false  TypeError.prototype is not on this chain

Three gotchas, and each one follows from "it only checks the chain":

"hi" instanceof String;                 // false  ← a primitive isn't an object, so there's no chain to walk

class Cat { constructor() { this.lives = 9; } }
const c = Object.create(Cat.prototype);
c instanceof Cat;   c.lives;            // true  undefined  ← linked, but the constructor never ran

Object.create(null) instanceof Object;  // false  ← its chain is empty

The middle one is the important one. instanceof means "is linked to", not "was built by". To check for an array, use Array.isArray(x). It doesn't depend on the chain, so it also works on arrays from another iframe, where instanceof Array fails.

11 · Extending Error: custom errors

The most common real-world reason to write extends today:

class ValidationError extends Error {
  constructor(message, field) {
    super(message);                  // Error's constructor sets .message and the stack
    this.name = "ValidationError";   // otherwise .name is "Error"
    this.field = field;
  }
}

try {
  throw new ValidationError("email is required", "email");
} catch (err) {
  if (err instanceof ValidationError) console.log(err.name, err.field, err.message);
  else throw err;                    // not ours: let it keep going up
}
// ValidationError email email is required
  • Why bother? So a catch can tell your expected failures (bad input, show the user a message) apart from real bugs (rethrow them). instanceof makes that a one-line check.
  • Forget this.name and String(err) is "Error: ...", and so is the first line of the stack trace. The class works, but the logs say Error.
  • The built-in error types are classes on the same chain. SyntaxError, ReferenceError, TypeError, RangeError, and the AggregateError from Promise.any all extend Error. new TypeError() instanceof Error is true. That answers the ebook's "types of errors" question.
  • Wrapping an error (modern JS): new Error("save failed", { cause: err }) keeps the original on .cause.

12 · React class components: just enough to read old code

react.dev lists Component under "Legacy APIs" and says: "We recommend defining components as functions instead of classes." Hooks don't work in classes. You won't write new class components, but older codebases and the ebook are full of them, and now you can read every line:

class Counter extends React.Component {
  constructor(props) {
    super(props);                                   // §3: no `this` until the parent builds it
    this.state = { count: 0 };
    this.handleClick = this.handleClick.bind(this); // Lesson 4: the lost-dot fix
  }
  handleClick() { this.setState({ count: this.state.count + 1 }); }
  render() {
    return <button onClick={this.handleClick}>{this.state.count}</button>;
  }
}
  • Why super(props)? Counter is a child of React.Component, so this doesn't exist until super runs. The React docs say to call super(props) before any other statement, so that this.props works inside the constructor.
  • Why the bind? onClick={this.handleClick} passes the function without its dot. React calls it later as a plain function, so this is undefined (class bodies are strict). That's the lost-method bug from Lesson 4 §3. The other fix is an arrow field, handleClick = () => {...}, from 5c §7.
  • The one place a class is still required: error boundaries. react.dev: "There is currently no way to write an Error Boundary as a function component." An error boundary uses static getDerivedStateFromError (a static, §8) and componentDidCatch. In practice, most teams use the react-error-boundary package rather than writing the class.
Say it like this "Class components are legacy now. I write function components with hooks. The one place I still see a class is an error boundary, because there's no hook for catching render errors yet. Usually I'd reach for react-error-boundary."

13 · Quick checks

In a child class constructor, why can't you use this before super()?

The object doesn't exist yet. In a child class the parent's constructor creates it, and super() is the call that runs it. Using this before that is a ReferenceError. Code that doesn't touch this is allowed before super.

A child class has no constructor. What happens on new Child("a")?

The parent's constructor runs with "a". The default child constructor is constructor(...args) { super(...args); }, which passes every argument up.

obj.#secret written outside the class. What happens?

SyntaxError. Private names are checked when the code is parsed, so the whole file is rejected before line 1 runs. obj["#secret"] is different: that's an ordinary string key, and it gives undefined.

What does x instanceof C actually check?

Whether C.prototype is anywhere on x's chain. That's why Object.create(C.prototype) instanceof C is true even though the constructor never ran.

Inside an override, how do you run the parent's version of speak?

super.speak(). It starts the search one link above the class it's written in, and keeps the same this. this.speak() finds the override itself and loops forever (RangeError). Parent.speak would look for a static.

D1 · class Car {}

D2 · class A { constructor(x, y) { this.sum = x + y; } }

P sees parent, then C sees child. While P's constructor runs, only P's field is installed. C's field goes on as soon as super() returns, so by C's console.log it has replaced the value.

"ABC". Each super.hi() goes one link up from the class it's written in: C's calls B's, B's calls A's. The strings are joined as the calls return, innermost first.

No outputs, no explanations. For each line, say: runs, TypeError, ReferenceError or SyntaxError. 60 seconds. Bar 7/8.

  2. new Early() on the line above class Early {}

Answers

  2. ReferenceError: the class is in the TDZ

  5. SyntaxError: the file is rejected before anything runs

16 · Coding drills

For each one, work in this order: how it's used → trace one example by hand → the steps as comments → code.

Drill A: write myInstanceOf(obj, Ctor)

A common polyfill question, and it's §10 turned into code. It must match the real instanceof.

// how it's used
class A {}  class B extends A {}
myInstanceOf(new B(), A);                  // true
myInstanceOf(new A(), B);                  // false
myInstanceOf(Object.create(null), Object); // false
myInstanceOf(5, Number);                   // false  ← primitives have no chain
Hint ladder, then the answer

Hint 1. Trace myInstanceOf(new B(), A) on paper. Which objects are on the chain of new B(), in order? At which one do you stop?

Hint 2. It's a loop: compare, then step up with Object.getPrototypeOf. What value tells you the chain has ended?

Hint 3. Primitives and null have to return false before the loop starts.

function myInstanceOf(obj, Ctor) {
  if (obj === null || (typeof obj !== "object" && typeof obj !== "function")) return false;
  let proto = Object.getPrototypeOf(obj);
  while (proto !== null) {
    if (proto === Ctor.prototype) return true;   // found the right side's .prototype
    proto = Object.getPrototypeOf(proto);        // one link up
  }
  return false;                                  // walked off the end
}

Checked on Node against the real instanceof for 8 cases, including arrays, arrow functions and null: all match. Two things to say out loud: it compares against Ctor.prototype, not Ctor, and the loop ends at null.

Drill B: a BankAccount class

The "design a class" question. It uses private fields, a getter, a static, and a custom error.

// how it's used
const acc = new BankAccount("Asha", 100);
acc.deposit(50);        // 150
acc.balance;            // 150   ← readable
acc.balance = 1e9;      // no effect: there's no setter
acc.withdraw(500);      // throws InsufficientFundsError
                        //   err.name === "InsufficientFundsError", err.shortBy === 350
JSON.stringify(acc);    // '{"owner":"Asha"}'   ← the balance is private
BankAccount.count;      // how many accounts have been created
Hint ladder, then the answer

Hint 1. Which line in the usage makes balance read-only? What do you write so that reading works and writing doesn't?

Hint 2. count belongs to the class as a whole, not to one account.

Hint 3. The error is its own class. What must its constructor call first, and which property makes the logs say InsufficientFundsError?

class InsufficientFundsError extends Error {
  constructor(shortBy) {
    super(`Short by ${shortBy}`);
    this.name = "InsufficientFundsError";
    this.shortBy = shortBy;
  }
}

class BankAccount {
  static count = 0;
  #balance;

  constructor(owner, opening = 0) {
    this.owner = owner;
    this.#balance = opening;
    BankAccount.count++;
  }

  get balance() { return this.#balance; }

  deposit(amount) {
    this.#balance += amount;
    return this.#balance;
  }

  withdraw(amount) {
    if (amount > this.#balance) throw new InsufficientFundsError(amount - this.#balance);
    this.#balance -= amount;
    return this.#balance;
  }
}

Every line of the usage was checked on Node. Four things to say out loud: #, not _ (real privacy) · a getter with no setter (read-only from outside) · BankAccount.count, not this.count (it belongs to the class) · a custom error, so the caller can catch it by type. Follow-up they'll ask: reject amount <= 0, which would be your input validation at the boundary.

17 · The sentences you say

"Class vs constructor function?"

"They build the same prototype chain, but a class adds guards. It throws if you call it without new, the body is always strict, methods are non-enumerable, and it's hoisted into the TDZ like let. It also gives you extends, super, static and private #fields."

"What does super do?"

"Two things. super(...) in a child constructor runs the parent's constructor. In a subclass the parent creates the object, so this doesn't exist until super returns. Using it earlier is a ReferenceError. super.method() in any method calls the parent's version, with the same this."

"How do you make a property private?"

"With a # field. It's enforced by the language: accessing it from outside the class is a SyntaxError, and it doesn't show up in keys or JSON. Before that, people used closures, which cost a copy of every method per object, or an underscore, which is only a convention. TypeScript's private is compile-time only."

"What does instanceof check?"

"Whether the right side's .prototype appears anywhere on the left side's prototype chain. It checks the link, not who built the object. For arrays I use Array.isArray, which also works across iframes."

"Why extend Error?"

"So a catch can tell expected failures from bugs with instanceof. I call super(message) first, set this.name so the logs show the right type, and rethrow anything I don't handle."
