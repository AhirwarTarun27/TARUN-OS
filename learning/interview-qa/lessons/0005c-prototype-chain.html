The prototype chain, from the floor up

Lesson 5 §5 opens with "every object has a hidden link to another object." That sentence is true, and it is unreadable — because nothing has ever shown you that link being created. This page shows you. Then §5 becomes revision.

Why this page exists Written 2026-09-20, after a re-read of §5 landed as "most of the things is hitting differently, I do not get the exact terms." Four gaps were named, and all four were real: the prototype / __proto__ collision, why any of this exists, the three code shapes looking unrelated, and shadowing.

But the answer to a fifth question was the actual diagnosis. "What does new Student('A') do, step by step?" → "No real idea."

new is the operation that installs the prototype link. A section about following a link, read by someone who has never watched one being made, cannot land however well it is written. That is the same shape as the getters/setters gap found this morning: the spread-vs-assign answer was unreachable because accessor properties had never been taught. Same failure, one module later, found the same way — by asking, not by drilling.

1 · Why prototypes exist at all

Start with the problem, because the solution is otherwise arbitrary trivia.

You have 1000 dogs. Every dog needs to bark. The naive object approach gives each dog its own copy of the function:

function makeDog(name) {
  return {
    name: name,
    bark() { return name + " says woof"; }   // a NEW function object, every single time
  };
}

1000 dogs, 1000 identical bark functions sitting in memory. That is pure waste. The behaviour is the same for every dog — only the data differs.

The fix: store bark in exactly one place, and give every dog a pointer to that place.

                  ┌────────────────────────┐
                  │   one shared object    │
                  │   { bark: function }   │
                  └────────────────────────┘
                     ▲        ▲        ▲
                     │        │        │      ← every dog points here
              ┌──────┘        │        └──────┐
       { name:"Rex" }  { name:"Fido" }  { name:"Bo" }
       1000 of these, each holding only its own DATA

That pointer is called the prototype. Following it is the prototype chain. And that is the whole idea.

The honest framing, and it makes everything downstream inevitable Prototypal inheritance began as a memory optimisation and became the object model. It is not a theory of classification borrowed from Java. It is "don't store the same function a thousand times," followed to its conclusion. Every strange thing in §5 is a consequence of that one decision.

Proof that the sharing is real, not a metaphor:

class Dog {
  constructor(name) { this.name = name; }
  bark() { return this.name + " says woof"; }
}
const rex = new Dog("Rex"), fido = new Dog("Fido");

Object.keys(rex);                   // ["name"]   ← only DATA lives on the dog
Object.hasOwn(rex, "bark");         // false      ← bark is NOT on rex
Object.hasOwn(Dog.prototype, "bark"); // true     ← it is over there

rex.bark === fido.bark;             // true       ← ONE function. not a copy each.

Read that last line again. rex.bark and fido.bark are not two equal functions. They are the same function object, reached through two different pointers. That is the optimisation working.

2 · What new actually does — the missing floor

Everything above depends on the pointer existing. new is what creates it. Four steps, in order:

const rex = new Dog("Rex");

  1.  create a fresh empty object                     →  {}
  2.  LINK it:  that object's prototype = Dog.prototype   ← THE STEP THAT MATTERS
  3.  run Dog's constructor body with `this` = that object →  { name: "Rex" }
  4.  return it

Step 2 is the answer to everything on this page. The "hidden link" §5 talks about is not hidden and not magic — it is step 2 of an operation you type every day.

Step 3 is Lesson 4 territory: rule 1, new binding. That is why this.name = name inside a constructor writes onto the new object. Same rule you already know, now with a name for where the object came from.

Write new yourself and it stops being magic

function fakeNew(Ctor, ...args) {
  const obj = Object.create(Ctor.prototype);   // steps 1 + 2: create AND link
  const ret = Ctor.apply(obj, args);           // step 3: run body with this = obj
  return (typeof ret === "object" && ret !== null) ? ret : obj;   // step 4
}

function Cat(name) { this.name = name; }
Cat.prototype.meow = function () { return this.name + " meows"; };

const fake = fakeNew(Cat, "A");
Object.getPrototypeOf(fake) === Cat.prototype;  // true
fake.meow();                                    // "A meows"
fake instanceof Cat;                            // true   ← indistinguishable from `new`

Four lines. That is the entire new operator. Object.create(proto) is the primitive that does steps 1 and 2 — make an object whose prototype is this. Remember that; it is the whole of §6.

One honest limitation of fakeNew fakeNew(Dog, "X") on a class throws TypeError. Classes refuse to be invoked without new — that is a deliberate ES6 guard, and .apply is not new. It works on old-style function constructors, which is exactly what it is demonstrating. Say this yourself if you ever write fakeNew on a whiteboard; noticing your own limitation is the senior move.

The fourth step has a quirk worth one line: if a constructor returns an object, that object wins and the freshly built one is discarded. Return a primitive, or nothing, and you get the new object. This is the basis of the "can a constructor return something?" question.

3 · Dog.prototype is NOT Dog's prototype

This is the worst naming collision in JavaScript, and §5 gives it one table row. It deserves a diagram.

Two completely different arrows come out of the word Dog:

                    ┌─────────────────────────┐
                    │   Dog   (a function)    │
                    └─────────────────────────┘
                       │                    │
     .prototype ───────┘                    └─────── its OWN prototype
     "the object I will HAND                        "what Dog itself
      to instances I build"                          inherits from"
                       │                                    │
                       ▼                                    ▼
          ┌────────────────────────┐          ┌──────────────────────┐
          │    Dog.prototype       │          │  Function.prototype  │
          │  { bark, constructor } │          │  { call, apply, bind}│
          └────────────────────────┘          └──────────────────────┘
                       ▲
                       │  ← Object.getPrototypeOf(rex)
                       │
          ┌────────────────────────┐
          │   rex  { name: "Rex" } │
          └────────────────────────┘
Object.getPrototypeOf(Dog) === Dog.prototype;        // FALSE  ← the trap
Object.getPrototypeOf(Dog) === Function.prototype;   // true   ← Dog is a function
Object.getPrototypeOf(rex) === Dog.prototype;        // true   ← rex is what it's FOR

rex.prototype;                                       // undefined ← instances don't have one
The fix: rename it in your head, permanently Every time you read Dog.prototype, say Dog.protoForMyInstances.

It is a delivery box, not Dog's own parent. The property is badly named — it should have been Dog.instancePrototype — and once you rename it internally, the collision stops existing. Only functions have .prototype. Every object has a prototype. Two different things that unfortunately share a word.
Dog.prototypeObject.getPrototypeOf(rex)

And they are the same object: Object.getPrototypeOf(rex) === Dog.prototype → true. One object, two names, two viewpoints.

Say Object.getPrototypeOf in an interview, never __proto__. __proto__ is a deprecated accessor kept alive for the web — and you already met its setter in 5b §7, where it was the prototype-pollution vector. Same property, both pages.

4 · One lookup, traced all the way

Now the chain is just "follow the arrow until you find it or run out."

rex.toString()

   rex                { name: "Rex" }                    toString? ✗
    │
    ▼   getPrototypeOf
   Dog.prototype      { bark, constructor }              toString? ✗
    │
    ▼
   Object.prototype   { toString, hasOwnProperty, ... }  toString? ✓  STOP
    │
    ▼
   null                                                  (the end of every chain)
Object.getPrototypeOf(rex) === Dog.prototype;             // true
Object.getPrototypeOf(Dog.prototype) === Object.prototype; // true
Object.getPrototypeOf(Object.prototype);                  // null

rex.toString();       // "[object Object]"  — found at depth 2

And when it runs out:

rex.fly();     // TypeError: rex.fly is not a function

Read that error message properly, because it is the most common error in JavaScript. It does not mean "fly is broken." It means the whole chain was walked to null, nothing called fly was found, so rex.fly is undefined, and you tried to call undefined. "X is not a function" almost always means "X was never found."

This is the same walk §5 shows for arrays, now with the mechanism underneath it:

const arr = [1, 2, 3];
arr.map(fn);
//  arr  →  Array.prototype  (map found here)  →  Object.prototype  →  null

Object.getPrototypeOf([]) === Array.prototype;             // true
Object.getPrototypeOf(Array.prototype) === Object.prototype; // true

You have used the prototype chain in every line of JavaScript you have ever written. Every .map, every .length, every .toString was a chain walk. It was never an advanced topic. It was just never named.

The chain can be cut deliberately Object.create(null) makes an object with no prototype at all. Object.getPrototypeOf(bare) is null and bare.toString is undefined. This is the standard safe-dictionary trick: no inherited keys, and immune to the __proto__ pollution from 5b §7, because there is no Object.prototype in the chain to hold that setter.

5 · Reads walk the chain. Writes never do.

§5 states this and moves on. Here is the mechanism, and it is one you already own.

function Student(name) { this.name = name; }
Student.prototype.company = "Hexagon";

const s1 = new Student("A"), s2 = new Student("B");

s1.company;                    // "Hexagon"  — not own. found on the prototype.
Object.hasOwn(s1, "company");  // false

s1.company = "Other";          // ← the write

s1.company;                    // "Other"
Object.hasOwn(s1, "company");  // true      ← a NEW own property was created
s2.company;                    // "Hexagon" — untouched
Student.prototype.company;     // "Hexagon" — untouched

The write did not travel up the chain and overwrite the shared value. It created a fresh own property on s1 that sits in front of the inherited one. That is shadowing. Proof that the original is still there, unharmed:

delete s1.company;
s1.company;                    // "Hexagon"  ← the shadow lifted, the inherited value reappears
   BEFORE                          AFTER s1.company = "Other"

   s1 { name }                     s1 { name, company:"Other" }  ← shadow
    │  company? ✗                   │  company? ✓ STOP
    ▼                               ▼
   Student.prototype               Student.prototype
   { company:"Hexagon" } ✓         { company:"Hexagon" }  still there, unreached

Why writes behave that way — and it is not a new rule

Assignment does walk the chain. §5's phrasing is a useful simplification, but the precise version is the one you learned this morning in 5b §5:

One mechanism, two pages [[Set]] walks the prototype chain looking for a setter. If it finds one, that setter runs. If it finds a plain data property instead, it stops looking and creates an own property on the object you started from.

So "writes don't walk" really means "writes walk, but only accessors can catch them."

And that is testable. An inherited setter does fire, and creates no own property:

function P() {}
Object.defineProperty(P.prototype, "v", { set(x) { console.log("fired"); this._v = x; } });

const p = new P();
p.v = 1;                       // "fired"   ← an INHERITED setter caught the write
Object.hasOwn(p, "v");         // false     ← no shadow was created
p._v;                          // 1

This is why 5b was worth building before this page. Shadowing and the Object.assign discriminator are the same mechanism seen from two angles.

The one case where "it changed all of them" is true

function Team() {}
Team.prototype.tags = [];          // a shared MUTABLE object on the prototype

const t1 = new Team(), t2 = new Team();
t1.tags.push("x");

t2.tags;                           // ["x"]   ← every team sees it
t1.tags === t2.tags;               // true    ← one array, always was

No shadowing happened, because there was no assignment. t1.tags is a read — which walks the chain, finds the shared array, and hands it over. Then .push mutates the thing everyone is pointing at. This is §3's copy-or-reference rule one level down. Never put a mutable value on a prototype. It is why class fields exist.

6 · The three shapes are one mechanism

§5 calls these "two spellings." They look like three unrelated things. They are one thing: something sets the link, and everything else is syntax.

ShapeWhat sets the linkLinked to
Object.create(proto)you do, by handproto
new Fn()new, step 2Fn.prototype
class + newnew, step 2 — identicalClass.prototype
class B extends Aextendslinks B.prototype → A.prototype
 
const protoA = { hi() { return "hi"; } };

const a = Object.create(protoA);                       // by hand
Object.getPrototypeOf(a) === protoA;                   // true

function F() {}  F.prototype = protoA;                 // via new
Object.getPrototypeOf(new F()) === protoA;             // true

extends quietly sets two links, not one — and the second one is the question people miss:

class Animal { speak() { return "..."; }  static create() { return "made"; } }
class Puppy extends Animal {}

Object.getPrototypeOf(Puppy.prototype) === Animal.prototype;  // true ← instance methods
Object.getPrototypeOf(Puppy) === Animal;                      // true ← STATIC methods

Puppy.create();                                               // "made" — statics inherit too

Two parallel chains: one for instances, one for the classes themselves. That second chain is how a subclass inherits static members, and almost nobody can name it.

Now, and only now, the §5 closing line is earned. Say it:

"Explain prototypal inheritance."

"JavaScript doesn't have classical inheritance — it has objects linked to other objects. Reading a property walks that chain of links until it finds the key or hits null. class is syntactic sugar over it: new links the instance to Class.prototype, and extends links one prototype to another, which is the same link Object.create sets by hand."

7 · Where class members actually land

class T {
  name  = "T";                  // field  → the INSTANCE
  reg()   { return this.name; } // method → T.prototype, shared
  arrow = () => this.name;      // field  → the INSTANCE, one per object
}
const t = new T(), t2 = new T();

Object.hasOwn(t, "reg");        // false  — on the prototype
Object.hasOwn(t, "arrow");      // true   — own, per instance
Object.hasOwn(t, "name");       // true   — own, per instance

t.reg   === t2.reg;             // true   — ONE shared function
t.arrow === t2.arrow;           // false  — a separate function each. memory cost.

Methods go on the prototype. Fields go on the instance. That one line is the whole rule, and it explains the carry item in §5.

It also explains the copying result — and note that the popular version of this fact is wrong:

{ ...t };     // { name: "T", arrow: [Function] }

Not {}. Fields survive the spread, methods do not. Two independent reasons, and you should say both:

  • reg is not own — it lives on T.prototype, and spread takes own properties only.
  • reg is also not enumerable — class methods are deliberately non-enumerable, like built-ins. Either reason alone would have excluded it.
Object.getOwnPropertyDescriptor(T.prototype, "reg").enumerable;  // false

A class with only methods and no fields spreads to {}. A class with fields does not. "Own and enumerable" — the phrase from 5b, deciding an outcome again.

Why arrow fields survive extraction, and methods don't

const pulled = t.reg;
pulled();            // TypeError — lost the dot (rule 4), and class bodies are strict,
                     //             so `this` is undefined rather than globalThis

const a = t.arrow;
a();                 // "T" — the constructor enclosed the arrow. permanent.

The follow-up, and it is asked: "so why not always use arrow fields?" → they cost one function object per instance, a subclass can't override them through the prototype chain, and prototype-level tooling like spies can't see them. Hooks made most of the argument moot — a function component has no this to lose.

8 · Quick checks

Is Object.getPrototypeOf(Dog) === Dog.prototype true?

No, and this is the central trap. Dog.prototype is the box Dog hands to its instances. Dog's own prototype is Function.prototype, because Dog is a function. The true identity is Object.getPrototypeOf(rex) === Dog.prototype.

Which step of new creates the prototype link?

Step 2, immediately after the empty object is made. Create, link, run the body with this bound, return. Object.create(Ctor.prototype) does steps 1 and 2 in one call.

s1.company = "Other" where company is on the prototype:

Creates an own property on s1. The prototype and every other instance are untouched. delete s1.company lifts the shadow and the inherited value reappears — which proves nothing was overwritten.

What does rex.fly is not a function actually tell you?

The whole chain was walked to null and nothing was found, so rex.fly is undefined and you called undefined. "X is not a function" nearly always means "X was never found."

9 · Cold drills — predict the output

Cover the answers. Say the output and which link produced it. All outputs run on Node 20.

D1 — class A { m(){} }
const a1 = new A(), a2 = new A();
console.log(a1.m === a2.m, Object.hasOwn(a1, "m"));

true false

One shared function, reached through two pointers, owned by neither instance. This is §1's optimisation stated as an assertion. If you said false true, you are still imagining methods being copied into each object — that is the model this page exists to replace.

D2 — function F(){}
console.log(Object.getPrototypeOf(F) === F.prototype, Object.getPrototypeOf(new F()) === F.prototype);

false true

The collision, as a one-liner. F's own prototype is Function.prototype — F is a function. F.prototype is the box F hands to instances, which is why the second one is true. Read F.prototype as F.protoForMyInstances and this stops being a trick.

D3 — function T(){}
T.prototype.tags = [];
const x = new T(), y = new T();
x.tags.push(1); x.count = 1;
console.log(y.tags, y.count);

[ 1 ] undefined

The line that separates the two halves of §5. x.tags.push(1) is a read followed by a mutation — it walks the chain, finds the one shared array, and mutates it, so y sees it. x.count = 1 is a write — it creates an own property on x and never touches the prototype, so y.count is undefined. Same object, two lines, opposite outcomes.

D4 — class B extends A {} where A has static make(){}. Is B.make available, and which link provides it?

Yes — via Object.getPrototypeOf(B) === A

extends sets two links: B.prototype → A.prototype for instance methods, and B → A for statics. Most candidates know the first and have never thought about the second. Naming the static chain out loud is a genuine differentiator.

D5 — const o = Object.create(null);
console.log(o.toString, "toString" in o);

undefined false

No prototype means no chain to walk, so none of Object.prototype's methods exist on it. This is the safe-dictionary idiom, and it is immune to the __proto__ pollution from 5b §7 — there is no Object.prototype in the chain to hold that setter. Trade-off: you lose toString, hasOwnProperty, and friends, which is why Object.hasOwn(o, k) exists as a standalone.

D6 — class T { f = 1; m(){} }
console.log({ ...new T() });

{ f: 1 }

Not {}, and not { f: 1, m: [Function] }. The field is own and enumerable so it survives; the method fails on both counts — it is on the prototype and non-enumerable. Say both reasons. A class with methods only would spread to {}, which is where the common half-memory of this fact comes from.

The locked 08-07 method: no outputs, no explanations. For each, say own or inherited, and what set the link. 60 seconds. Bar is 7/8.

  2. rex.bark where bark(){} is a class method
  3. [].map

Answers

1 own — constructor assignment · 2 inherited from Dog.prototype, link set by new step 2 · 3 inherited from Array.prototype, link set by the array literal · 4 inherited from Object.prototype, two hops up · 5 own — class fields land on the instance · 6 inherited, link set by Object.create by hand · 7 inherited via the static chain Puppy → Animal, set by extends · 8 own — the write created a shadow.

The traps are 5 and 8. Both look inherited — 5 is declared inside a class body next to the methods, and 8 is a name that genuinely exists on the prototype. Both are own. The discriminator: ignore where it was written, ask what Object.hasOwn would say. This is surface-shape matching, the course's most durable failure mode, in its fifth costume.

11 · The sentences you say

"What does new do?"

"Four things: creates an empty object, links its prototype to the constructor's .prototype, runs the constructor body with this bound to that object, and returns it — unless the constructor explicitly returns an object, which wins. The linking step is the one that matters, because that is what makes the prototype chain exist."

"prototype vs __proto__?"

".prototype only exists on functions, and it's the object that function will hand to the instances it constructs. __proto__ — properly Object.getPrototypeOf — exists on every object and is what that object actually inherits from right now. They meet in one identity: Object.getPrototypeOf(new Dog()) === Dog.prototype. Same object, seen from the factory and from the product."

"Why does the prototype chain exist?"

"So behaviour is stored once instead of copied into every object. A thousand instances share one bark function. Reads walk the chain to find it; writes always create an own property on the object in front of you, which is why assigning to an inherited key shadows it instead of changing it for everyone."
