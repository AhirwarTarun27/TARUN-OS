Lesson 6 · Module 6 — JavaScript Foundations

Arrays & iteration

Lesson 5 asked is this the same object or a new one. Every array method asks it again, out loud: does it return something, and did the original change?

Where this sits, and what the 10-03 probe found Arrays are objects, so everything from Lesson 5 applies: arr2 = arr is the same array, slice is a shallow copy, and .map is found by walking the prototype chain. This lesson is the toolkit on top of that.

It was built from your six-question probe, not from the ebook's order. The probe showed the mechanism is mostly there and the labels are loose: map and filter were close but not exact (filter was described inverted), the callback's third argument came out as this, sort was only half described, and for...in vs for...of was a clean "no idea". So the lesson spends its time on exactly what each method returns and on the two loops.

Not in this lesson: Map, Set, WeakMap, WeakSet. They get their own page next, because "Map vs a plain object" was also a clean "no idea" and deserves its own floor.

0 · Gate check — carried from Lesson 5

Two items from the 10-03 drill. Both were missed on the surface word, not on the mechanism. Answer both before you scroll.

freeze is shallow — what does each line do? 
const fa = Object.freeze([{ n: 1 }]);
fa[0].n = 2;
fa.push(3);
console.log(fa[0].n, fa.length);

fa[0].n = 2 works. It follows fa[0] to the inner object, which was never frozen. Freeze locked the array, one level only.

fa.push(3) throws TypeError — even without "use strict". This is the part that corrects the L5 rule of thumb. Plain assignment (fa[1] = 3) on a frozen array is silently ignored in sloppy mode, but the built-in methods (push, pop, sort) are specified to throw regardless of mode. So console.log is never reached. Verified on Node.

Say it as: "Freeze is shallow. And mutating methods on a frozen array throw TypeError in any mode, while a bare = only throws in strict mode."

slice — deep or shallow, and what does that mean for the objects inside? 
const a = [{ n: 1 }];
const b = a.slice();
b[0].n = 2;
console.log(a[0].n, a === b, a[0] === b[0]);

2 false true. A new array (a === b is false), but the elements are the same objects (a[0] === b[0] is true). slice() is a shallow copy, the same as [...a]. It only looks deep on an array of numbers, because there is nothing nested to share.

1 · The one question every array method answers

Before the individual methods, learn the question. For any array method, ask two things in this order:

  1. What does it return? A new array, the same array, a single value, a boolean, or undefined.
  2. Did the original change?

Almost every array bug, and almost every array interview question, is a wrong answer to one of those two. The methods fall into three groups. Memorise the groups, not the list.

GroupMethodsReturnsOriginal changes?
Changes the original push pop shift unshift splice fill reverse sort varies: new length, removed item, removed items, or the same arrayyes
Returns a new array map filter slice concat flat [...arr] a new arrayno
Returns one answer find findIndex indexOf includes some every reduce join at an element, an index, a boolean, a string or one reduced valueno
Returns nothing forEach undefinedonly if your callback mutates
The two that fool people sort and reverse change the original and also return it. Because they return an array, they look like the "new array" group, and they are not. The returned value and the original are the same array: arr.sort() === arr is true. Your probe answer on sort said "it mutates, it doesn't return a new array", which is correct about the first half. The second half is that it does return something, and that something is the original.

Modern fix: toSorted(), toReversed(), toSpliced() are the non-mutating twins (Node 20+, current browsers). They return a new array and leave the original alone.

What each mutator returns (added after the 10-04 drill)

"Changes the original" says nothing about what comes back. In the drill, push and pop were labelled SAME because they mutate, and sort was called "a new array" three times. Ask "what did it return?" as its own question, first. Do not let the answer to question 2 fill in question 1.

MutatorReturns
push unshiftthe new length
pop shiftthe removed element
splicean array of the removed elements
sort reverse fillthe same array (arr.sort() === arr)

concat sounds like "add", but it is the add that does not mutate: it returns a new array.

2 · The callback contract

Every iteration method calls your function with the same three arguments, in this order:

arr.map((value, index, array) => ...)
//        1      2      3

The third one is the array itself, not this. Your probe said "value, index, this". That is the label to fix, and it is an easy one to mix up for a reason: there is a this involved, but it is a different thing.

  • this inside the callback is decided by the L4 rules. A plain function callback is called bare by map's code, so it gets the default binding. An arrow callback inherits from its enclosing function.
  • The method has an optional second argument, thisArg: arr.map(fn, thisArg). That is how you set this for a non-arrow callback. It is an argument to map, not to your callback.

The trap that proves you know the contract

["1", "2", "3"].map(parseInt)
// [1, NaN, NaN]

It looks like it should be [1, 2, 3]. It is not, because map calls parseInt("1", 0, arr), then parseInt("2", 1, arr), then parseInt("3", 2, arr). parseInt takes (string, radix), so the index became the radix. Radix 0 means "default to 10" so the first one works. Radix 1 is invalid and radix 2 has no digit 3, so you get NaN. The fix is to pass only what you mean: .map(s => parseInt(s, 10)) or .map(Number).

Say it as: "map passes three arguments, so a function that takes optional second and third parameters gets the index and array as well."

2b · Who actually calls your callback

Added after the 10-04 drill, where two misses had one root: the callback was read as the body of a loop. It is not. It is a separate function, and the method's own code calls it, once per element. Roughly, this is inside forEach and map:

for (let i = 0; i < arr.length; i++) {
  cb(arr[i], i, arr);   // YOUR function is called here, fresh, every time
}

Three facts fall straight out of that one line:

  • return ends that one call, not the loop. The loop is in forEach's code, and you cannot reach it. [1, 2, 3, 4].forEach with if (x === 2) return; still runs for 3 and 4.
  • map stores whatever comes back, including undefined. A bare return; does not mean "keep the original": [1, 2, 3].map(x => { if (x === 2) return; return x * 10; }) is [10, undefined, 30].
  • A function passed by name gets all three arguments. That is the whole parseInt trap above: ["10", "10", "10"].map(parseInt) is [10, NaN, 2].

This is the L4 call-point rule in an array costume: find the ( that actually runs the function. Drill A (myMap) is writing that loop yourself, which is why it is the fix.

3 ·map, filter, forEach, reduce

Four methods, one sentence each, with the label that was loose in your probe.

MethodThe callback must returnThe method returns
mapthe new value for this elementa new array, same length
filtertruthy = keep, falsy = dropa new array, equal or shorter
forEachnothing (the return value is ignored)undefined
reducethe next accumulatorone value, whatever the accumulator ended as

Two corrections to the probe, because both were the exact thing an interviewer listens for:

  • map's callback is not a condition. It is a transformation: it returns the new element. map always produces one output per input.
  • filter keeps the elements the callback is true for. The probe said "removing the values which is true", which is inverted. filter(x => x > 2) keeps the ones greater than 2.
[1, 2, 3, 4].filter(x => x % 2)          // [1, 3]  — kept where truthy (1 and 3 give 1)
["a", "", 0, 1, null, "b"].filter(Boolean)  // ["a", 1, "b"]  — drops every falsy value

Two things that go wrong

1. A block body with no return gives you an array of undefined. The probe question "what happens if you ignore the result of map" has two answers, and this is the second:

[1, 2, 3].map(x => { x * 2 })
// [undefined, undefined, undefined]   // braces = a block, so no implicit return
[1, 2, 3].map(x => x * 2)
// [2, 4, 6]

2. Using map and throwing the result away. It still builds a whole new array, which is wasted work and, more importantly, tells the reader you wanted a loop. If you do not use the returned array, you wanted forEach (or for...of). Say it: "map when I want the new array, forEach when I want the side effect." forEach cannot be chained, since it returns undefined, which is why .forEach(...).map(...) throws. It also cannot be stopped: return inside the callback only skips that one call, and break is a syntax error.

You wrote this yourself on 10-01 ua.some(obj => obj.name === arr[i].name) in the unique-objects drill. The mistake you fixed there, some with !==, is the whole of §4: some asks "does any element match", so the question you put in the callback has to be the match, and the negation goes outside.

4 · find, findIndex, some, every

These four stop early and return one answer. The decision is: what do I want back?

You wantUseReturns if nothing matches
the elementfindundefined
its positionfindIndex-1
yes/no: is any a matchsomefalse
yes/no: are all matcheseveryfalse (on a non-matching element)
Two traps, both asked in interviews 1. findIndex returns -1 for "not found", and -1 is truthy. if (arr.findIndex(x => x > 5)) is true when nothing matched, and false when the match is at index 0. Compare to -1 explicitly, or use some / find.

2. Empty arrays. [].some(...) is false, because no element can match. [].every(...) is true — "all of nothing" is vacuously true. That second one surprises people, and it is why your unique drill worked: on the first pass ua was empty, ua.some(...) was false, and so the first item was pushed with no special case.

One more fact that matters in React: find returns the element itself, not a copy. users.find(u => u.id === 2).id = 99 edits the object that is inside users. That is the L5 identity rule, now inside an array method.

5 · slice vs splice

The ebook marks this one "most helpful in problem solving", and it is the one you got half of in the probe (you knew splice mutates).

slice(start, end)splice(start, deleteCount, ...items)
Changes the original?noyes
Returnsa new array of the copied partan array of the removed items
end / countend index, exclusivehow many to remove, not an end index
Negative numberscount from the end (slice(-2) is the last two)same for start
Can insert?noyes: the extra arguments
 
const s = [1, 2, 3, 4, 5];
s.slice(-2)        // [4, 5]   s is still [1,2,3,4,5]
s.slice(1, 3)      // [2, 3]   index 3 is excluded

const sp = [1, 2, 3, 4, 5];
sp.splice(1, 2, "a")   // returns [2, 3]  (the removed items)
sp                      // [1, "a", 4, 5]  (the original, now changed)

The one that catches people: splice's return value is what you removed, not the array you now have. const result = arr.splice(...) gives you the cut-out pieces, and arr is the one that changed. And slice is shallow, which you proved in §0.

6 · sort, the trap with a name

This is the one I want to be careful about, because your probe answer was correct about mutation and you did not give the output, and the output is the whole question.

[10, 9, 1].sort()
// [1, 10, 9]

The default sort converts everything to strings and compares them as text. "10" comes before "9" because "1" is less than "9" character by character. It does not sort numbers by size. That is not a bug in your code, it is the specified default, and it is the most-asked sort question there is.

[10, 9, 1].sort((a, b) => a - b)      // [1, 9, 10]  — a comparator fixes it

Three rules for the comparator:

  1. It returns a number: negative means "a first", positive means "b first", zero means "keep the order".
  2. It must not return a boolean. (a, b) => a > b returns true or false, which become 1 and 0, and never a negative. On Node 24, [3, 1, 2].sort((a, b) => a > b) returns [3, 1, 2] — unchanged. Use subtraction for numbers.
  3. sort mutates and returns the same array (§1). To keep the original, copy first: [...arr].sort(...), or use toSorted.

Two more facts on defaults. undefined always goes last: [3, undefined, 1, null, 2].sort() is [1, 2, 3, null, undefined]. And strings sort by character code, so capitals come before lowercase: ["b","a","C","B"].sort() is ["B","C","a","b"].

Say it like this "The default sort compares as strings, so [10, 9, 1] comes out [1, 10, 9]. For numbers I pass (a, b) => a - b. It sorts in place and returns the same array, so in React I copy first."

7 · for...in vs for...of

This was a clean "no idea" in the probe, and it connects to two things you already know, so it is quicker than it looks.

for...infor...of
Gives youthe keysthe values
Type of what you getalways a stringwhatever the element is
Walks the prototype chain?yes — inherited enumerable keys toono
Works onany objectonly iterables (arrays, strings, Map, Set, NodeLists)
break / continue / awaityesyes
 
for (const i in [10, 20]) console.log(typeof i, i + 1);
// string 01      string 11      // i is "0", so "0" + 1 is "01"

for (const v of "hi") console.log(v);
// h      i

Why for...in on an array is a trap. It is the L5 §6 fact again: it walks the chain and returns every enumerable key. If anyone adds to Array.prototype, or you put an extra property on the array (a.foo = "bar"), for...in returns it too, while for...of only walks the real elements ([1, 2, 3, foo] gives for...in four keys and for...of three values; length stays 3). And because the key is a string, i + 1 concatenates.

Why for...of on a plain object throws. A plain object has no Symbol.iterator, so for (const x of { a: 1 }) {} throws TypeError ("... is not iterable"). Same label as L2 and L5. To loop an object's values, go through an array first:

for (const [key, value] of Object.entries({ a: 1 })) console.log(key, value);
// a 1

You used Object.entries in deepClone. That is why.

The rule of thumb: for...in is for object keys, for...of is for array values. On an array you almost never want for...in.

8 · The procedure — the seventh question

Six questions so far. This module adds the seventh, and it is the array version of Q6:

  1. Which keyword declares it?
  2. What state is the binding in at this exact line?
  3. What are you doing to it?
  4. When does this actually run — and what is the binding at that moment?
  5. How was this function called — and is it an arrow?
  6. Is this the same object or a new one — and is the property own or inherited?
  7. What does this method return — and did the original change?

Say it once per method call on the page and you will not need to memorise the table.

9 · Retrieval quiz

[10, 9, 1].sort() returns…

[1, 10, 9]. The default sort compares as strings, character by character. The array is also changed in place, and the value returned is the original array.

What does filter(x => x > 2) do with the elements the callback is true for?

Keeps them. Truthy means keep, falsy means drop. The result is a new array, equal in length or shorter.

Which one returns the removed items instead of the array you now have?

splice. It changes the original and hands back what it cut out. slice leaves the original alone and returns a copied part.

The third argument a map callback receives is…

The array itself. (value, index, array). this is set separately, by the L4 rules or by the method's own thisArg second argument.

[].every(x => false) returns…

true. "Every element passes" is vacuously true when there are no elements. [].some(...) is false. The pair is worth remembering as a pair.

10 · Output drills

Cold. Fresh snippets. For each, run question 7 before you answer: what does it return, and did the original change? Give the value and the label.

D1 · map returns a new array 
const d1 = [1, 2, 3];

d1r.push(9);

D2 · sort returns the same array

[1,2,3,0] 4. d2r and d2 are the same array, so the push shows up in d2. D1 and D2 look identical and are opposite. That is the whole point of §1.

D3 · splice returns the removed

const d3r = d3.splice(1, 2);

[1,4,5] [2,3]. d3 lost the two items. d3r is the two that were cut out, not the array you now have.

D4 · forEach returns nothing 
const d4 = [1, 2, 3].forEach(x => x * 2);
console.log(d4);

undefined. forEach ignores the callback's return value and returns undefined itself. Both halves are the question.

D5 · for...in gives strings 
const d5 = ["a", "b"];
for (const i in d5) console.log(i + 1);

"01" then "11". i is the string "0", so + 1 concatenates. Not 1 and 2.

D6 · the copy that wasn't there 
const d6 = [5, 1, 10];
const d6s = [...d6].sort();
console.log(d6, d6s);

[5,1,10] [1,10,5]. The spread made a copy, so the original is untouched. The sorted copy is lexicographic, so 10 comes before 5. Two facts at once: the copy protects the original (§1), and the default sort is string order (§6).

D7 · find returns the element, not a copy 
const users = [{ id: 1 }, { id: 2 }];
const found = users.find(u => u.id === 2);
found.id = 99;
console.log(users);

[{id:1},{id:99}]. find hands you the element itself. Editing found edits the object inside users. L5 identity, inside an array method.

11 · Label-only round

No outputs, no explanations. For each call, pick one label. The bar is 7/8, and the planted trap is one that looks like it returns a new array.

  • NEW — returns a new array, original unchanged
  • SAME — changes the original and returns that same array
  • REMOVED — changes the original and returns what it removed
  • NOTHING — returns undefined
  • ONE — returns a single value, original unchanged
  1. arr.map(f)
  2. arr.sort()
  3. arr.splice(1, 1)
  4. arr.forEach(f)
  5. arr.slice(1)
  6. arr.find(f)
  7. arr.reverse()
  8. arr.filter(f)
Answers
  1. map — NEW
  2. sort — SAME
  3. splice — REMOVED
  4. forEach — NOTHING
  5. slice — NEW (and shallow)
  6. find — ONE (the element itself, not a copy)
  7. reverse — SAME
  8. filter — NEW

#2 and #7 are the planted traps. They return an array, so they pattern-match to "NEW". They are SAME: arr.sort() === arr. This is surface-shape matching in its seventh costume: "it returns an array, so it must be a copy."

12 · Coding drills

Drill A — write myMap

Write Array.prototype.myMap(callback, thisArg) so that [1, 2, 3].myMap((v, i) => v * i) returns [0, 2, 6]. Attempt it before opening anything. Start with the three lines you can say out loud: make an output array, loop over the indexes, call the callback with value, index, array.

Hint ladder, then the answer

Hint 1. Inside a method, this is the array you called it on. You are using L4's rule 3: left of the dot. That is also why this cannot be an arrow function. An arrow would not get the array as this.

Hint 2. The callback needs thisArg as its own this. Which L4 method sets this for one call?

Array.prototype.myMap = function (cb, thisArg) {
  const out = [];
  for (let i = 0; i < this.length; i++) {
    if (i in this) out[i] = cb.call(thisArg, this[i], i, this);
  }
  return out;
};

What it proves at once: L5 (you are adding a method to Array.prototype, so every array finds it by walking the chain), L4 (this is the array because of the dot; cb.call(thisArg, ...) is rule 2; it must be a regular function, not an arrow) and §2 (the callback gets value, index, array). The i in this check skips holes in a sparse array, which is what the real map does: [1,,3].myMap(x => x) keeps the hole, same as [1,,3].map(x => x).

Limitation to say yourself: it does not validate that cb is a function, and it adds an enumerable property to Array.prototype, which shows up in for...in on every array. That is the §7 trap, now caused by you. Real code would use Object.defineProperty with enumerable: false (the descriptor from 5b).

Drill B — the second largest element

The ebook's problem 25. Return the second-largest number in an array. Then say what you return for [5, 5, 3], [2, 2], [1] and []. Attempt it before opening anything.

Two edge cases decide this question

Duplicates. "Second largest" means the second-largest distinct value in the usual reading, so [5, 5, 3] returns 3, not 5. Ask the interviewer. Asking is the senior move.

Too few values. [2, 2], [1] and [] have no second-largest. Return undefined, and say so.

function secondLargest(arr) {
  let first = -Infinity, second = -Infinity;
  for (const n of arr) {
    if (n > first) { second = first; first = n; }
    else if (n < first && n > second) second = n;
  }
  return second === -Infinity ? undefined : second;
}

One pass, O(n), no sorting. The brute-force version sorts with (a, b) => b - a and takes index 1, which is O(n log n) and also needs the comparator from §6. n < first is the line that handles duplicates: a repeat of the maximum must not become the second. Outputs: [5,5,3] gives 3; [2,2], [1] and [] give undefined; [1,9,9,4] gives 4 (all verified).
