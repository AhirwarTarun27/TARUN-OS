Lesson 5 · Module 5 — JavaScript Foundations

Objects & prototypes

Lesson 4 asked what is this when the method runs. This one asks the two questions underneath it: where does the method actually live, and is this the same object or a different one.

Where this sits You have spent four lessons on things that are decided by position — scope is decided by where a variable is written, closures by where a function is written, this by where the call happens. Objects are the first topic decided by identity: two objects with identical contents are still two different objects, and one object with two names is still one object. Almost every bug in this module is a wrong answer to "same one, or a new one?"

The second half is prototypes — the mechanism that has been quietly running since Lesson 1. Every time you called .length, .map, .toString, you used it. Lesson 4 taught you to read the call site for this; this lesson teaches you to read the lookup path for the method itself.

0 · Gate check — carried from Lesson 4

Two items from the 08-07 drill were taught and never re-tested cold. Answer both out loud, before you scroll. A third carry item — arrow class field vs prototype method — is deliberately not here. It belongs to this module, so it is tested in §5 where it lands naturally.

Does an arrow function survive being pulled off its object? Say when, and say the rule that decides it.

It depends on one thing only: is there a real function enclosing the arrow? Not "is it an arrow" — you already know it is.

const o = { n: "O", f: () => this.n };
const a = o.f;
a();                       // undefined — an object literal is NOT a scope,
                           // so the arrow reached past it to module/global
                           // (in a real ES module `this` is undefined, so this THROWS)

function C() {
  this.n = "T";
  this.f = () => this.n;   // the CONSTRUCTOR encloses this arrow
}
const b = new C().f;
b();                       // "T" — survives extraction, .call(), and setTimeout

You answered undefined for the second one on 08-07. The arrow captured C's this at construction time, and that capture is permanent — stronger than bind, because there is no this to rebind. The discriminator to say out loud: "does a real function enclose the arrow?" Object literal → no → global. Constructor or method → yes → that function's this.

What does f.call.bind(f, ctx) produce, and why would anyone write it?

It produces a function that, when called, runs f with this = ctx — the same thing as f.bind(ctx), taken the long way round.

Unpick it left to right, and the only trick is noticing which function bind is being called on. It is not called on f. It is called on f.call:

f.call            // → Function.prototype.call, a normal function value
f.call.bind(f, ctx)
//  ^^^^^^ bind's receiver is `call` itself
//         arg 1 (f)   → becomes `this` INSIDE call  → the fn call will invoke
//         arg 2 (ctx) → becomes call's first arg    → the `this` f will see

This is the uncurry-this idiom. The real-world version is Object.prototype.hasOwnProperty.call.bind(Object.prototype.hasOwnProperty) — a standalone hasOwn(obj, key) that works even on objects that don't inherit from Object.prototype. You will almost never write it; you should be able to read it. It is the same failure as the .call dot trap at higher difficulty: the dot before bind tells you nothing, the receiver of bind is whatever sits immediately to its left.

1 · Objects, and the ways to make one

An object is an unordered collection of key → value pairs, where every key is a string or a symbol, and every value is anything. The ebook flags "different ways to create an object" as most asked — the answer is a list, so learn it as a list and deliver it as one.

2 · Every key is a string (the one that already bit you)

Object keys are strings or symbols — never anything else. Hand a key anything else and it is coerced with String() first.

const o = {};
o[1] = "a";
o["1"] = "b";
console.log(o);              // { "1": "b" }  — ONE key. 1 and "1" are the same key

o[{ id: 7 }] = "x";
console.log(o);              // { "1": "b", "[object Object]": "x" }
You met this in the memoize session, 07-30 Your v2 cache was a plain {} keyed by the argument. It worked for numbers and broke the moment an object went in, because every object stringifies to the same "[object Object]". That is what pushed v3 to Map + JSON.stringify(args). Same fact, filed under objects instead of closures.

Map is the fix when keys must keep their type: a Map key can be an object, a function, NaN, anything, and it is compared by reference identity — the §3 rule below.

3 · Copy or reference — the sentence that scores

The ebook asks this as "pass by value vs pass by reference". That framing is the common one and it is slightly wrong, and knowing why is free marks.

JavaScript is always pass-by-value. What differs is what the value is. For a primitive, the value is the data. For an object, the value is a reference — so copying the variable copies the arrow, not the thing it points at.

function tweak(o) {
  o.n = 2;              // follows the reference → the CALLER's object changes
  o = { n: 99 };        // repoints the local arrow → caller sees nothing
  return o;
}

const a = { n: 1 };
const b = tweak(a);
console.log(a.n, b.n);  // 2 99
Say it like this "Technically JavaScript is always pass-by-value — but for objects the value is a reference, so mutation is visible to the caller and reassignment is not. The precise name for that is call by sharing."

That last sentence is worth memorising verbatim. It is the difference between reciting a table and understanding it, and it is exactly the shape of answer this course has been grading you on — the mechanism plus the label.

This is the same fact as the Lesson 4 gate item, seen from the other side. === on objects compares reference identity, never contents:

{ a: 1 } === { a: 1 }        // false — two objects
const x = { a: 1 }, y = x;
x === y                      // true  — one object, two names
Where this shows up in React — have this ready state.items.push(x) mutates in place, so the reference never changes, prevState === nextState is true, and React skips the re-render. That is why you replace instead of mutate: setItems([...items, x]). Immutability in React is not a style preference — it is how change detection works.

4 · Shallow vs deep copy

A shallow copy gives you a new top-level object whose nested values are still the same references. A deep copy recursively rebuilds every level, so nothing is shared.

const orig = { id: 1, tags: ["a"], meta: { ok: true } };

const shallow = { ...orig };
shallow.id = 2;              // top level → independent
shallow.tags.push("b");      // one level down → SHARED

console.log(orig.id);        // 1
console.log(orig.tags);      // ["a", "b"]  ← the bug
TechniqueDepthWhat it costs you
{ ...obj }shallowOwn enumerable props only. Prototype is dropped — you get a plain object
Object.assign({}, obj)shallowSame, but it assigns rather than defines, so setters on the target fire
structuredClone(obj)deepThe modern native answer. Handles Date, Map, Set, RegExp and circular references. Throws on functions; class instances come back as plain objects
JSON.parse(JSON.stringify(obj))deepThe old trick, and it silently destroys things — see below
Hand-written recursion / lodash cloneDeepdeepFull control. The interview follow-up asks you to write it (§13)
What the JSON round-trip silently eats Functions → gone · undefined values → gone · symbols → gone · Date → an ISO string · Map/Set → {} · NaN/Infinity → null · the prototype → gone, so a class instance comes back as a plain object · circular reference → throws TypeError · BigInt → throws.

"It's a deep copy but it loses functions, dates and undefined" is the answer that scores. You met the type-loss half of this in memoize v3, where you serialized arguments and had to reason about what survives the trip.
The spread-vs-assign discriminator, if they push Both are shallow and both copy own enumerable properties. The real difference: Object.assign uses assignment, so a setter already on the target object will run; spread defines properties, so it never triggers setters. Almost nobody can name a difference at all.

5 · The prototype chain

Every object has a hidden link to another object — its prototype. When you read a property, JavaScript looks on the object itself, and if it isn't there it follows that link, and keeps following it until it hits null. That path is the prototype chain, and it is the whole of JavaScript's inheritance.

const arr = [1, 2, 3];
arr.map(...)
// `map` is not on arr. Lookup walks:
//   arr  →  Array.prototype  (found it)  →  Object.prototype  →  null

prototype vs __proto__ — the naming trap

Fn.prototypeobj.__proto__
Lives onfunctions onlyevery object
Means"the object I will hand to instances I construct""the object I actually inherit from, right now"
Modern spelling—Object.getPrototypeOf(obj) · Object.setPrototypeOf
The identityObject.getPrototypeOf(new P()) === P.prototype → true

__proto__ is a deprecated accessor kept alive for the web. Use it to read in a console; say Object.getPrototypeOf in an interview.

function Student(name) { this.name = name; }
Student.prototype.company = "Hexagon";           // shared by every instance

const s1 = new Student("A"), s2 = new Student("B");
s1.company;                     // "Hexagon" — found on the prototype
s1.company = "Other";           // creates an OWN property on s1. Shadows, does NOT overwrite
s2.company;                     // "Hexagon" — untouched
Student.prototype.company;      // "Hexagon" — untouched
The asymmetry that gets asked Reads walk the chain. Writes never do. Assigning always creates or updates an own property on the object in front of you. This is why "I changed one instance and it changed all of them" is almost never true for values — and why it is true when you mutate a shared object on the prototype (s1.tags.push(x) where tags lives on Student.prototype). §3's rule, one level down.

Prototypal inheritance, the two spellings

// ES5 — explicit
const package_ = { ship() { return "shipping " + this.name; } };
const application = Object.create(package_);
application.name = "app";
Object.getPrototypeOf(application) === package_;   // true

// ES6 — sugar over exactly the same thing
class Package { ship() { return "shipping " + this.name; } }
class Application extends Package {}

Say this and the topic is finished: "JavaScript doesn't have classical inheritance — it has objects linked to other objects. class is syntactic sugar over the prototype chain; extends just sets the link that Object.create sets by hand."

The follow-up, and it is asked: "so why not always use arrow fields?" → because they're allocated per instance, they can't be overridden by a subclass through the prototype chain, and they're invisible to prototype-level tooling like spies. Hooks made the whole argument mostly moot — a function component has no this to lose.

6 · Own vs inherited — and the four ways to ask

Once there is a chain, every question about properties splits in two: does this object have it, or can this object see it.

ExpressionOwn?Inherited?Note
Object.hasOwn(o, "k")✓✗The modern answer. ES2022
o.hasOwnProperty("k")✓✗Breaks on Object.create(null) — no prototype, no method
"k" in o✓✓Walks the chain — the bug you hit in memoize
Object.keys(o)✓✗Own enumerable only
for (const k in o)✓✓Enumerable, including inherited
 
const base = { a: 1 };
const child = Object.create(base);
child.b = 2;

Object.keys(child);            // ["b"]        — own only
const seen = [];
for (const k in child) seen.push(k);
seen;                          // ["b", "a"]   — walked into base
"a" in child;                  // true
Object.hasOwn(child, "a");     // false
Why for...in doesn't drown in built-ins Object.prototype is full of methods — toString, hasOwnProperty, valueOf — and for...in walks right past them. It sees none of them because they are non-enumerable. Enumerability is the filter; the chain is the path. Two separate dials.

keys / values / entries

const data = { name: "Sai", lang: "English" };

Object.keys(data);      // ["name", "lang"]
Object.values(data);    // ["Sai", "English"]
Object.entries(data);   // [["name","Sai"], ["lang","English"]]

Object.fromEntries(Object.entries(data).map(([k, v]) => [k, v.toUpperCase()]));
// { name: "SAI", lang: "ENGLISH" }  ← entries + fromEntries = map() for objects

All three return own enumerable string-keyed properties, as an array — which is the actual reason they exist: they turn an object into something you can map/filter/reduce (Module 6). Object.fromEntries is the return trip, and naming it unprompted is a small, cheap win.

One line each: freeze = read-only. seal = fixed shape, editable contents. Check with Object.isFrozen / Object.isSealed.

The two follow-ups that always come 1. Both are shallow. Object.freeze(cfg) does nothing to cfg.db.host. A "deep freeze" is a recursive walk you write yourself.
2. Failure is silent in sloppy mode and throws TypeError in strict mode — and modules and class bodies are strict by default, so in real modern code it throws.

That TypeError is the third time this course has landed on it: the illegal-operation error on a binding that was found. Reassigning a const, calling a non-function, writing to a frozen property — found it, operation not allowed.

8 · Destructuring, spread and rest

Three ES6 features the ebook asks separately and interviewers ask together. The trap is spread vs rest, because they are the same three dots doing opposite jobs.

// DESTRUCTURING — unpack into variables
const { name, lang: language = "en", meta: { ok } } = data;
//      ^rename↑         ^default        ^nested
const [first, , third = 0] = [1, 2];        // arrays destructure by POSITION

// SPREAD — expand one thing into many
const merged = { ...a, ...b };              // b wins on conflicts
Math.max(...[1, 2, 3]);

// REST — collect many things into one
const { id, ...everythingElse } = obj;      // remaining OWN ENUMERABLE props
function log(first, ...others) {}           // must be LAST
The one-liner that settles spread vs rest "Same syntax, opposite direction — and you can tell them apart by which side of the = they're on. On the right, it's spread: expanding. On the left (or in a parameter list), it's rest: collecting."

Two details worth having ready: object rest gives you omit-a-key without mutating (const { password, ...safe } = user), and destructuring a property that doesn't exist gives undefined, but destructuring from null or undefined throws a TypeError — which is why you see function f({ a } = {}) everywhere.

9 · The procedure — the sixth question

Five questions so far: three from M2, one from M3, one from M4. This module adds the sixth, and it is the one that catches object bugs before you write them.

  1. Which keyword declares it?
  2. What state is the binding in at this exact line?
  3. What are you doing to it?
  4. When does this actually run — and what is the binding at that moment?
  5. How was this function called — and is it an arrow?
  6. Is this the same object or a new one — and is the property own or inherited?

Question 6 has two halves because this module has two halves. The first half catches every copy/mutation bug; the second catches every prototype bug. Run both.

10 · Retrieval quiz

const c = { ...orig } — what did you get?

Own enumerable properties, one level deep. Nested objects are still shared references, and the prototype is not carried over — a spread of a class instance gives you a plain object.

After Object.seal(o), which one still works?

Changing an existing value. Seal fixes the shape — no adding, no deleting — but writable properties stay writable. That is the entire difference from freeze.

What does for...in give you that Object.keys doesn't?

Inherited enumerable properties. for...in walks the prototype chain; Object.keys stops at own properties. Neither one sees non-enumerables, which is why built-in methods never show up in either.

P.prototype vs p.__proto__ — which is true?

prototype lives on functions — it's the object instances will inherit from. __proto__ lives on every object — it's the link it does inherit through. They meet at Object.getPrototypeOf(new P()) === P.prototype. Say Object.getPrototypeOf out loud, not __proto__.

Which deep-copy method drops functions AND turns a Date into a string?

The JSON round-trip. structuredClone keeps Date as a real Date and throws on functions rather than silently dropping them. The other two aren't deep copies at all.

D7 · what the round-trip eats 
const o = { d: new Date("2020-01-01"), f() {}, u: undefined, n: NaN, s: new Set([1]) };

{ d: "2020-01-01T00:00:00.000Z", n: null, s: {} }. f and u vanish without trace, the Date is now a string, NaN became null, and the Set became an empty object. Five values in, three keys out. This is why structuredClone exists.

13 · Coding drills

Drill A — unique objects from an array

The ebook's problem 16. Attempt it before opening anything.

const arr = [{name:"sai"}, {name:"Nang"}, {name:"sai"}, {name:"Nang"}, {name:"111111"}];
// → [{name:"sai"}, {name:"Nang"}, {name:"111111"}]
First: why can't you just use Set or includes?

Because §3. new Set(arr) keeps all five — every object is a distinct reference, and Set compares by reference identity. Same reason arr.includes({name:"sai"}) is always false. You must dedupe by a derived key, not by the object. Getting to that sentence is the question.

Now find the two bugs in the ebook's answer 
const seen = {};
if (!seen[currentItem]) { uniqueArr.push(array[i]); seen[currentItem] = true; }

Bug 1 — the prototype chain. seen is a plain object, so it inherits from Object.prototype. Feed it {name:"toString"} and seen["toString"] finds the inherited function, which is truthy, so a first-time value is silently dropped as a duplicate. You already hit this exact bug in memoize on 07-30.

Bug 2 — it only dedupes by a hard-coded .name. Fine for the ebook's input, useless as an answer. Say so and generalise it.

The fixes, cheapest first: new Set() instead of {} (no prototype, no coercion), or Object.create(null), or Object.hasOwn(seen, k) instead of truthiness.

The version to write in an interview 
function uniqueBy(arr, keyFn) {
  const seen = new Set();
  return arr.filter(item => {
    const k = keyFn(item);
    if (seen.has(k)) return false;
    seen.add(k);
    return true;
  });
}

uniqueBy(arr, o => o.name);
uniqueBy(arr, o => JSON.stringify(o));   // dedupe on the WHOLE object

Then volunteer the limitation before they ask — the same one you found in memoize v3: JSON.stringify is key-order sensitive, so {a:1,b:2} and {b:2,a:1} serialize differently and won't dedupe. The fix is to sort the keys before stringifying. Naming a limitation in your own solution is the single most senior thing you can do in a coding round.

Drill B — write deepClone

The standard follow-up to §4. Handle nested objects and arrays; state your limitations out loud.

Answer + what to say about it 
function deepClone(value, seen = new WeakMap()) {
  if (value === null || typeof value !== "object") return value;   // primitives + functions
  if (seen.has(value)) return seen.get(value);                     // circular refs

  const out = Array.isArray(value) ? [] : {};
  seen.set(value, out);
  for (const [k, v] of Object.entries(value)) out[k] = deepClone(v, seen);
  return out;
}

Four things this proves at once: the base case is the primitive check (and typeof null === "object" is why the null guard comes first — Lesson 1); Object.entries gives you own enumerable properties, so inherited stuff is correctly excluded; the WeakMap handles circular references, which is the follow-up interviewers reach for; and it does not handle Date, Map, Set, or class prototypes — say that yourself, then say "which is what structuredClone is for."

Why WeakMap and not Map? Keys are held weakly, so the cache can't keep cloned objects alive. Module 6 covers this properly.
