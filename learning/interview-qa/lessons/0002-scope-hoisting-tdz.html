Lesson 2 · Module 2 — JavaScript Foundations

Scope, Hoisting & the TDZ

Where a variable lives, and when it starts existing. Two different questions — and interviewers test both in one snippet.

Where this sits Lesson 1 answered what a value is. This one answers where a name is visible and when it becomes usable. You need both before closures make any sense — a closure is literally "a function that kept its scope alive," so Module 3 is unreachable until this is solid. This is also the single most-asked cluster in the ebook: hoisting, TDZ, and let/var/const are all flagged "Most asked."

1 · Scope: the three kinds

Scope is the region of code where a name is visible. JavaScript has three:

  • Global scope — declared outside every function and block. Visible everywhere.
  • Function scope — declared inside a function. Visible anywhere in that function, including nested functions. var only respects this boundary.
  • Block scope — declared inside { } (an if, a for, or a bare block). Visible only inside those braces. let and const respect this; var ignores it completely.
function demo() {
  if (true) {
    var  a = "var";
    let  b = "let";
  }
  console.log(a);   // "var"  — var ignored the block, it's function-scoped
  console.log(b);   // ReferenceError — let stayed inside the { }
}
Say this in the interview "var is function-scoped, let and const are block-scoped. That single difference is why var leaks out of if blocks and loops."

The scope chain

When JavaScript can't find a name in the current scope, it looks in the enclosing scope, then the one outside that, up to global — then throws ReferenceError. That upward path is the scope chain, and it only goes outward, never inward.

const outerVal = "outer";

function parent() {
  const midVal = "middle";

  function child() {
    console.log(outerVal, midVal);  // "outer middle" — found by walking up
  }
  child();
}
console.log(midVal);   // ReferenceError — parent's scope is not visible from outside
Remember the direction Inner code can reach out. Outer code can never reach in. Hold onto that sentence — in Module 3 it becomes the definition of a closure.

2 · Hoisting: declarations move, assignments don't

Before running a line of your code, the JavaScript engine scans the scope and registers every declaration it finds. That's why you can use some things before the line that declares them. This is hoisting.

The trap: only the declaration is hoisted, not the assignment.

console.log(x);   // undefined  ← NOT an error, and NOT 5
var x = 5;
console.log(x);   // 5

// The engine effectively sees:
//   var x;          ← hoisted, auto-initialised to undefined
//   console.log(x); ← undefined
//   x = 5;          ← assignment stays put
Precision beats the textbook answer Most candidates say "declarations are moved to the top." Nothing physically moves — the engine registers declarations in the scope before execution. Saying it that way, then adding the words temporal dead zone, is exactly the follow-up bait interviewers want.

3 · What is hoisted, and how

This is a straight recall question in the ebook. Learn the table, not the vibes:

DeclarationHoisted?Usable before its line?
function foo() {} (declaration)Yes, fullyYes — body and all
var xYes, initialised to undefinedYes, but the value is undefined
let xYes, uninitialisedNo — ReferenceError (TDZ)
const xYes, uninitialisedNo — ReferenceError (TDZ)

var f = function(){} (expression)Only the varNo — f is undefined, calling it is a TypeError
var f = () => {} (arrow)Only the varNo — same TypeError
 
greet();          // "hi" — function declarations are fully hoisted
function greet() { console.log("hi"); }

speak();          // TypeError: speak is not a function
var speak = function () { console.log("yo"); };
// var speak was hoisted as undefined; undefined() is a TypeError, not a ReferenceError.
The distinction that scores points ReferenceError = the name isn't usable yet (or doesn't exist). TypeError = the name resolved fine, but the value isn't the kind of thing you just did to it. Naming the right error is a small detail that reads as real experience. MDN: Hoisting

4 · The Temporal Dead Zone

Here's the part people fumble: let and const are hoisted. They're registered in the scope from the very top. They're just not initialised. The window between entering the scope and reaching the declaration line is the temporal dead zone — the variable exists but touching it throws.

{
  // ── TDZ for `name` starts here ──
  console.log(typeof other);  // "undefined" — undeclared names are fine with typeof
  console.log(typeof name);   // ReferenceError — TDZ isn't even safe for typeof
  let name = "Tarun";
  // ── TDZ ends at the declaration line ──
  console.log(name);          // "Tarun"
}
Say this in the interview "The temporal dead zone is the period between a let/const being hoisted into the scope and its declaration being evaluated. The binding exists but is uninitialised, so any access throws a ReferenceError. It exists on purpose — it turns a silent undefined bug into a loud error."

Notice the why in that last sentence. var's hoisting hands you undefined and lets the bug travel downstream. The TDZ was ES6 deciding that failing immediately is better. Interviewers remember candidates who explain the design intent.

5 · var vs let vs const — the full answer

Flagged "Most asked" in the ebook. Answer on four axes, in this order:

The const follow-up they always ask const freezes the binding, not the value. You can't point the name at something else, but if it points at an object you can still mutate its insides. const u = {n:1}; u.n = 2; is legal. u = {} throws TypeError: Assignment to constant variable. (Want a genuinely immutable object? That's Object.freeze — Module 5.)

6 · The classic: "it prints 6 every time"

The single most-asked output question in the ebook, and it's pure scope. Read it before the answer:

function x() {
  for (var i = 1; i <= 5; i++) {
    setTimeout(() => { console.log(i); }, i * 1000);
  }
}
x();   // 6, 6, 6, 6, 6 — one second apart
Why 6, and why five times?

Two facts collide. One: var i is function-scoped, so there is exactly one i for the whole loop — not one per iteration. All five arrow functions close over that same single variable. Two: setTimeout is asynchronous — the callbacks don't run during the loop, they run after it finishes (full mechanics in Module 7). By the time the first one fires, the loop has already run its exit check, which is what pushed i to 6. Five callbacks, all reading the same variable, all seeing 6.

Fix 1 — the one-character fix

Change var to let. let is block-scoped, and a for loop creates a fresh binding per iteration — five separate is, each frozen at its own value. Output: 1 2 3 4 5. This is the answer to give first, because it's what you'd actually write.

for (let i = 1; i <= 5; i++) {
  setTimeout(() => console.log(i), i * 1000);
}
Fix 2 — the pre-ES6 fix (say this one too)

Wrap the timer in a function call. Every call creates a new function scope with its own parameter, so each callback captures a different variable. This is the ebook's closure solution — and giving both fixes shows you understand why let works, rather than having memorised it.

function x() {
  function closur(n) {                      // new scope per call
    setTimeout(() => console.log(n), n * 1000);
  }
  for (var i = 1; i <= 5; i++) closur(i);   // 1 2 3 4 5
}
You just met a closure That inner function remembering n after closur already returned is a closure. Module 3 names it and drills it — you've now seen the problem it solves before the definition, which is the right order.

7 · The three-question procedure

Knowing the rules is not the same as applying the right one under pressure. The failure mode is pattern-matching on the shape of a snippet and firing a rule you recognise, instead of reading the actual state of the binding. Run these three questions on every identifier, in order, and never skip ahead to the answer.

  1. Which keyword declares it? function declaration · var · let · const · class · parameter · nothing
  2. What state is the binding in at this exact line? not registered (undeclared) · registered but uninitialised (TDZ) · registered holding undefined · holding a real value
  3. What are you doing to it? reading · calling · assigning · typeof

The outcome falls straight out of the intersection:

Re-run question 2 after every line State changes as the program executes. Hoisting only decides the starting state — an assignment further down still runs at its own line. The most common slip is answering correctly for line 1, then never re-reading the state before answering for line 4.
The two no-ops worth memorising A bare var a; when a already holds a value does nothing — it does not reset to undefined. Same for var a when a is already a parameter. The declaration was processed at parse time; re-stating it later is dead weight. Both show up as "guess the output" questions constantly.

8 · Retrieval check

No scrolling up. Answer, then read the explanation.

What does this log? console.log(a); var a = 10;

undefined. The declaration var a is hoisted and auto-initialised to undefined; only the assignment a = 10 stays on its original line. Swap var for let and this becomes a ReferenceError.

Which of these is hoisted and usable before its line?

The function declaration. It's the only one hoisted with its body, so calling it early works. let and class are hoisted but sit in the TDZ; an arrow assigned to var hoists only the variable, so calling it early is a TypeError.

Inside the TDZ, what does typeof myLet do?

It throws. typeof is famously safe on undeclared names — it returns "undefined" instead of throwing. That safety net does not extend to the TDZ. A great follow-up answer to have ready.

Which line throws? const u = {n:1}; then…

u = {n:2}. const locks the binding, not the contents — mutating, adding and deleting properties are all fine. Only pointing the name at a new value throws TypeError: Assignment to constant variable.
Bonus (harder): what does this log, and why? 
var v = "global";
function test() {
  console.log(v);
  var v = "local";
}
test();

undefined — not "global". The inner var v is hoisted to the top of test, which shadows the global v for the entire function body. So the lookup never walks up the scope chain; it finds the local v, which is still undefined at that point. This is called variable shadowing, and it's the cleanest one-snippet proof of why hoisting matters.
