Lesson 3 · Module 3 — JavaScript Foundations

Functions, Closures & HOFs

The 99%-asked topic. A function that remembers where it was born, and every pattern built on top of that one fact.

Where this sits Lesson 2 ended on one sentence: inner code can reach out, outer code can never reach in. That was not a throwaway line. It is the closure. This lesson names it, proves it, and then shows you the five interview patterns that are all the same trick wearing different clothes. The ebook flags "what is a closure" as asked in 99% of interviews. Nothing else in the JavaScript half pays better.

0 · Gate check — carried from Lesson 2

One item stayed open: naming the right error. Answer both before you scroll.

Which error, and why? const n = 5; n = 6;

TypeError: Assignment to constant variable.

The rule in one sentence, worth memorising word for word: the name resolved fine, so the reference is not the problem — the operation on that binding is illegal, therefore TypeError. A ReferenceError means JavaScript could not find the name at all (undeclared) or was forbidden from touching it yet (TDZ).

Find vs do. Can't find it → ReferenceError. Found it, illegal operation → TypeError.

Which error? var f; f();

TypeError: f is not a function. Same test: the name f resolved perfectly, it holds undefined. Calling undefined is the illegal operation. Compare g(); with no g anywhere → ReferenceError: g is not defined.

1 · Functions are values

Everything in this lesson follows from one property: in JavaScript a function is just a value. You can store it in a variable, pass it as an argument, return it from another function, or stick it in an array. This is what "functions are first-class citizens" means.

// declaration — hoisted with its body (Lesson 2)
function add(a, b) { return a + b; }

// expression — only the variable hoists
const sub = function (a, b) { return a - b; };

// arrow — same hoisting story as the expression
const mul = (a, b) => a * b;

const ops = [add, sub, mul];        // stored in an array, totally normal
console.log(ops[2](3, 4));          // 12
Watch the parentheses add is the function value. add() is the result of calling it. Passing add() where you meant add is the single most common beginner bug in every callback and event handler, and it's a favourite interview typo-spotting question.

2 · The lexical environment

Lexical means "determined by where it's written in the source," not by where or when it's called. Every function, the moment it's created, gets an invisible reference to the scope it was born in. That reference is its lexical environment.

Critically, that reference is attached at authoring time and never changes. Move the function, call it from anywhere, hand it to a library: it still points home.

function outer() {
  const secret = 42;
  function inner() {
    console.log(secret);   // reaches out to outer's scope
  }
  return inner;            // ← we hand `inner` OUT, without calling it
}

const fn = outer();        // outer() has now FINISHED and returned
fn();                      // 42 — how? outer's scope should be gone.

3 · So: what is a closure?

What is a closure? (asked in ~99% of interviews)

A closure is a function bundled together with the lexical environment it was created in. Because of that bundle, the function keeps access to its outer variables even when it is executed somewhere else entirely, long after the outer function has returned.

In the snippet above, outer() finished and returned. Normally its local variables would be garbage collected. They aren't, because inner still holds a live reference to that environment. JavaScript keeps secret alive for exactly as long as something can still reach it.

Say this in the interview "A closure is a function plus its lexical environment. Every function in JavaScript closes over the scope where it was defined, not where it's called, so it can still read those variables after the outer function has returned. That's what makes private state, function factories and once/memoise patterns possible."
The word that scores Say lexical and mean it. Plenty of candidates say "a function inside a function." That's a description of the shape, not the mechanism, and the follow-up ("so why does it still work after the outer function returned?") is where they fall over. You already have the answer: the environment reference is attached at authoring time and keeps the scope alive.

You already met this in Lesson 2

The "prints 6 every time" fix. Here it is again, now with the real name on it:

function closur(n) {                          // each CALL makes a new environment
  setTimeout(() => console.log(n), n * 1000); // the arrow closes over THAT n
}
for (var i = 1; i <= 5; i++) closur(i);      // 1 2 3 4 5

Five calls, five separate lexical environments, five separate ns. With bare var i there was only ever one environment and therefore one i. And let works for the same reason: the for loop builds a fresh binding per iteration, so each arrow closes over a different one. Same mechanism both times.

The fourth question — added after the 2026-07-30 drill

Lesson 2 gave you a three-question procedure: which keyword declares it, what state is the binding in at this line, what are you doing to it. That procedure assumes the read happens on the line you're looking at. A closure breaks that assumption, because it moves the read into the future.

Question 4 When does this function actually run — and what is the binding at that moment? Never read a closed-over variable at the line where the function was written. Read it at the line where the function is called.

The whole trap is that a closure captures the variable, not a copy of its value. Arguments, by contrast, capture the value at call time. Knowing which of the two you're looking at answers almost every deferred-read question:

And the mirror of that: a mutation to a closed-over variable persists across calls, because there is only one of it. a.inc() twice on a counter leaves n at 2, not 1 — the environment is not rebuilt per call, only per call of the factory.

The operator that decides the return value Same side effect, different value handed back — and interviewers pick whichever one you didn't expect:
  • n++ (post) → returns the old value, then increments. A counter built on n++ yields 0 1 2.
  • ++n (pre) → increments, then returns the new value. The same counter yields 1 2 3.
After three calls n is 3 either way. The difference is only what each call evaluated to. Read the operator before you read the sequence.

4 · Closures in practice: private state

This is what closures are actually for, and the counter is the classic whiteboard ask.

function makeCounter() {
  let count = 0;                    // unreachable from outside — genuinely private
  return {
    inc:   () => ++count,
    value: () => count
  };
}

const c = makeCounter();
c.inc(); c.inc();
console.log(c.value());   // 2
console.log(c.count);     // undefined — no way in

const c2 = makeCounter(); // a SECOND, independent environment
console.log(c2.value());  // 0 — not 2
The follow-up they ask "Why is c2 zero?" Because each call to makeCounter creates a new lexical environment. Closures capture an environment per invocation, not per function definition. If you can explain that, you've shown you understand closures rather than having memorised the shape.

5 · Callbacks

What is a callback?

A function passed as an argument to another function, to be called later.

function greet(name, callback) {
  console.log("Hi " + name);
  callback();                    // called later, by someone else
}
greet("Tarun", () => console.log("done"));
// Hi Tarun
// done

Where you meet them: setTimeout, array methods (map, filter, forEach), DOM event handlers, and any async work. Note the overlap with the last section: a callback almost always is a closure, because it gets executed inside some other function's scope while still reading variables from where you wrote it. That's the whole reason callbacks are usable at all.

6 · Higher-order functions

What is a higher-order function?

A function that takes a function as an argument, returns a function, or both.

// takes a function
[1, 2, 3].map(n => n * 2);        // map is a HOF

// returns a function (a "function factory")
function multiplier(factor) {
  return n => n * factor;          // closes over `factor`
}
const double = multiplier(2);
const triple = multiplier(3);
console.log(double(5), triple(5)); // 10 15
The connection to name out loud A HOF that returns a function is only useful because of closures. Without them, the returned function would forget factor the instant multiplier returned. Interviewers love hearing the two concepts linked instead of recited separately. Advantages to list if pushed: abstraction, reusability, composition, and readable async code.

7 · Pure vs impure functions

PureImpure
Same input → same outputalwaysnot guaranteed
Side effectsnoneyes
Touches outside stateneverreads or mutates it
 
// PURE — depends only on its arguments, changes nothing
const greet = name => `Hello ${name}`;

// IMPURE — reads outside state, so the output can change under it
let msg = "Hello";
const greet2 = name => `${msg} ${name}`;

// IMPURE — mutates its input (a side effect)
const addItem = (arr, x) => { arr.push(x); return arr; };

// PURE version — returns a new array instead
const addItemPure = (arr, x) => [...arr, x];
The React tie-in (say this, it lands) "Pure functions are predictable, testable and cacheable. It's why React expects render to be pure and why you never mutate state directly — you return a new object. useMemo and React.memo only work because the same input reliably gives the same output." That connects the JavaScript half of the interview to the React half, which very few candidates do.

A "side effect" is anything a function does beyond returning a value: mutating an argument, writing to a global, logging, hitting the network, touching the DOM. Note the honest bit worth saying out loud: impure is not a synonym for bad. Every useful program needs side effects. The discipline is keeping them at the edges instead of scattered through your logic.

8 · IIFE

An Immediately Invoked Function Expression runs the moment it's defined.

(function () {
  console.log("runs immediately");
})();

(() => {
  console.log("arrow flavour");
})();

The wrapping parentheses matter. They force JavaScript to read function as an expression rather than a declaration, and only expressions can be invoked on the spot.

Why it existed, and why you rarely write one now Before ES6 there was no block scope. An IIFE was the only way to get a private scope and keep variables off the global object. Modules and let/const replaced that job. Saying "IIFEs solved the scoping problem that let and modules now solve" is a much better answer than the definition alone, because it shows you know why a feature exists.

9 · Arrow functions

Advantages: shorter syntax, implicit return for single expressions, and no own this — which removes a whole category of binding bugs in callbacks.

What are the limitations of arrow functions? (straight recall)

  1. Not hoisted with a body — they follow the function-expression rule from Lesson 2.
  2. No arguments object.
  3. No own this — they inherit it from the enclosing scope.
  4. Cannot be used as constructors — new throws a TypeError.
  5. Cannot be generator functions (no yield).
const Person = (name) => { this.name = name; };
new Person("Tarun");   // TypeError: Person is not a constructor
Deliberately parked Item 3 is the big one, and it's the whole of Module 4. For now hold exactly this much: an arrow has no this of its own, so it uses whatever this the surrounding code had. Next lesson explains what decides that value. The ebook warns that "arrow function + this" combination questions get asked heavily here, so we're giving it a full module rather than a bullet point.

10 · Coding drills

Predict, then write it yourself before opening the answer. These are standard live-coding asks and all three are closures.

Write once(fn) — a function that runs fn only the first time 
function once(fn) {
  let called = false;       // private, per call to once()
  let result;
  return function (...args) {
    if (called) return result;
    called = true;
    result = fn(...args);
    return result;
  };
}

const init = once(() => { console.log("init!"); return 1; });
init();  // "init!" → 1
init();  // (silent)  → 1

The flag lives in the closure. Nothing outside can flip it back, which is exactly why this is trustworthy.

Write memoize(fn) — cache results by argument 
function memoize(fn) {
  const cache = {};                   // survives between calls via closure
  return function (n) {
    if (n in cache) return cache[n];
    cache[n] = fn(n);
    return cache[n];
  };
}

const slowSquare = n => { for (let i = 0; i < 1e7; i++); return n * n; };
const fast = memoize(slowSquare);
fast(9);   // slow the first time
fast(9);   // instant — served from the closed-over cache

Mention the caveat and you'll stand out: this key-by-argument version only works for primitive arguments, and the cache grows forever. In production you'd bound it or use a Map. And note why memoisation is safe here: fn must be pure. Caching an impure function returns stale answers.

What does this log, and why? 
function make() {
  let n = 0;
  return () => ++n;
}
const a = make();
const b = make();
console.log(a(), a(), b());

1 2 1. a and b came from two separate calls, so they closed over two separate environments. b's n was never touched by a. This is the single fastest way to check whether someone actually understands closures or just recognises the shape.

11 · Retrieval check

Why can a returned inner function still read the outer function's variable?

It kept its lexical environment. The function holds a live reference to the scope it was defined in, so that scope isn't garbage collected. Nothing is copied, nothing goes global, and outer really did return.

What does const f = multiplier(2) return, if multiplier returns n => n * factor?

A function that closed over factor = 2. multiplier is a higher-order function because it returns a function, and that returned function is a closure. Nothing is computed until you call f(...).

Which of these is a pure function?

(a, b) => [...a, b]. It returns a new array and mutates nothing. The others mutate an outer array, produce a different result every call, and mutate an outer counter. Same input, same output, no side effects — both halves are required.

Which is not a limitation of arrow functions?

They can absolutely be passed around. Arrows are values like any function — that's the whole point of first-class functions. The other three are real limitations, along with "not hoisted" and "cannot be generators".
Bonus (harder): why does this print 3 3 3, and what are the two fixes? 
const fns = [];
for (var i = 0; i < 3; i++) {
  fns.push(function () { return i; });
}
console.log(fns[0](), fns[1](), fns[2]());

Same mechanism as Lesson 2's setTimeout question, with the async part stripped away — which proves the bug was never about timing at all. One var i means one binding; all three functions closed over the same environment, and the loop left i at 3. Fix 1: let i, giving a fresh binding per iteration. Fix 2: push ((n) => () => n)(i), creating a new environment per iteration by hand. Saying "it isn't a timing bug, it's a single-binding bug" is the answer that ends the follow-ups.
